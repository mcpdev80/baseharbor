## Product fixes in this continuation

- Restore SQL archives through stdin: omit the filename argument to
  `pg_restore`; explicitly disable Compose TTY allocation for binary streams.
- Restore in a single SQL transaction, avoiding partially applied DDL/data.
- Bind both recovery streams and restore receipts to the actual Target in
  addition to installation, provider, transaction and original version.
- Persist `sql_started`, `sql_restored`, and `recovered` receipts under the
  central provider transaction. Configuration recovery retries do not repeat
  a committed SQL restore. Concurrent initial restore claims use `O_EXCL`.
- An interrupted or failed SQL command can have an unknown server COMMIT
  outcome. It stays BLOCKED for database reconciliation; it is never blindly
  retried. This remains an explicit limitation, not automatic crash recovery.
- Attest the etcd cluster before taking a snapshot from a single endpoint;
  native `etcdctl snapshot save` does not accept a multi-endpoint request.
- Accept a snapshot revision newer than pre-snapshot status; reject an older
  revision. A real write between those operations exercises this behavior.
- Generate an identity/snapshot-bound recovery cluster token shared by all
  restored members. Never reuse the live bootstrap token.
- Persist Patroni replica completion only after quorum/readiness has returned;
  completed three-member roll replays verify all images without another restart
  or switchover.
- Validate permanent Patroni `initialize`/`config` data on isolated DCS boot.
  Leased leader/member keys are not durable recovery evidence. This is namespace
  validation, not live Patroni readiness or PostgreSQL system-ID crosschecking.
- Serialize native provider updates with the existing Core bootstrap lifecycle
  lock before inventory/backup. The same installation lock covers different
  releases and is automatically released by the kernel on process exit.
- Bind the existing hosted rootless Core bootstrap Docker/Podman matrix to
  pushes of the authorized work branch. It does not call pre-release workflows,
  create tags, publish images or operate on persistent self-hosted runners.
- Apply native etcd leader-ID derivation to the separate `EtcdBootProbe` too;
  its status-without-`isLeader` regression rejects contradictory helper flags.
- The hosted Podman bootstrap gate failed in a Keycloak init dependency's
  completion wait (run 37936333789). Replace inverse `is-active` guessing with
  positive successful exit/timestamp evidence, retain init state using
  `RemainAfterExit=yes`, and test completed/never-started/running/failed cases.
  The new live gate must establish whether this resolves the bootstrap failure.
- Keep in-flight work-branch gates running when another fix is pushed; the
  workflow concurrency group serializes runs. Capture only fixture lifecycle
  state and credential-free error categories before failed fixture cleanup.
- The Docker bootstrap run also failed when `keycloak-db-init` exited 1.
  Static inspection found the single Keycloak PostgreSQL service executing its
  root entrypoint with all capabilities dropped. Run the database as `postgres`
  with a read-only root filesystem and writable scratch mounts; its existing
  transient TLS initializer also prepares only the owned data-volume directory
  permissions. Live acceptance of this correction is still required.
- Derive leadership from etcd member/leader IDs. Actual v3 StatusResponse
  does not contain `isLeader`; contradictory optional helper flags are rejected.

## Evidence and its limits

The exact final SHA and completed checks are recorded in PR #837 after commit.
Local verification uses Go 1.27.2. The real-process gate uses release-pinned
etcd 3.7.2; its official Linux archive SHA-256 is
`3a3679bc51a4ee9d30bccea1da7cd4fe62c6fc1d2ca1255068d2c53bf3026135`.

The opt-in `TestRealEtcdMTLSSnapshotRestoreQuorum` launches six processes in
sequence, three live and three restored, with loopback-only endpoints and a
private temporary directory. It uses the real PKI, native snapshot store,
etcdctl and etcdutl; proves mTLS rejection without a client identity, preserved
keys/revision, new member/cluster IDs, and exactly one leader across three
restored members. It kills only the processes it starts.

This gate runs under UID 0 in this sandbox because switching to UID 1000 is
not permitted. It is **not** a Docker, Podman-rootless, Patroni, Spilo or
live-Core DCS-cutover acceptance result. Its production RuntimeProvider
transport remains subject to those gates.
