# BaseHarbor v0.4.1 release audit

## Scope

Target issue: #156, capability/provider/resource/binding core.

The implementation stays within the intended v0.4.1 boundary:

- shared capability/provider/resource/binding domain types;
- fail-closed capability/provider negotiation;
- reusable non-interactive lifecycle model;
- machine-readable plan/status/verification/diagnostic results;
- minimal PostgreSQL, Valkey and OpenBao adoption to prove the model;
- unchanged Manifest v1 and Compose-first developer workflow.

Explicitly deferred to later releases:

- provider registry and shared/dedicated/external ownership (#157);
- additional capability products;
- public generic capability manifest changes;
- Kubernetes/OpenShift/cloud runtime or provider implementations.

## Architecture alignment

Application intent remains provider-neutral.

Runtime providers and capability providers remain independent axes.

The shared capability core lives below the CLI and has no terminal prompting dependency. Its structured results can be consumed by the CLI, future HTTP/Web UI surfaces and future Operator reconciliation.

Existing Compose orchestration remains authoritative rather than being duplicated behind a premature generic provider framework.

## Lifecycle

The reusable capability lifecycle is:

```text
resolve
  ↓
preflight all resources
  ↓
apply
  ↓
bind
  ↓
verify
```

Provider/capability negotiation occurs during planning. Unsupported combinations fail before provider hooks run.

All planned provider preflights complete before the first provisioning mutation is allowed.

## Existing-provider proof

Current application requirements resolve as:

```text
database.sql    -> PostgreSQL
cache.key-value -> Valkey
secrets         -> OpenBao
```

Protected runtime `bindings/metadata.json` now records the resolved logical capability/provider/workload bindings while preserving the existing standard PostgreSQL/Valkey environment and file bindings.

The existing real protocol verification paths remain authoritative:

- PostgreSQL authenticated query verification;
- Valkey authenticated PING/PONG verification;
- OpenBao application scope/authentication verification.

## Compatibility

- Manifest v1 unchanged.
- Existing v0.4.0 repositories require no migration.
- Compose remains the complete runtime implementation.
- Existing application environment variables and binding files remain unchanged.
- Capability metadata is additive protected runtime state.

## Security

- Unsupported capability/provider mappings fail closed before mutation.
- Secret values and provider credentials do not enter capability requirements, resources, bindings, plans or diagnostics.
- Existing OpenBao and runtime credential boundaries remain unchanged.
- No capability registry ownership semantics are invented before #157.

## Documentation audit

All maintained documentation surfaces were reviewed for v0.4.1, including README, changelog, architecture, application contract, provider model, roadmap, release/versioning guidance, CLI/operations documentation, German maintained documentation, ADRs and historical release material.

Historical ADRs, previous release notes and previous release audits keep their original version references intentionally.

Corrections made during the final audit:

- removed the premature README claim that v0.4.1 was already the latest published stable release before the tag existed;
- updated current English and German roadmap headings to the v0.4.1 foundation;
- updated the German architecture boundary from v0.4.0 to v0.4.1;
- rewrote the v0.4.1 release notes around user impact, rationale, compatibility and deferred scope instead of commit history;
- made the mandatory per-task pre-release requirements explicit in the development guidelines.

## Validation

Executable release candidate `31c512055307bfa6a9e9e2f8a5c5b124be76e62b` passed the complete required matrix: CI, release-check, documentation/pages, runtime image, developer journey, PostgreSQL backup/restore, OpenBao backup/restore, application backup/restore, runtime-broker acceptance, runtime-broker performance and MailFlow acceptance.

The final changes after that executable head are documentation-only. Per the repository CI policy, they require only the lightweight documentation/release validation and must not trigger another expensive runtime acceptance matrix.

## Outcome

v0.4.1 establishes the smallest reusable capability-provider foundation needed for subsequent v0.4.x work without changing the application-facing v0.4 contract.
