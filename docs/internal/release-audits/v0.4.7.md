# Pre-release documentation audit

Target release: `v0.4.7`.

Latest published stable release before this release: `v0.4.6`.

## Scope

Issue #162: OpenTelemetry and OTLP transport/binding foundation.

Implemented:

- `telemetry.otlp/v1` as the provider-neutral transport capability;
- explicit export direction with OTLP HTTP/protobuf as the initial v1 transport;
- trace, metrics and logs signal declarations in Manifest v1;
- typed OTLP binding in the shared capability lifecycle and Provider Protocol v1;
- OpenTelemetry Collector 0.161.0 as a lazy shared Compose reference provider;
- external OTLP endpoint placement without BaseHarbor provider lifecycle ownership;
- standard `OTEL_*` workload injection without a BaseHarbor SDK;
- stable OpenTelemetry service/environment identity plus BaseHarbor application/resource/provider attribution;
- provider lifecycle instrumentation hooks for preflight/apply/bind/verify using metadata-only observations;
- real OTLP export verification in apply/up/show/status/doctor;
- shared-provider lifecycle ownership and global destroy cleanup;
- manual-only Docker/Compose Collector acceptance workflow;
- explicit negative coverage proving OTLP does not provision Prometheus, Loki, Tempo or Grafana.

Not implemented and not claimed:

- Prometheus metrics storage/collection provider;
- Loki log storage provider;
- Tempo/Jaeger trace storage provider;
- Grafana/dashboard integration;
- OTLP/gRPC application binding;
- application-hosted/receive-mode OTLP;
- advanced sampling/routing/OpAMP;
- Kubernetes/OpenShift Collector realization.

## Architecture review

- OpenTelemetry is treated as the instrumentation ecosystem; OTLP is the portable protocol boundary.
- The OpenTelemetry Collector is a provider implementation and never appears as portable application identity.
- External and managed OTLP destinations satisfy the same capability semantics.
- Provider placement, concrete endpoints, Collector configuration and authorization material remain deployment/provider state.
- The implementation reuses the v0.4.1 capability lifecycle, v0.4.2 provider registry, v0.4.4 endpoint/binding concepts and Provider Integration Contract v1.
- No parallel observability lifecycle or CLI-only business logic was introduced.
- OTLP transport remains separate from metrics/logs/traces platform providers.
- Compose remains first-class; no Kubernetes/OpenShift behavior is prematurely implemented.

## Security review

- External OTLP authorization is accepted through deployment/runtime `BASEHARBOR_OTLP_HEADERS`, not portable manifest content.
- Credential-bearing URLs, query parameters and URL fragments are rejected fail-closed.
- Provider registry and capability metadata contain provider/resource identity only, never authorization header values.
- Standard workload `OTEL_EXPORTER_OTLP_HEADERS` is materialized only at the trusted workload boundary for external providers.
- Provider lifecycle observations contain phase/status/application/capability/resource/provider/duration only; bindings, endpoints and credentials are intentionally excluded.
- Invalid/missing OTLP binding semantics fail before provider mutation.

## Readiness review

- Success is not based on Collector process liveness.
- BaseHarbor sends a real OTLP HTTP/protobuf trace and requires an accepted response from the resolved endpoint.
- Managed Collector startup waits for its OTLP receiver to accept traffic.
- `baha app show`, `status` and `doctor` use the materialized deployment binding and perform real OTLP verification.
- External provider verification retains external lifecycle ownership.
