## Registration

The adapter source is preserved under `internal/providerupgrade/**`. The integration API lives under `internal/providerbinding/**`, outside `internal/coreupdate/**` and the Session 1A exclusive files.

Session 1A should assemble `providerbinding.Dependencies` from the **existing Core install state** and existing runtime provider:

1. `RuntimeBinding{Reader: selectedRuntimeProvider, Engine: selectedKind, Sources: ...}` with exact, installation-owned `Project/Service` pairs discovered from the already persisted Core installation; never derive ownership from name alone.
2. OpenBao: the existing `openbao.Executor` and `runtime.Files`, plus Core-controlled `openbao.RuntimeHooks`. Backup/VerifyBackup and Restore MUST refer to durable SQL backing-store evidence. Never invent a local volume or treat an OpenBao process image as its database.
3. Keycloak: installation `DataDir/Namespace/InstallationID/ExpectedIssuer`, plus `keycloak.CoreHooks` populated by Session 1A's retained SQL/archive/configuration checkpoint and member lifecycle.
4. Call `providerbinding.New(deps)` and fail closed on any missing runtime, installed Keycloak Core material, SQL/recovery hook, semantic verifier, or invalid provider mapping.
5. For each provider plan, use `registry.Preflight(ctx, provider, request)` followed by the **central durable update journal** for adapter `Backup/Execute/Verify/Recover`. Do not call `Execute` before a verified `BackupRef`, and do not create another scheduler or journal.
6. A return from `registry.Resolve` means Core runtime ownership and immutable image identity were checked against the selected RuntimeProvider; the provider adapter performs its own inventory/owner/version/topology validations. Reject unowned targets, mixed member versions, missing PostgreSQL evidence, or unknown digest.

## Boundaries and hard failures

OpenBao native inspection, HA member checks, manager verification and unseal semantics use the existing OpenBao implementation. AppRole/policy and application-access verification MUST use actual runtime Core secrets via the explicitly provided callbacks.

Keycloak OIDC verification uses `identityprovider.VerifyCoreIdentity` and the installed Keycloak ownership/issuer; SQL, HA lifecycle, realms/clients/roles and token flows MUST be supplied by Core callbacks. Keycloak's `ExistingCoreRuntimeFiles` is read-only and must not bootstrap or reinitialize provider state.

Pre-mutation dependency, snapshot and topology errors are fatal. A post-mutation failure requires the central journal and verified recovery point, not a blind retry. Foreign resources must never be mutated or automatically adopted.
