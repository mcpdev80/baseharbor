# v0.4.24 package integration and upgrade acceptance

This runbook coordinates the three parallel implementation packages. **It is not evidence of an already completed runtime acceptance test.** Do not start prerelease, Docker, Podman or Kubernetes runtime gates until all packages are integrated and the operator requests them.

## Package ownership

- Package 1: Core, HA, upgrade safety, provider reconciliation and host trust. Core update changes must preserve product and user data; classify every provider delta as `no_change`, `safe_reconcile`, `backup_recovery_required`, `migration_required` or `unsupported`.
- Package 2: interactive CLI, Target selection, TUI, user-facing diagnostics, non-TTY and JSON/MCP parity. Its exclusive `cmd/baha/**` changes should not be edited by package 3.
- Package 3: documentation, Node Connector and Console contracts, integration tests, translations and P0 Next.js generator #844.

## Local/Hugging Face gates before integration

1. Check formatted Go source and `go test`/`go vet` for `internal/coreupdate`, `internal/hosttrust`, `internal/targetaccess`, `internal/machine`, `internal/development` and `internal/devgateway`.
2. Verify Package 2 target precedence, stale Target handling, CLI JSON/MCP schema and non-interactive errors through targeted unit and contract tests.
3. Validate Connector enrollment, CSR identity binding, symlink-safe private key reads and authorization-file handling.
4. Run Console contract tests, TypeScript checks, lint and production build; do not mistake the fixture preview for an authenticated live session.
5. Run EN/DE page parity, preserved code/literal integrity and strict `mkdocs.de.yml` build.

## Acceptance after combining the packages

Only after the combined branch is ready and explicitly approved:

1. Run the targeted Next.js greenfield Docker E2E manually; confirm the generated manifest exposure, Compose `PORT`, `8080:8080`, Dockerfile `EXPOSE` and healthcheck agree.
2. Verify the actual `baha app up` workflow yields HTTP 200 and `baha app destroy` removes owned resources. Bare `docker compose down` does not replace BaseHarbor lifecycle evidence.
3. Test `baha target activate`/effective Target precedence and remote Connector enrollment using real mTLS on Docker and Podman, separately.
4. Test the Console via real OIDC authentication against the matching Core and Connector SHA set.
5. Exercise Core update safe-reconcile, backup-required refusal, unsupported downgrade, interrupted-update recovery and owned host-trust cleanup. Ensure `destroy --all` does not orphan host-trust state.
6. Record gate name, candidate SHA, target/runtime, result, artifacts, retry scope and any exclusions. Restart **only** failed or invalidated gates after a fix. Run full prerelease only when these atomic gates are green.

## Failure interpretation

A 502/503/504 development-gateway response may mean that the Application upstream does not listen at the declared exposure port. Diagnose actual workload listener, selected Target and routed upstream first. Do not report missing canonical route by default, dump internal Caddy/state paths or flood repeated upstream logs.

## Upgrade safety

Before changing a Core provider, compare the installed realization with the desired digest/version, persist a durable update journal, obtain backup/recovery evidence when required and reject unsupported or ambiguous changes. Mutation follows plan → preflight → apply → verify. No successful status may be emitted until verification; interruptions must remain recoverable.

This guide is the cross-package checklist, not a substitute for implementation or runtime proof.
