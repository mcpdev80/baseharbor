# BaseHarbor v0.4.15 release audit

## Scope

v0.4.15 completes the Target, secure service-access, observability and agent-native lifecycle foundation before the later v0.4 audit/recovery/identity tracks and the v0.5 contract freeze.

Release-scoped work:

- #397 — TLS everywhere and environment-aware service access baseline;
- #398 — complete automatic Metrics/Logs/Traces semantics;
- #403 — complete agent-native BaseHarbor lifecycle over MCP/JSON;
- #408 — BaseHarbor Target, deployment registry and visible shell Target;
- #416 — full installation destroy/uninstall cleanup.

#398, #403 and #408 are complete. #397 and #416 remain open until their final release acceptance/evidence is proven by the exact-candidate Pre-Release gate.

Deferred work is explicitly assigned to later releases, including selectable recovery-unit expansion (#399), Audit/Evidence semantics (#212), managed identity (#363), semantic full-stack pre-freeze acceptance (#174) and the v0.5 contract freeze (#175).

## Architecture and engineering review

The release continues to follow `docs/DEVELOPMENT_GUIDELINES.md`:

- Target is independent from Application and Environment;
- runtime, capability and delivery remain separate provider axes;
- portable application intent remains provider-neutral;
- Manifest v1 remains the compatibility contract;
- mutation continues through shared plan/preflight/apply/verify semantics;
- CLI, JSON and MCP reuse one semantic lifecycle core;
- ownership ambiguity and foreign resources remain fail-closed;
- secrets/private keys/tokens stay out of normal output, logs, metrics labels and evidence;
- Docker executes Compose directly while Podman executes native rootless Quadlets.

## Security review

v0.4.15 establishes the provider-neutral secure service-access baseline:

- TLS or stronger authenticated transport is required for managed network services;
- dev access remains zero-friction without disabling TLS;
- test authentication is automatable through protected/generated state;
- production management/observability surfaces require authentication and least privilege;
- managed-local and external/BYOC PKI stay behind provider/runtime boundaries;
- observability transport and machine lifecycle paths reuse the same security semantics;
- full destroy never guesses ownership of foreign resources.

## Observability review

Metrics, logs and traces use the shared signal/source registry and placement/ownership semantics.

Current source classes remain:

```text
application
application-provider
platform-provider
```

Provider/runtime observability declarations carry support/realization/verification semantics. Runtime Broker and Runtime Executor participate through standards-based OpenMetrics, structured logs and OTLP traces.

Unsupported or adapter-required provider signals are reported truthfully and are not silently marked collected.

## Agent/MCP review

The machine/MCP contract exposes bounded semantic operations over the same lifecycle core as the CLI, including mutation and recovery operations.

There is no generic shell, Docker, Compose, Podman or provider-native execution primitive. Destructive operations require explicit approval and machine errors remain typed/actionable without carrying secret values.

## Target/runtime review

Target-scoped config/state separates deployment destination from portable Application/Environment identity.

Docker and Podman state are isolated. Kubernetes/OpenShift Target definitions remain contract-only and execution fails closed until those runtime providers exist.

Podman release evidence must explicitly prove native Quadlet operation with `podman compose` blocked.

## Full destroy review

`baha destroy --all [--yes]` is the explicit installation cleanup path.

It reuses existing ownership-aware application/provider/runtime cleanup, operates across all known Targets, continues best-effort across damaged BaseHarbor state and reports per-resource outcomes.

Application source repositories, foreign resources and external application-owned data remain preserved.

## Branch/rules review

Repository rulesets require pull requests, resolved review threads, linear history and squash-only merges for both `develop` and `main`. Neither branch permits deletion or non-fast-forward updates.

`develop` and `main` have historical divergence. Release promotion therefore uses one reviewed `develop -> main` PR and tree-level diff review rather than assuming branch-history equivalence.
