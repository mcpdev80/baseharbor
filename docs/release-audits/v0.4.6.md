# Pre-release documentation audit

Target release: `v0.4.6`.

Latest published stable release before this release: `v0.4.5`.

## Scope

Issue #161: S3-compatible object storage capability.

Implemented:

- `object-storage.s3/v1` as the product-neutral capability boundary;
- one or multiple logical buckets in Manifest v1;
- SeaweedFS as a lazy shared Compose reference provider;
- shared provider-registry ownership with application-owned logical buckets;
- per-bucket IAM credentials through `secure-binding/v1`;
- standard S3/AWS environment and file bindings;
- authenticated SigV4 Put/Get verification;
- status/doctor/apply/up integration;
- application destroy removes only application-owned S3 resources;
- global destroy removes the shared provider after application bindings are released;
- fail-closed backup/restore for applications containing object storage until bucket contents are included in recovery;
- capability/provider replaceability tests without changing application intent.

Not implemented and not claimed:

- dynamic external-provider loading/provider-selection UI;
- shipped Ceph RGW/AWS/cloud provider adapters;
- object-content backup/restore;
- Kubernetes/OpenShift runtime/provider realization;
- HA/replication/topology/tiering/versioning policy.

## Architecture review

- Application intent contains logical buckets only; SeaweedFS is not part of the portable contract.
- Provider-native bucket names, IAM identities, host ports, network names and storage topology remain provider/deployment state.
- The implementation reuses the shared capability lifecycle and provider registry rather than introducing a parallel object-storage framework.
- `secure-binding/v1` carries provider-neutral credential/authorization references; plaintext credentials are resolved only at the trusted runtime/binding boundary.
- Shared SeaweedFS infrastructure does not grant cross-application/bucket access.
- Provider-internal S3 use by a later provider does not create an application S3 capability unless the application independently declares it.
- Compose remains first-class and current; no Kubernetes/OpenShift behavior is prematurely implemented.

## Security review

- Each logical bucket gets distinct access/secret credentials.
- SeaweedFS IAM is explicitly enabled.
- No global S3 superuser credential is persisted for the reference provider.
- Credential-bearing files are owner-only.
- SeaweedFS IAM credential commands are delivered through runtime stdin rather than process arguments, and a negative test verifies access/secret values do not appear in command arguments or returned errors.
- CLI environment output masks S3 credentials by default.
- Provider registry and capability metadata do not contain plaintext credentials.
- Real readiness uses authenticated SigV4 Put/Get rather than container liveness.
- The first Docker acceptance attempt exposed an invalid `weed shell -command` invocation; v0.4.6 now uses SeaweedFS' stdin shell interface and keeps credentials off argv before the final acceptance rerun.

## Recovery review

- S3 object contents are not silently omitted from a supposedly complete recovery.
- Backup and restore reject managed-object-storage applications before presenting successful recovery semantics.
- Shared provider state is not removed by application lifecycle operations.
