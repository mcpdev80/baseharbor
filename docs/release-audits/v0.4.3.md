# BaseHarbor v0.4.3 release audit

## Scope

Primary roadmap issue: #158 — repository inspection and deterministic detection core.

Architecture prerequisites included since v0.4.2:

- #178 — Provider Integration Contract v1;
- #179 — provider contract hardening against open-standard best practices.

## Implemented

Repository inspection:

- shared `internal/repositoryinspect` core;
- `baha app inspect [PATH]`;
- human-readable and machine-readable JSON output;
- Detected / Suggested / Possible confidence;
- extensible Detector interface;
- Compose, Dockerfile, dependency, env-name, import, configuration, port and health-check evidence;
- logical PostgreSQL/Valkey instance evidence;
- shared detection used by guided `app init`;
- workload-only quick-init preserved without inventing PostgreSQL.

Safety:

- read-only inspection;
- environment values discarded;
- symlinks skipped;
- generated/vendor trees ignored;
- per-file size bound;
- ambiguous Compose selection fails closed.

Provider ecosystem foundation:

- versioned capability specifications;
- provider protocol v1;
- built-in integration adapter/conformance foundation;
- gRPC/Protocol Buffers external boundary;
- JSON Schema 2020-12 provider configuration;
- digest-first OCI distribution direction;
- async operation/idempotency/deadline/cancellation rules;
- secret-safe binding representation;
- standard signature/SBOM/provenance direction.

## Development-rules review

The implementation keeps repository detection in shared core code rather than the CLI, adds no AI/runtime dependency, performs no repository mutation during inspection and does not create a parallel provider architecture.

Later capability releases can register additional detectors without rewriting the inspection engine.

## Compatibility

Manifest v1 is unchanged.

Compose remains first-class and is still the complete current runtime.

Existing explicit app-init flags remain deterministic and supported.

No external provider loader, Kubernetes/OpenShift/cloud runtime, or new backend provider is introduced by this release.

## CI strategy

Use one consolidated central CI gate on the final implementation/documentation head.

Do not trigger unrelated MailFlow, backup/restore, broker-performance or other acceptance workflows merely because this release changes repository inspection.

If the central gate finds a concrete failure, fix that failure and rerun only the required gate.

## Release message

The release notes describe user-visible behavior, architectural purpose, safety, compatibility and deferred scope rather than reproducing commit history.
