# BaseHarbor v0.4.17

BaseHarbor v0.4.17 ergänzt die Standards-erste verwaltete Applikations-Identität und die vor dem Einfrieren des v0.5-Vertrags erforderliche minimale Operator-Authentifizierungs-Grenze.

Das Release hält den normalen Entwicklerpfad klein: local dev bleibt vertrauenswürdig-lokal, während Test und Prod einen authentifizierten Operator benötigen. Anwendungen verbrauchen Standard-OIDC/OAuth2-Schnittstellen statt einer BaseHarbor-Authentifizierung SDK.

## Verwaltete Anwendungsidentität

Anwendungen können anbieterneutrale Managed Identity deklarieren. BaseHarbor löst den Provider auf, erstellt oder versöhnt den Anwendungs-/Umweltidentitätsbereich, materialisiert eine Standard-OIDC-Bindung und überprüft den realisierten Zustand.

Der verwaltete Keycloak-Referenzanbieter unterstützt:

- isolierte Anwendungsbereiche/Umweltbereiche und Kunden;
- OIDC-Entdeckung und JWKS;
- Expositionsabgeleitete Umleitungs- und Ausloggen-URIs;
- Umfang und Ansprüche;
- tragbare MFA-, TOTP-, WebAuthn-, Passkey- und passwortlose Anforderungen;
- automatisches TLS/trust;
- owner-aware beobachten, versöhnen, überprüfen und zerstören.

Externe OIDC bleibt ohne Provider-seitige Bereitstellung unterstützt. Provider-native Namen und Administration APIs werden nicht portable Anwendung Absicht.

Die gemeinsame Provider-Infrastruktur impliziert keine gemeinsamen Anwendungsidentitäten.

## Operator-Authentifizierung durch Umgebung

Der Zugriff auf den Operator ist auf das effektive Ziel und die Umgebung beschränkt: dev nutzt den vertrauenswürdigen lokalen Modus; Test und Prod erfordern einen authentifizierten OIDC-Operator-Zugriff.

Für geschützte Umgebungen verwendet der CLI standardkonformen OIDC Authorization Code + PKCE und speichert nur eine kurzlebige owner-only lokale Sitzung.

Befehle:`baha login -e test `, ` baha whoami -e test `, und` baha logout -e test`.

Die erste interaktive Nutzung eines unkonfigurierten geschützten Target/Environment kann entweder die verwaltete Keycloak-Operator-Grenze oder einen externen OIDC-Provider bootstrapen. Die daraus resultierende Konfiguration ist Target/Environment-Scoped und wird von Anwendungen an dieser Grenze wiederverwendet.

Application Identity und BaseHarbor Operator Identity bleiben logisch getrennt, auch wenn ein physikalisches IdP beides bietet.

Fortgeschrittene RBAC, JIT-Erhöhung, Genehmigungen und Break-Glass-Governance bleiben außerhalb v0.4.17.

## Lebenszyklus eines Shared Providers erster Klasse

v0.4.17 macht eine ressourceneffiziente gemeinsame Platzierung zu einer Kernanbieter-Regel statt einer produktspezifischen Ausnahme.

Die gebündelten PostgreSQL- und Valkey-Anbieter unterstützen nun beide `shared` und `application` Platzierung. Ihre Voreinstellung ist umgebungsgebundene gemeinsame Platzierung:

- PostgreSQL läuft einmal pro Target/Environment-Sharing-Grenze und erstellt anwendungsisolierte Datenbanken und am wenigsten privilegierte Rollen.
- Valkey verwendet einen Lifecycle eines Target-eigenen Anbieters und erstellt isolierte Pro-Application Cache Services/Credentials, so dass normale Redis/Valkey Clients kompatibel bleiben, ohne Geschwisterschlüssel freizulegen.
- Service Binding 1.1 Projektionen bleiben anwendungsskaliert, auch wenn Provider-Infrastruktur geteilt wird.
- Die Anwendung zerstört nur die Datenbank/Rolle/Cache-Ressourcen und Bindungen der Anwendung.
- Der Shared-Provider überlebt, während Geschwister-Anwendungen es noch verwenden und wird an der Provider/Target-Eigenschaftsgrenze entfernt.
- Verpflichtet `application` Die Platzierung bleibt für Fälle, die eine gesonderte Provider-Instanz erfordern, unterstützt.

Das bedeutet, dass zehn Anwendungen, die SQL anfordern, standardmäßig nicht mehr zehn Instanzen des PostgreSQL-Anbieters beinhalten. Gemeinsame Infrastruktur spart Speicher, CPU, Image/Runtime Overhead und Startzeit, ohne die Applikationseigentums-Eigenschaft zu schwächen.

Die offizielle v0.4.17 Demo nutzt für jeden verwalteten Provider eine gemeinsame Platzierung und hält nur die Anwendungs-Workload-Anwendung scoped.

Für PostgreSQL hat der gemeinsame Lebenszyklus eine strikte Verwaltungsgrenze: eine interne `baseharbor_admin` identity wird nur von BaseHarbor für den Provider-Lebenszyklus verwendet, während jede Application + Environment + SQL-Instanz eine eigene deterministische Rolle, eigene Datenbank und geschützte Anmeldereferenz erhält. Der Administrator wird niemals an Anwendungsbindungen emittiert. Reconcile widerruft den öffentlichen Datenbank-/Schema-Zugang, überprüft die Anmeldebestätigung gegen seine eigene Datenbank und überprüft, ob Geschwisterdatenbanken verweigert werden.

Application Backup/Restore bleibt selbst auf dem Shared Provider datenbankspezifisch. Zerstört die geschützte Registrierung plus Live-Datenbankbesitz vor dem Beenden von Verbindungen und löscht nur die Datenbank/Rolle der ausgewählten Anwendung. Das Target besitzt den Shared Provider unabhängig von Anwendungskunden. Zerstört die finale Anwendung entfernt seine Datenbank/Rolle/Cache Ressourcen und Anmeldeinformationen, lässt aber den Provider Zustand/Laufzeit intakt; explizite Provider/Target Zerstörung besitzt Provider-Treepdown.

## Provider-Schnittstellen und optionale Management-UIs

Der geführte Anwendungsfluss behandelt Provider-Schnittstellen durch semantischen Zweck anstelle von Produktnamen.

Optionale Managementflächen umfassen derzeit:

- PostgreSQL-Anwendung über pgAdmin;
- Cache-Verwaltung durch Redis Commander;
- geteilte Objekt-Speicherverwaltung durch SeaweedFS Admin;
- die bestehende Shared OpenBao Web UI;
- Managed identity login/account und separate Keycloak-Verwaltungsflächen.

Ausgewählte Entwicklungs-UIs werden automatisch mit verwalteten TLS/trust und kanonischen HTTPS-URLs materialisiert.`baha.localhost`, und ein lokales HTTPS-Gateway. Interne zufällige Loopback-Ports bleiben Laufzeitimplementierungsdetails und sind nicht mehr die normale Entwickleradresse. Docker bindet das kanonische Entwicklungs-Gateway an 443; rootless Podman verwendet deterministischen Port 8443, so dass das gleiche Hostname-Modell ohne privilegierte Port-Host-Konfiguration funktioniert.

Die kanonische Namensgebung ist bewusst kurz:

```text
<app>.baha.localhost        application workload/API
pgadmin.baha.localhost      shared PostgreSQL UI
cache.baha.localhost        shared cache UI
storage.baha.localhost      shared object-storage UI
auth.baha.localhost         shared OIDC/login surface
auth-admin.baha.localhost   shared identity administration
secrets.baha.localhost      shared OpenBao UI
metrics.baha.localhost      shared Prometheus UI
```

Anwendungsskopierte Provider-Oberflächen, wenn explizit ausgewählt, verwenden `<app>-<service>.<dev-domain>`. Externe Anbieter behalten Provider-eigene URLs.

Ein geteilter Anbieter schafft eine Administrationsfläche für die Provider-Grenze und nicht eine Benutzeroberfläche pro Anwendung. Test/Prod-Verwaltungsflächen bleiben standardmäßig eingeschränkt/nicht öffentlich.

Das gleiche kanonische Routing-Modell gilt für den normalen Anwendungsendpunkt. Ein eindeutiger Entwicklungsaufwand erhält `https://<app>.<dev-domain>` automatisch und Swagger/OpenAPI wird unter dem gleichen Host an exponiert `/swagger/`. ` status `, ` doctor`und strukturierte Statusausgabe Bericht kanonische Browser-URLs anstatt zufällige Loopback-Ports.

Managed OIDC ist Placement-aware. Mit dem Standard-Shared Keycloak-Anbieter verwendet der Emittent `https://auth.<dev-domain>`; ein explizit anwendungsskopierter Identitätsanbieter nutzt einen anwendungsqualifizierten Host. Entwicklungs-Workloads erhalten den gleichen kanonischen Emittenten und die entwicklungs-gateway-Vertrauensbindung, während anbieterinterne Administrations-/Readinessendpunkte private Implementierungsdetails bleiben.

## Einheitlicher Zugang zur Entwicklung

Entwicklungsziele besitzen auch einen BaseHarbor-gemanagten Management-Login. Der Standard-Benutzername ist `developer`; BaseHarbor erzeugt ein starkes Passwort und setzt es nur durch die explizite ` baha dev credentials`Befehl.

Wenn Managed Identity vorhanden ist, versöhnt BaseHarbor die gleiche Entwickler-Identität durch Managed OIDC. Provider-Oberflächen, die eine native Authentifizierung erfordern, verwenden das gleiche Entwicklungs-Credential über providerspezifische Adapter. Service-Anmeldeinformationen wie Datenbankkennwörter, S3-Schlüssel und Laufzeitidentitäten bleiben separate am wenigsten privilegierte Anmeldeinformationen.

Die Entwicklungsdomäne kann mit `baha dev domain [DOMAIN]`. Der Assistent fragt nach der Entwicklungsdomäne und dem Management-Zugriff einmal für das Ziel, anstatt nach Hostnamen oder separaten Administrator-Anmeldeinformationen pro Fähigkeit zu fragen.

Dieses gemeinsam genutzte lokale Convenience Credential wird nie für Test/Prod verwendet. Geschützte Umgebungen verwenden weiterhin einzelne OIDC-Sitzungen, Richtlinien und eine stärkere Authentifizierung.

## Identitätsbereitschaft, Audit und Wiedereinziehung

`status `, ` doctor`, JSON und Evidenz überprüfen die realisierte Identitätsgrenze erneut, anstatt erfolgreiche Bereitstellung als permanente Wahrheit zu behandeln. Managed Keycloak Verifikation umfasst Emittenten/Entdeckung, Eigentümer Reich/Client Zustand, Umleitung/Logout Drift, Bindungszustand und erforderliche Authentifizierungspolitik. Externe OIDC Verifikation umfasst Entdeckung und die materialisierte Anwendung verbindlich.

Authentifizierte Lifecycle-Audit-Ereignisse tragen, soweit vorhanden, geheim-sichere Operator-Identitäts- und Sicherheitskontexte. Token, Passwörter, Provider-Admin-Anmeldeinformationen und Authentifizierungsgeheimnisse sind ausgeschlossen.

Recovery behandelt portable Identitätsabsichten getrennt von anbietergeführten Identitätsverzeichnisdaten. Die portable OIDC/Client-Richtlinie wird aus Anwendungs-Metadaten rekonstruiert. Provider gehaltene Benutzer, Anmeldeinformationen, MFA und Passkey-Status werden nicht ohne einen scoped Provider-Export als erstattungsfähig beansprucht; Managed Identity bleibt daher eine explizite dauerhafte Wiederherstellungsgrenze, während externe OIDC extern bleibt.

## Umweltisoliertes Anbieterregister

Provider-Registerbindungen werden von Application plus Environment scoped bereitgestellt.

Dadurch wird ein Fehler bei der Voreinfrierung des Eigentums behoben, bei dem zwei Umgebungen derselben Anwendung auf einem Target die Anbieter-Registrierungs-Bindung des jeweils anderen ersetzen könnten, obwohl ihre Laufzeitressourcen isoliert waren.

Bestehende v1 Registrierungseinträge ohne Umgebung bleiben lesbar und werden bei normaler Abstimmung in die aktuelle Bereitstellungsumgebung migriert.

## Agenten- und Read-Only-Policy-Verhalten

Read-only policy/evidence inspection erfordert keine installierte Docker- oder Podman-Orchestrierung mehr, wenn repository Compose source statisch analysiert werden kann.

Der Fallback bleibt für Sicherheitsbefunde ausfallen und wird nur verwendet, wenn die Laufzeit-Orchestrierung wirklich nicht verfügbar ist. Runtime/Provider-Fehler werden nicht stillschweigend in Erfolg umgewandelt.

## Schneller Weg zur Entwicklung des Arbeitsbaums

Lokale Entwicklung behandelt den aktuellen Projektarchiv-Arbeitsbaum als gültige Anwendungsquelle. Ein Entwickler kann Anwendungscode bearbeiten und ausführen `baha up` ohne vorher zu begehen oder zu drängen.

Wenn die Anwendung ist bereits READY und die tragbare `baseharbor.yaml` Vertrag plus geschützter Bereitstellungs-Kontroll-Zustand unverändert sind,`baha up` Die vorhandenen Workload-Engine-Fingerabdrücke erstellen und ausführen die Servicekonfiguration, bauen nur Build-Backed-Services neu auf, erstellen nur konfigurationsgeänderte Dienste, warten auf Workload HTTP/TLS-Pressance und überprüfen dann die gesamte Anwendungsbereitschaft.

Änderungen `baseharbor.yaml`, geschützter Deployment-Control-Zustand, eine nicht verfügbare/unvorbereitete Laufzeit oder eine Bedingung, die nicht sicher beweisen kann, dass nur die Arbeitsbelastung Konvergenz über den vollständigen Anwendungsabgleich Pfad fortgesetzt wird.

`baha app update` hält einen separaten Zweck: Es führt eine Git-Backed-Anwendung sicher von seinem konfigurierten Upstream aus und benötigt daher weiterhin einen sauberen, nicht divergierten Arbeitsbaum. Es sticht niemals, setzt zurück, überschreibt oder verwirft lokale Entwicklungsarbeiten.

## Endgültige V0.4.17-Release-Verhärtung

Der finale Release Pass strafft sechs Release-Blocking-Grenzen, ohne Manifest v1 zu ändern.

- **Shared Provider Lifecycle:** Shared PostgreSQL/Valkey-Infrastruktur ist Target-owned. Application zerstöre niemals den Provider, nur weil die Anwendung der Endverbraucher war.
- **OpenBao Recovery:** eine veraltete/bestehende Recovery-Ausgabedatei wird vor der neuen control-plane-Mutation abgelehnt. Bestehendes Recovery-Material wird nie überschrieben;`--recovery-file PATH` ist die ausdrückliche Sanierung.
- **Leerheitswahrheit:** RUNNING wird nicht mehr als READY behandelt. Kompose Health, HTTP/TLS-Sonden und TCP-Hörersonden sind positive Bereitschaftssignale; ein laufender Arbeiter ohne solches Signal wird RUNNING/UNVERIFIED gemeldet.
- **Developer-Gateway-Port:** Docker bevorzugt 443 und rootless Podman bevorzugt 8443, aber Kollisionen wählen einen deterministischen freien Fallback aus 18443. Der ausgewählte Port ist Zielzustand und jeder kanonischen URL/Status/Doktorpfad verwendet ihn wieder.
- **Native TLS zuerst:** OpenBao, PostgreSQL, Keycloak, SeaweedFS S3, Prometheus und OTLP verwenden native TLS. Das einzelne Ziel-Entwickler-Gateway bleibt der kanonische Browser-Router. Dedizierte Adapter bleiben nur dort, wo sie eine echte Sicherheits-/Protokoll-Grenze hinzufügen, wie z.B. Cache UI TLS oder die aktuell koordinierte Loki/Tempo-Aufnahme-Edge.
- **Dependency/security audit:** go-oidc 3.21.0 und OpenBao 2.7.0 werden angenommen. OpenBao verwendet eine dedizierte am wenigsten privilege Datenbank/Benutzer im bestehenden PostgreSQL-Steuerplane-Provider mit `verify-full`, native TLS-Reload und Hybrid-PQC-erste TLS; kein Vermächtnis ` storage.file`oder Zwischen-Raft-Kompatibilitätspfad bleibt bestehen. Go-1.26-erfordert x/crypto/x/sys-Updates und unabhängige CI/toolchain-Majors bleiben bewusst zurück. #533 verfolgt die Yaml.v3-Ersatzuntersuchung.

Die Zertifikatsdrehung folgt dem unterstützten Reload-Modell jedes nativen Anbieters: Keycloak befragt seine Zertifikatsdateien, Prometheus liest Web-TLS-Material auf Anfrage neu, SeaweedFS verwendet einen Reload-Zertifikatsanbieter, OTLP verwendet ein gebundenes TLS-Reload-Intervall und OpenBao 2.7 verwendet native `tls_auto_reload`.

## Laufzeit-Provider-Grenze

v0.4.17 legt die anbieterneutrale Runtime Provider-Grenze fest, die vor zukünftiger Kubernetes- und OpenShift-Arbeit erforderlich ist.

Der Vertrag ist wie folgt versioniert:

```text
baseharbor.runtime/v1
```

Ein Runtime Provider Deskriptor erklärt die Identität und Version des Anbieters, angenommene Standards, Workload-Source-Kompatibilität, Laufzeitrealisierung und unterstützte Runtime-Fähigkeiten. Capability-Verhandlung ist fehlgeschlagen und produktneutral.

Die Paketstruktur setzt nun diese Grenze durch:

```text
internal/runtime/contract
    provider-neutral runtime contract and model

internal/runtime/resolver
    first-party provider selection and registration

internal/providers/runtime/docker
    Docker provider implementation

internal/providers/runtime/podman
    Podman/Quadlet provider implementation
```

Portable Core importiert keine konkreten Docker- oder Podman-Providerpakete. Statische Architekturtests erzwingen die Abhängigkeitsrichtung und verhindern, dass providerspezifische Implementierungsdateien zum neutralen Laufzeitpaket zurückkehren.

Compose bleibt ein erstklassiger Workload-Source-Standard, ist aber nicht mehr die Identität eines Runtime Providers.

Docker realisiert die aktuelle Compose-Workload-Quelle über Docker Compose.

Podman realisiert die gleiche tragbare Laufzeit Semantik durch native Quadlet-Einheiten und rootless `systemd --user`. Es gibt keine ` podman compose`Rückfall.

Die Runtime Provider-Konformitätsabdeckung übt beide Referenzanbieter durch denselben versionierten semantischen Vertrag aus.

## Rootless Podman Parität und Freigabe Verhärtung

Die abschließende v0.4.17-Validierung schließt die verbleibenden Docker/Podman Paritätslücken, die vom nativen Quadlet-Akzeptierungspfad entdeckt wurden:

- verwaltete Quadlet-Netzwerke behalten native `.network` Ressourcenreferenzen und -nutzung `NetworkAlias=` anstatt Legacy-Alias-Optionen in den Netzwerkwert einzubinden;
- externe Workload/Provider-Netzwerke verwenden dasselbe native Quadlet-Alias-Modell, das rootless Podman DNS für Runtime-Executor, Metriken-Scraping und kanonischen Entwicklungsrouting wiederhergestellt;
- BaseHarbor bewahrt gemeinsame Podman-Netzwerke, während aktive Geschwister Verbraucher immer noch nutzen sie;
- rootless Candidate-Image Build, Verifikation und Quadlet-Ausführung teilen sich den gleichen Podman-Speicherkontext;
- Podman-Service-State-Beobachtung liest die veröffentlichten Ports vom laufenden Container zurück, so dass HTTP/TLS-Workload-Evaluation die gleichen positiven Hinweise auf Docker hat;
- runtime-executor ready diagnostics entlarvt die ausfallende nachgelagerte Abhängigkeit, und Podman ready budgets machen den langsameren nativen Quadlet/systemd-Startpfad aus, ohne die ausfallenden Checks zu schwächen.

Die gezielte Podman geführte Akzeptanz überprüft diesen Weg Ende vor dem vollen Pre-Release-Gate zu beenden.

## Laufzeitneutrale Protokolle

Docker und Podman konvergieren nun hinter einer laufzeitneutralen Log-Source-Grenze.

BaseHarbor normalisiert Workload-, Application-Provider- und Plattform-Provider-Log-Quellen auf dieselbe semantische Identität:

```text
application
environment
source class
provider
service
```

Docker heftet Container stdout/stderr derzeit über seinen syslog Logging Treiber. Podman verwendet journald durch die native Quadlet/systemd Realisierung. Diese Transportdetails bleiben hinter dem Laufzeitadapter.

Die Podman-Verifikation überprüft nun das aktuell laufende Projekt/Dienst statt die Protokollkonfiguration bedingungslos zu akzeptieren. Ungültiges Eigentum, Provider-Identität, Signalart oder Laufzeitziel scheitert vor der Loki-Verifikation.

Es wird kein proprietäres Protokoll zur Protokollierung eingeführt. Bestehende Laufzeitprotokollierung, RFC5424 syslog, systemd journal semantics, Alloy und Loki bleiben die Implementierungsstandards.

## Standards-erste Laufzeitarchitektur

Die Überprüfung des Runtime Provider dokumentiert die Adoptions-/Delegationsgrenze für:

- OCI-Bildspezifikation;
- OCI-Distributionsspezifikation;
- OCI-Laufzeitspezifikation;
- Komposen-Spezifikation;
- Kubernetes API;
- CRI;
- CNI,
- CSI;
- Kubernetes Gateway API;
- Leistungsbindungs-Spezifikation;
- Crossplane-Zusammensetzung/Anbieter-Muster.

BaseHarbor verwendet oder delegiert diese Standards, wo sie bereits die erforderliche Grenze definieren. BaseHarbor-spezifische Semantik beschränkt sich auf portable Absichten, Provider-Verhandlungen, Eigentumsverhältnisse, Richtlinien, Lebenszyklus und semantische Verifikation, wenn die überprüften Standards nicht das erforderliche anwendungsorientierte Verhalten definieren.

Siehe `docs/architecture/runtime-standards-audit.md`, ` docs/architecture/runtime-log-source-contract.md`und ADR 0007.

## Vorsorglich aufgeschoben

v0.4.17 nicht implementiert:

- Kubernetes Runtime Provider Ausführung;
- Ausführung des OpenShift Runtime Providers;
- einen proprietären Ersatz für OCI, CRI, CNI, CSI, Gateway API oder Compose;
- fortgeschrittene Betreiber-RBAC-, JIT-Höhen-, Genehmigungs- oder Bruchglas-Governance;
- Die vollständige Workload-Source-Normalisierung des Repositorys wird weiterhin in #519 verfolgt; v0.4.20 deckt Compose, natives Quadlet und rohes Kubernetes YAML ab, während Helm und Kustomize absichtlich auf spätere Quelladapter verschoben werden;
- ein außerbaumliches Runtime-Prozess-/Distributionsprotokoll, bevor eine echte externe Anbieteranforderung den notwendigen Transport nachweist.

```bash
baha app init
```

## Vereinbarkeit

- Manifest v1 bleibt der tragbare Anwendungsvertrag.
- OIDC/OAuth2 und Service Binding bleiben die anwendungsorientierte Integrationsgrenze.
- Keycloak, pgAdmin, Redis Commander und SeaweedFS bleiben Referenz-/Providerimplementierungsdetails.
- Runtime Provider Identität ist explizit `docker` or ` podman`; Kompose bleibt Workload-Source-Kompatibilität und nicht Provider-Identität.
- Docker Compose und Podman/Quadlet behalten äquivalente logische Anwendungs- und Provider-Eigenschaftssemantik.
- Neue implizite lokale Target-State-Standards für Docker. Podman benötigt natives Quadlet plus eine nutzbare benutzersystemte Sitzung und schlägt fehl, wenn diese Umgebung nicht verfügbar ist.
- Bestehende Anbieter-Registrierung v1 Zustand bleibt lesbar; Umgebungsbereich ist additive Bereitstellung Metadaten.

Die Referenz-Demo-Workload selbst ist nur HTTPS. Sein Compose-Dienst erklärt `io.baseharbor.workload.protocol: https`; das Entwicklungs-Gateway verwendet beim Routing zu ihm den projizierten Workload CA und den Compose-Dienstnamen als SNI. Plaintext-Fallback ist absichtlich nicht Teil des Referenzpfades.


## Freigabevalidierung

Die Freigabe-Grenzvalidierung wird in zwei Schichten vorbereitet:

- Validierung der lokalen/befestigenden Face-Quellquelle:`gofmt -l .`, ` go vet ./...`, fokussierte Anbieter/Laufzeit-Tests und ` go test ./...`;
- das obligatorische GitHub Pre-Release Gate gegen den exakten Release Candidate und unveränderlich `baseharbor-demo` Revision.

Die finale GitHub Release Evidenz wird den exakten BaseHarbor Kandidaten SHA, das Pinned Demo SHA und den erfolgreichen Docker/Podman Pre-Release Run aufzeichnen.
