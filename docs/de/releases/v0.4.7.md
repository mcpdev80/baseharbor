# BaseHarbor v0.4.7

BaseHarbor v0.4.7 fügt eine **providerneutrale OpenTelemetry Protocol (OTLP) Transport Foundation** hinzu, bevor die einzelnen Metriken, Protokolle und Spurenplattformen für die nächsten Releases geplant sind.

## Warum das so wichtig ist

Anwendungen sollten in der Lage sein, Telemetrie auszusenden, ohne je nachdem, welche Beobachtungsprodukte eine Umgebung verwendet.

v0.4.7 macht diese Grenze explizit:

```text
application instrumentation
        |
        | telemetry.otlp/v1
        v
OTLP transport/binding
        |
        +-- shared OpenTelemetry Collector today
        +-- external OTLP destination
        +-- other conforming providers later
```

OpenTelemy Collector ist das Ökosystem- und Instrumentierungsmodell. OTLP ist das tragbare Protokoll. OpenTelemy Collector ist ein Anbieterimplementierung, nicht Teil der Anwendungsidentität.

## Hinzugefügt

- Verändert `telemetry.otlp/v1` Spezifikation für die Fähigkeit.
- Manifest v1 OTLP-Signalmeldungen für Spuren, Metriken und Protokolle.
- OTLP HTTP/protobuf exportieren als erster v1-Transport.
- OpenTelemetry Collector 0.161.0 als fauler gemeinsamer Compose-Referenzanbieter.
- Externe Unterstützung von OTLP-Destinationszielen, ohne dass BaseHarbor den Lebenszyklus übernimmt.
- Standard-Workload-Bindungen für OpenTelemetrie:
  - `OTEL_EXPORTER_OTLP_ENDPOINT`
  - `OTEL_EXPORTER_OTLP_PROTOCOL`
  - `OTEL_SERVICE_NAME`
  - `OTEL_RESOURCE_ATTRIBUTES`
- Gemeinsame Anwendung/Umwelt/Arbeitsbelastung/Ressourcen/Anbieteridentität.
- Secret-safe Anbieter Lifecycle Instrumentierung Haken für Preflight / apply/bind/verify.
- Reale OTLP-Exportprüfung mit einer vom ausgewählten Endpunkt akzeptierten Protobuf-Trace.
- Fähigkeit, manifest, verbindlich, negativ und real Collector Akzeptanz Abdeckung.

## Verändert

OTLP folgt nun dem gleichen gemeinsamen BaseHarbor-Lebenszyklus wie andere von Anbietern unterstützte Funktionen:

```text
resolve
  -> preflight
  -> provision
  -> bind
  -> verify
```

Der Managed Collector wird nur erstellt, wenn eine Anwendung explizit den OTLP-Transport anfordert. Mehrere Anwendungen dürfen diesen gemeinsam genutzten Provider wiederverwenden, während ihre logischen telemetrischen Ressourcen weiterhin im Besitz der Anwendung bleiben.

Repository-Workloads mit dem verwalteten Collector an einem dedizierten BaseHarbor Telemetrie-Netzwerk anhängen. Externe OTLP-Destinationen erstellen oder besitzen keinen BaseHarbor Collector.

## Anwendungsvertrag

Eine instrumentierte Anwendung kann die Signale erklären, die sie exportiert, ohne ein Beobachtungsprodukt zu nennen:

```yaml
workload:
  compose: compose.yaml
  services:
    - api
    - worker

telemetry:
  otlp:
    signals:
      - traces
      - metrics
```

BaseHarbor injiziert die aufgelöste Endpunkt- und Standard-Ressourcenidentität von OpenTelemetry in die ausgewählten Workloads.

## Externe OTLP-Destinationen

Eine Bereitstellung kann einen bestehenden Endpunkt ohne Änderung der portablen Anwendungsabsicht binden:

```bash
export BASEHARBOR_OTLP_ENDPOINT=https://otel.example.com
```

Optionale Berechtigungs-Header verwenden `BASEHARBOR_OTLP_HEADERS`. Dies sind Bereitstellungs-/Laufzeiteingaben und werden niemals in das portable Anwendungsmanifest geschrieben.

## Überprüfung

Leichtfertigkeit bedeutet nicht, dass ein Sammler-Container existiert.

BaseHarbor sendet eine echte OTLP HTTP/Protokollspur an den aufgelösten Endpunkt und benötigt den Endpunkt, um ihn zu akzeptieren. Dies beweist den Transport-/Bindungspfad, auf dem später Prometheus, Loki und Tempo-Integrationen aufbauen werden.

## Sicherheit

- OTLP-Beglaubigungs-/Kopfmaterial ist nicht Teil von `baseharbor.yaml`.
- Provider-Registrierung und portable Fähigkeiten Metadaten enthalten keine Klartext-Telemetrie-Anmeldeinformationen.
- Externe Anbieter-Lebenszyklusbesitz bleibt extern.
- Ungültige oder fehlende OTLP-Bindungssemantiken scheitern vor der Anbietermutation.
- Globale Zerstörung entfernt nur den Shared Collector im Besitz von BaseHarbor.

## Kein impliziter Beobachtungsstapel

Antragstellung `telemetry.otlp/v1` bestimmt nicht ****:

- Prometheus;
- Loki,
- Tempo oder Jaeger;
- Grafana,
- Dashboards oder Alarmierung.

Diese bleiben separate Bedenken hinsichtlich der Plattform/Anbieter und werden durch spätere Freigaben absichtlich behandelt.

## Kompatibilität & Upgrade-Notizen

- Die offensichtlichste Version bleibt erhalten `1`.
- Bestehende Manifeste erfordern keine Migration.
- OTLP ist additiv und opt-in.
- Bestehende PostgreSQL, Valkey, OpenBao, sichere Bindungen, verwaltete Belichtung und S3-Verhalten bleiben kompatibel.
- Compose bleibt die komplette aktuelle Laufzeitimplementierung.
- Anwendungen verwenden weiterhin Standard-Ökosystemprotokolle und -Konfiguration; es wird kein BaseHarbor SDK benötigt.
