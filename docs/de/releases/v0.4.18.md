# BaseHarbor v0.4.18

BaseHarbor v0.4.18 vervollständigt die Autoren- und Erweiterungsstiftung, die vor dem Einfrieren des v0.5-öffentlichen Auftrags existieren muss.

Die Veröffentlichung fügt eine erstklassige Greenfield-Entwicklerpfad, wiederverwendbare Entwicklung Stack Profile, vier ökosystem-native Referenz Entwicklungsadapter, Multi-Repository-Workspace-Auflösung, optionale Backstage-Katalog-Emission, stärkere Lebenszyklus-Treardown, Fähigkeit-Subset-Annahme und Runtime-aware-Host-Ressource-Vorflug.

Manifest v1 bleibt der tragbare Anwendungsvertrag. Bestehende Brownfield-Repositories verwenden weiterhin die normale `baha app init -> baha up -> READY` Pfad.

## Erstellung von Greenfield-Anwendungen

`baha app new` ist jetzt der erstklassige Greenfield-Eingangspunkt.

Es erstellt ein normales ökosystem-natives Projekt aus Anwendungsfähigkeitsabsicht und validiert die generierte Implementierung gegen den resultierenden BaseHarbor-Vertrag.

Referenzstapel in dieser Version:

- Go;
- Der nächste.js;
- Python;
- Quarks.

Beispiel:

```bash
baha app new catalog-api --stack go --http --sql --cache --telemetry
cd catalog-api
baha up
```

Generierte Anwendungen verwenden normale Ökosystembibliotheken und Konfiguration. BaseHarbor führt kein Anwendungsframework oder proprietäres SDK ein.

Der gleiche Creation Flow hat einen deterministischen JSON-Ausgang und einen semantischen MCP-Betrieb. Human CLI, strukturierte Ausgabe und MCP verwenden das gleiche Entwicklungs-Domain-Ergebnismodell.

## Wiederverwendbare Stack-Profile

Entwicklungspräferenzen können als wiederverwendbare Stack Profile erfasst werden, ohne zu portablen Bereitstellungsanforderungen zu werden.

```bash
baha stack list
baha stack show team-api
baha stack create
```

Die Führung `baha stack create` Assistent und deterministische Flags verwenden das gleiche Profilmodell. Profile können mehrere stabile Entwicklungskomponenten enthalten und bestehende Profile mit expliziter Konfliktbearbeitung komponieren.

Anforderungen an die Anwendung, Entwicklungspräferenzen, Kompetenzanbieter, Platzierung, Laufzeit und Lieferung bleiben separate Anliegen.

## Entwicklungsverlängerungsvertrag v1

v0.4.18 fügt versionierte maschinenlesbare Verträge für:

- gemeinsame Erweiterungsdeskriptoren;
- Anbieterdeskriptoren;
- Stack-Profile;
- Entwicklungspläne.

Entwicklungsadapter implementieren deterministische Detect-, Plan-, Bootstrap- und Validate-Semantik. Die Referenzadapter beweisen das Round-Trip-Verhalten vom Vertrag bis zur Implementierung und zurück zur BaseHarbor-Inspektion/Beweis.

Anbieter- und Entwicklungserweiterungen teilen gegebenenfalls Verpackungs-/Entdeckungs-/Trust-Mechanik, teilen aber keine Lebenszyklus-Semantik nur zur Code-Wiederverwendung.

## Multi-Repository-Anwendungen und Workspace-Assistent

Eine logische Anwendung kann nun umfassen:

- ein Repository,
- eine Monorepo mit mehreren Komponenten;
- mehrere bereits vorhandene lokale Repositorys/Worktrees;
- eine Mischung aus lokalen Quellen und OCI-Bildern.

Das portable Quellmodell ist versionsgesteuert unter `.baseharbor/sources.yaml`. Entwickler-lokale Checkout-Pfade bleiben XDG-lokale Workspace-Metadaten und geben Sie niemals portable Application Intent ein.

```bash
baha app workspace
baha app workspace show
baha app workspace resolve
```

Die No-Subcommand-Form ist der geführte Assistent. Deterministisch `init`, ` map `, ` show `und` resolve`Befehle stehen weiterhin für die Automatisierung zur Verfügung.

Applikations- und Komponentenidentität sind unabhängig vom aktuellen Arbeitsverzeichnis und von entwickler-lokalen Checkout-Pfaden. Fehlende Worktrees scheitern vor der Mutation mit durchführbarer Diagnostik.

Automatischer Klon/Fetch/Checkout/sync bleibt auf den späteren Managed-Workspace-Lebenszyklus verschoben; v0.4.18 löst nur bereits vorhandene lokale Repositories/Worktrees auf.

## Externe Entwicklerportale nach Vertrag

Backstage wird als erster Referenzportalverbraucher unterstützt, ohne eine BaseHarbor-Abhängigkeit zu werden.

`baha app new ` kann optional eine minimale anwendungseigene emittieren`catalog-info.yaml`:

```bash
baha app new catalog-api \
  --stack go \
  --emit-backstage \
  --backstage-owner platform-team
```

Portal-Eigentum ist explizit und wird nie aus BaseHarbor-Eigentum abgeleitet. Backstage-Lebenszyklus-Metadaten werden nicht aus BaseHarbor dev/test/prod-Umgebung abgeleitet.

BaseHarbor bettet kein Backstage SDK, Katalog-Client, Template-Interpreter oder repository-publishing Credential-Modell ein. Portal-Integrationen verbrauchen stabile BaseHarbor JSON/Evidence-Kontrakte und normale Repository-Metadaten.

## Kapazitäts-Subset-Annahme

Die Referenzdemo überprüft nun eine deklarative Fähigkeitsmatrix, anstatt anzunehmen, dass eine Full-Stack-Demo jeden kleineren Vertrag beweist.

Die Matrix umfasst:

- nur Arbeitsaufwand;
- SQL und optionale SQL Management Benutzeroberfläche;
- Zwischenspeicher;
- Speicherung von Objekten;
- Geheimnisse;
- Identität;
- Metriken;
- Protokolle;
- Telemetrie,
- gemischte SQL/Cache- und Entwickler-Core-Profile;
- die vollständige Referenzkombination;
- Ungültige Cross-Capability-Kombinationen, die vor der Mutation ausfallen müssen.

Kontrakt-nur-Matrix-Fälle bleiben billig und deterministisch. Runtime-Akzeptierung beginnt nur die Anbieter, die durch das ausgewählte reduzierte Profil benötigt werden; es baut nicht den gesamten Provider-Stack für jeden Fall.

## Lebenszyklus und Zerreißverhärtung

Application stop/destroy verwendet nun beobachtetes Laufzeiteigentum, anstatt den erfolgreichen Anwendungszustand zu rekonstruieren.

Dies bedeutet, dass teilweise konvergente Bereitstellungen noch sicher gereinigt werden können, wenn ein Anbieter Bindung oder später Lebenszyklusschritt nie abgeschlossen.

Owned Workload-Container und -Netzwerke werden entfernt, bevor der Bereitstellungszustand gelöscht wird, während Repository- / Application-eigene Volumes gemäß Eigentumsregeln erhalten bleiben.

Zu den zusätzlichen V0.4.18-Lebenszyklushärten gehören:

- Dauerhafter Workload-Port-Fallback, der konsequent angewendet wird;
- das Starten der Projektarchiv-Workloads bei Terminal-Laufzeitfehlern schnell fehlgeschlagen ist;
- kanonische Entwicklungs-Gateway/Identity-URLs bewahren den effektiven, persistenten Gateway-Port;
- Management UI Bereitschaft folgt Browser-Umleitung Ketten anstatt eine erste Umleitung als Ausfall zu behandeln.

## Host-Ressource-Vorflug

Vor der lokalen Docker- oder Podman-Mutation evaluiert BaseHarbor nun Runtime-Host-Speicher-Headroom mit Linux:

- `MemAvailable`;
- Swap-Zustand;
- Speicher PSI, soweit verfügbar;
- eine Delta-aware-Schätzung der ausgewählten Anwendungs-/Kontrollebenen-Fähigkeiten.

Das Ergebnis wird als sicher, eng oder unsicher eingestuft.

Unsichere Kopffreiheit versagt vor Laufzeitmutation. Enge Kopffreiheit erfordert eine explizite interaktive Genehmigung oder die explizite `--skip-memory-preflight` Überbrückung.

Diese Beweise sind bewusst Laufzeit-Scoped:

- Docker und Podman verwenden lokale Runtime-Host-Evidenz;
- Kubernetes/OpenShift verwenden nicht** die CLI-Maschine `/proc` Werte.

Zukünftige Kubernetes/OpenShift-Anbieter müssen clusterspezifische Ressourcennachweise für Kapazität/anwendbare Ressourcen, Anfragen/Grenzen, Quoten und Terminbeschränkungen implementieren.

## Vorab-Release-Architektur

Die Release-Validierung hält jedes kleine Demo-Gate individuell für die Diagnose lauffähig, aber der Release-weite Laufzeit-Proof verwendet nun langlebige Umgebungen.

Die komplette Laufzeitsemantik wird auf beiden Referenzlaufzeiten in vier parallel verlaufenden Bahnen ausgeübt:

- `Docker · Core Journey`;
- `Docker · Operations`;
- `Podman · Core Journey`;
- `Podman · Operations`.

Jede Spur baut/lädt den exakten Kandidaten einmal und führt eine Sequenz von bereits gezielten Gates auf die gleiche Umgebung, wo sicher. Dies entfernt wiederholte Provider/Container-Setup, ohne Docker/Podman semantische Abdeckung zu reduzieren.

Gezielte Workflow-Runs werden nach Zweck benannt, zum Beispiel `Docker · Capability Matrix`, statt interner Branchen-/Testterminologie.

## Abhängigkeit und Toolchain-Entscheidung

BaseHarbor v0.4.18 bleibt absichtlich auf:

```text
go 1.25.0
golang.org/x/crypto v0.55.0
```

Die verfügbaren `x/crypto` v0.56/v0.57 line erfordert Go 1.26. Das Erheben des Projekts Go floor ist eher eine Entscheidung über Plattform/Toolchain als eine Routine-Abhängigkeits-Refresh, so dass das Update explizit auf eine spätere Veröffentlichung mit der entsprechenden CI/Support-Dokumentationsänderung verschoben wird.

Die YAML v3-Abhängigkeit hat sich auf die gepflegte `go.yaml.in/yaml/v3` Modul.

## Vereinbarkeit

- Das Manifest v1 bleibt unterstützt.
- Bestehende Brownfield-Repositories bleiben kompatibel.
- Entwicklungs-Metadaten und lokale Workspace-Mappings sind additive Authoring-Time-Status.
- Lokale Dateisystempfade werden nicht zur portablen Anwendungsidentität.
- Generierte Projekte nutzen ökosystem-native Abhängigkeiten und Standard-Service-Bindungen.
- Docker und Podman bleiben die beiden implementierten lokalen Runtime Provider.
- Kubernetes/OpenShift Zieldefinitionen bleiben Future-Runtime-Kontrakte; Local-Host-Speichernachweise werden explizit nicht für Cluster-Kapazitätsentscheidungen wiederverwendet.

## Vorsorglich aufgeschoben

v0.4.18 fügt nicht hinzu:

- automatische Git-Klon/Fetch/Pull/Checkout/Worktree-Synchronisation;
- Kubernetes Runtime Provider Ausführung;
- Ausführung des OpenShift Runtime Providers;
- eine Backstage-Laufzeit/API-Abhängigkeit;
- ein BaseHarbor-Anwendungsrahmen;
- ein implizites Upgrade der Werkzeugkette Go 1.26.

Diese Grenzen bleiben nach dem Einfrieren des v0.5-Vertrags und nicht nach versteckten Anforderungen im v0.4.18-Bewerbungsvertrag additive Arbeit.
