# BasisHarbor v0.4.20

Status: Laufende Arbeiten

Auslöseschirm: #519

## Höhepunkte

v0.4.20 macht die Repository-Adoption quellneutral und vervollständigt den sicheren Git-Workflow für Entwickler-Workspaces vor dem v0.5 Contract Freeze.

### Annahme von mehr bestehenden Repositorys

BaseHarbor kann Anwendungen prüfen und übernehmen, die mit:

- Docker Compose;
- Podman-Quadlet für das Projektarchiv;
- Rohes Kubernetes YAML.

Das tragbare `baseharbor.yaml` beschreibt logische Workload-Komponenten, anstatt Compose-spezifische Dienst- oder Dateiidentität zu tragen.

Dies bedeutet, dass dieselbe Anwendungsabsicht nicht mehr an die Syntax des Repositorys gebunden ist.

Wenn ein Repository mehrere plausible Workload-Quellen enthält, ahnt BaseHarbor nicht. Geführte Adoption fragt, welche Quelle maßgeblich ist und zeichnet diese Repository-Auswahl bei Bedarf getrennt vom portablen Anwendungsvertrag auf.

### Kubernetes Repositories können vor Kubernetes Laufzeitunterstützung verstanden werden

v0.4.20 kann rohe Kubernetes-Manifestierungen inspizieren und übernehmen, ohne einen Live-Cluster zu benötigen.

Diese Version fügt den Kubernetes Runtime Provider hinzu. Ein Repository kann daher auch dann verstanden und übernommen werden, wenn der aktuell ausgewählte Runtime Provider diese Workload-Quelle noch nicht ausführen kann. BaseHarbor berichtet, dass diese Einschränkung explizit statt stillschweigend die Anwendung übersetzen oder ändern würde.

### Sicherere Multi-Repository-Workspace-Updates

Der bestehende Multi-Repository-Workspace gewinnt:

```text
baha app workspace status
baha app workspace update --check
baha app workspace update
```

BaseHarbor verwendet das installierte Git CLI und führt nur sichere Fast-Forward-Updates durch, wenn der Arbeitsbaum sauber ist, ein Upstream existiert und die Historie noch nicht divergiert ist.

Es verwahrt nicht automatisch Änderungen, reset Worktrees, rebase, Zusammenführung divergierenden Zweige, Konflikten oder Switch-Zweigen.

### Klarere Überprüfung des Lagers

`baha app inspect` jetzt berichtet Workload-Source-Ambiguität und Adoption Ergebnisse konsequent über Compose, Quadlet und Kubernetes Repositories.

Der normale Entwicklerstrom bleibt gering:

```bash
baha app inspect .
baha app init
baha up
```

## Nicht enthalten in v0.4.20

Für spätere Veröffentlichungen bleibt geplant:

- Unterstützung der Workload-Quelle durch Helm;
- Unterstützung der Workload-Source-Unterstützung von Kustomize;
- Kubernetes Runtime Provider;
- OpenShift Runtime Provider;
- Argo CD / Flux oder generische GitOps Lieferung.
