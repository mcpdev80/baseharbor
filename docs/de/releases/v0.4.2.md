# BaseHarbor v0.4.2

BaseHarbor v0.4.2 trennt die logische Ressource einer Anwendung von der Instanz des Providers, die sie bedient.

Mit dieser Unterscheidung lässt BaseHarbor Infrastruktur wiederverwenden, in der Sharing sinnvoll ist, dedizierte Infrastruktur isoliert halten, wo es darauf ankommt, und bestehende externe Dienste übernehmen, ohne zu behaupten, BaseHarbor besitze sie.

Der Entwickler-Workflow bleibt gleich: **no Manifest v1 migration is required**.

## Hinzugefügt

BaseHarbor versteht nun drei Anbieter-Scopes:

- **shared** — ein von BaseHarbor verwalteter Anbieter kann mehrere Anwendungen bedienen;
- **application-scoped** — ein Anbieter gehört zu einer Anwendung und kann diese Eigentumsgrenze nicht überschreiten;
- **extern** — ein bestehender/BYO-Anbieter kann eine logische Ressource erfüllen, während sein Lebenszyklus außerhalb von BaseHarbor bleibt.

Das Provider-Register ist im geschützten BaseHarbor-Status erhalten und registriert logische Ressourcen-zu-Provider-Instanz-Bindungen sowie explizite Lebenszyklus-Eigentümer.

## Verändert

Der aktuelle Stack zeigt nun natürlich an die Registry:

```text
OpenBao              -> shared
PostgreSQL instances -> application-scoped
Valkey instances     -> application-scoped
```

Eine zweite Anwendung kann denselben kompatiblen Shared-Provider wiederverwenden, ohne dass BaseHarbor versehentlich ein Duplikat bereitstellt.

Bestehende v0.4.1-Anwendungen werden nach dem nächsten Erfolg automatisch übernommen `baha app apply` or ` baha app up`.

Das Zerstören einer Anwendung entfernt seine Bindungen und BaseHarbor-eigene anwendungsskopierte Provider-Aufzeichnungen, während gemeinsame und externe Provider-Instanzen bestehen bleiben.

## Sicherheit

Provider Registry-Status wird atomar mit owner-only Berechtigungen geschrieben und Lesen/Ändern/Schreiben-Updates werden serialisiert, so dass gleichzeitige BaseHarbor-Operationen einander nicht leise überschreiben können.

Application-scoped Provider scheitern bei Cross-Application-Bindungsversuchen. Beschädigter, doppelter oder mehrdeutiger Registry-Status wird abgelehnt.

Externe Anbietereinträge verwenden ausschließlich nicht geheime Referenzen; Anmeldeinformationen und geheime Verbindungsdaten verbleiben außerhalb der Registry. BaseHarbor behandelt einen externen Anbieter niemals als Lebenszyklus.

## Veraltet

Keine Öffentlichkeit `baha` Befehl oder Feld Manifest v1 wird in v0.4.2 deprecated.

## Gelöscht

Nichts aus dem unterstützten v0.4.1 CLI, Manifest v1 oder Compose Workflow wird entfernt.

## Kompatibilität & Upgrade-Notizen

No `baseharbor.yaml` Migration ist erforderlich.

Anbieterplatzierung bleibt Deployment/Operator-Zustand und wird absichtlich nicht zu portablen Anwendungsabsichten hinzugefügt.

v0.4.2 fügt noch keine Syntax für die öffentliche Providerauswahl hinzu, ersetzt bestehende Compose-Provisioning oder implementiert Kubernetes/OpenShift/Cloud-Provider. Diese bleiben separate Meilensteine, so dass dieses Release fokussiert und kompatibel bleibt.

Der praktische Nutzen ist architektonisch, aber konkret: Spätere gemeinsame Beobachtbarkeit, dedizierte Datenbanken, kundengeführte Services und Cloud-Provider können eingeführt werden, ohne zu ändern, was die Anwendung benötigt.

Für eine detaillierte technische Geschichte siehe `CHANGELOG.md`.
