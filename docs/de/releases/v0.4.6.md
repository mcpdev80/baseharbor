# BaseHarbor v0.4,6

BaseHarbor v0.4.6 fügt **providerneutralen S3-kompatiblen Objektspeicher** als nächste reale Fähigkeit hinter dem Shared Provider Vertrag hinzu.

## Warum das so wichtig ist

Anwendungen benötigen oft Objektspeicher lange bevor sie eine volle Beobachtbarkeit oder AI/RAG-Stapel benötigen. BaseHarbor lässt nun eine Anwendung logische S3-Eimer anfordern, ohne den Anwendungsauftrag an SeaweedFS, Ceph, AWS oder ein anderes Speicherprodukt zu koppeln.

Die gleiche Trennung, die für Datenbanken, Geheimnisse und verwaltete Exposition verwendet wird, gilt nun für Objektspeicherung:

```text
application intent
  object-storage.s3/v1
        |
        v
provider boundary
        |
        +-- SeaweedFS today
        +-- Ceph RGW / AWS S3 / other conforming providers later
```

## Hinzugefügt

- Verändert `object-storage.s3/v1` Spezifikation für die Fähigkeit.
- Manifest v1 Objekt-Speicher-Deklarationen mit einem oder mehreren logischen Eimern.
- `--s3 ` und wiederholbar`--s3-bucket NAME` applikations-init/create paths.
- SeaweedFS 4.47 als erster fauler gemeinsamer Compose-Referenzanbieter.
- Bucket-scoped SeaweedFS IAM Identitäten und Anmeldeinformationen.
- Anbieterneutral `secure-binding/v1` Metadaten für S3-Zugriff.
- Standard S3/AWS-kompatible Host- und Workload-Bindungen.
- Authentifizierte AWS SigV4 Einsatz/Erhalten Sie die Bereitschaft in Anwendung, nach oben, Status und Arzt.
- Anbieter-Register-Eigentum für die Shared SeaweedFS-Instanz und anwendungseigene logische Eimer.
- Real Docker/Compose Akzeptanzabdeckung für den S3-Lebenszyklus.

## Verändert

- Der Lebenszyklus des Object-Storage-Anbieters nutzt nun den gemeinsamen Plan/Preflight/Provision/bind/verify-Pfad.
- SeaweedFS administrative IAM-Befehle werden über stdin geliefert, so dass pro-bucket Anmeldeinformationen nie in Prozessargumenten oder Laufzeit-Fehlermeldungen erscheinen.
- Application Backup/Restore fehlschlägt geschlossen, während S3 Objekt Inhalt außerhalb der Recovery-Einheit sind.

## Anwendungsvertrag

Ein Repository kann Objektspeicher anfordern, ohne ein Produkt zu benennen:

```yaml
services:
  object_storage:
    buckets:
      attachments: {}
      exports: {}
```

or:

```bash
baha app init mailflow \
  --s3-bucket attachments \
  --s3-bucket exports
```

Provider-native Bucket-Namen, IAM-Identitäten, Ports, Speichertopologie und SeaweedFS-Konfiguration bleiben geschützter Provider/Deployment-Zustand.

## Anbringungsseitige Bindungen

Für einen eindeutig bevorzugten Eimer veröffentlicht BaseHarbor normale S3/AWS-Konfiguration wie:

```text
S3_ENDPOINT
S3_BUCKET
S3_REGION
AWS_ENDPOINT_URL
AWS_REGION
AWS_ACCESS_KEY_ID
AWS_SECRET_ACCESS_KEY
```

Benannte Eimer zusätzlich erhalten `S3_<NAME>_*` Variablen und geschützte Dateibindungen.

Repository Workloads verwenden den internen Provider-Endpoint über ein BaseHarbor-eigenes Objekt-Speicher-Integrationsnetzwerk. Hostseitige Prozesse verwenden einen Loopback-only-Endpoint. Anwendungen benötigen kein BaseHarbor SDK oder Laufzeit-Login.

## Sicherheit

- Jeder logische Eimer erhält separate Anmeldeinformationen, die zu diesem Eimer scoped.
- SeaweedFS IAM ist explizit aktiviert.
- BaseHarbor besteht kein globales S3-Superuser-Zertifikat für den Referenzanbieter.
- S3 Credential-Dateien sind owner-only.
- `baha app env` Masken S3-Zugriffsschlüssel und geheime Schlüsselwerte standardmäßig.
- Plaintext-Anmeldeinformationen geben keine portablen Fähigkeiten Metadaten, Provider-Register-Aufzeichnungen oder normale Diagnosen ein.
- Ein gemeinsam genutzter Provider-Prozess impliziert keine gemeinsame Bucket-Zulassung.

## Bereitschaft und Lebenszyklus

Der Erfolg basiert nicht auf einem laufenden SeaweedFS-Container. BaseHarbor unterzeichnet eine echte S3-Anfrage und überprüft einen Put/Get-Flow mit den Bucket-Scope-Anmeldeinformationen der Anwendung.

`baha app down ` bewahrt die gemeinsam genutzten Provider- und Bucket-Daten.`baha app destroy --yes ` entfernt nur die verwalteten Eimer/Identitäten und Zustand der Anwendung. Der gemeinsam genutzte Anbieter bleibt für andere Anwendungen verfügbar und wird nur von global entfernt`baha destroy --yes` nachdem die Bewerbungsbindungen weg sind.

## Rückforderungsgrenze

Objektinhalte sind noch nicht Teil der verschlüsselten BaseHarbor-Anwendungswiederherstellungseinheit. v0.4.6 schlägt daher für `baha app backup` und `baha app restore` wenn verwalteter Objektspeicher deklariert wird. BaseHarbor wird keine unvollständige S3-Wiederherstellung als erfolgreiches Backup/Restore präsentieren.

## Kompatibilität & Upgrade-Notizen


- Die offensichtlichste Version bleibt erhalten `1`.
- Bestehende Manifeste erfordern keine Migration.
- PostgreSQL, Valkey, OpenBao, sichere Bindungen, verwaltete Belichtung und bestehende Compose-Workflows bleiben kompatibel.
- Objektspeicher ist additiv und opt-in; es wird keine SeaweedFS-Laufzeit erstellt, es sei denn, eine Anwendung verlangt ausdrücklich S3.
- SeaweedFS ist eine Referenzimplementierung, keine Anwendungsidentität.

## Ersatz des Anbieters

Der Funktionslebenszyklus, Provider Integration Contract v1, Provider Registry und Konformitätstests beweisen, dass die gleiche logische S3-Anfrage von einem anderen konformen Treiber ohne Änderung der Anwendungsabsicht erfüllt werden kann.

Der aktuelle öffentliche v0.4.6 Workflow wählt die integrierte SeaweedFS Referenzimplementierung für den verwalteten Objektspeicher Compose aus. Allgemeines dynamisches Laden/Auswahl von externen Anbietern bleibt separate Plattformarbeit; im Vorgriff darauf werden dem Bewerbungsvertrag keine produktspezifischen Felder hinzugefügt.
