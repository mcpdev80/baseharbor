# BaseHarbor v0.4.15

BaseHarbor v0.4.15 ist ein wichtiger Schritt auf dem Weg zum v0.5 Contract Freeze. Sie erweitert BaseHarbor von einer starken lokalen Entwicklerplattform zu einem vollständigeren, agenten-nativen und laufzeitneutraleren Anwendungslebenszyklus und hält dabei tragbare Anwendungsabsichten unabhängig von konkreten Infrastrukturprodukten.

## Vollständiger MCP-Lebenszyklus

Die MCP/JSON-Schnittstelle ist nicht mehr auf die Inspektion beschränkt.

Agenten können nun den unterstützten BaseHarbor-Lebenszyklus über den gleichen semantischen Kern wie der CLI nutzen, einschließlich:

`inspect -> plan -> apply -> status -> doctor -> observe -> update -> repair -> backup -> restore -> destroy`

Politik, Eigentum, Aussöhnung, Verifikation und Genehmigungsauflagen bleiben unabhängig davon, ob BaseHarbor von einem Menschen oder einem Agenten betrieben wird, bestehen.

Es wird keine generische Shell, Docker, Compose oder Podman Ausführungsschnittstelle freigelegt.

## Native Podman mit Quadlets

Docker verwendet weiterhin Docker Compose.

Podman verwendet jetzt native rootless Quadlets verwaltet durch `systemd --user` statt sich darauf zu verlassen `podman-compose`.

Die gleiche BaseHarbor-Anwendung und Provider-Semantik sind über beide Laufzeiten erhalten, während Podman nun seinem nativen Laufzeitmodell genauer folgt.

## Sicherer Service-Zugang

Managed Service-Zugriff folgt nun einem gängigen TLS- und Authentifizierungsmodell über Umgebungen hinweg.

BaseHarbor unterstützt verwaltete lokale PKI sowie externe/BYOC PKI und hält dabei Vertrauen, Anmeldeinformationen und Transportdetails aus portablen Anwendungsabsichten heraus.

Anwendungen verbrauchen weiterhin Standard-URLs, Umgebungsvariablen und Dateibindungen, während BaseHarbor das Deployment-seitige Sicherheitsmodell verwaltet.

## Vollständige Metriken, Protokolle und Spuren

Das Beobachtbarkeitsmodell wurde in folgenden Bereichen ergänzt:

- Metriken;
- Protokolle;
- Spuren.

Anwendungsworkloads, Managed Provider, Runtime Broker und Runtime Executor nehmen nun am gleichen Provider-neutralen Beobachtungsmodell teil.

Prometheus, Loki, Tempo und OpenTelemetrie bleiben Referenzimplementierungen hinter tragbaren Verträgen, anstatt Teil der Anwendungs-API zu werden.

## CLI-Ziele und installationsweiter Lebenszyklus

v0.4.15 führt erstklassige Ziele als neue Bereitstellungsdimension ein.

Ein Einsatz wird nun ermittelt durch:

`target + application + environment`

Dies ermöglicht es, die gleiche Anwendung und Umgebung unabhängig über verschiedene Docker- oder Podman-Ziele zu existieren, während BaseHarbor Laufzeitzustand, Provider, Netzwerke, Volumina und Besitzstaat isoliert hält.

Die Ziele sind durchgängig über die CLI-, Shell-Integrations-, JSON- und MCP-Schnittstellen verfügbar und legen die Laufzeitgrenze fest, die für die zukünftige Kubernetes- und OpenShift-Unterstützung benötigt wird.

Das Target-Modell ermöglicht auch eine installationsweite Reinigung über alle bekannten Targets:

```bash
baha destroy --all
```

Cleanup bleibt eigentumssicher: Repositories aus der Applikationsquelle und ausländische oder externe anwendungseigene Ressourcen bleiben erhalten.

## Intelligentere Init- und Repository-Adoption

BaseHarbor ist besser im Verständnis vorhandener Repositories, bevor er den Entwickler bittet, sie manuell zu beschreiben.

Repository-Inspektion kann Anwendungs-Workloads von auswechselbarer Infrastruktur unterscheiden, unterstützte Fähigkeiten erkennen und die Adoption leiten, ohne stillschweigende Intention zu erfinden, wenn ein Repository mehrdeutig ist.

Geführte init umfasst jetzt eine klarere Auswahl von Fähigkeiten, verbesserte geheime Handhabung, deterministische Workload-Auswahl und umsetzbarere Ausfälle.

Auch das Anwendungsmodell wurde während dieser Arbeit immer anbieterneutraler: generische Service-Familien wie z.B.`sql ` und`cache` werden anstelle von produktspezifischen Anwendungsabsichten verwendet, während normbasierte Servicebindungen die Integrationsoberfläche für Workloads bleiben.

## Vereinbarkeit

Das Manifest v1 bleibt der Kompatibilitätsvertrag.

Docker bleibt Compose-basiert. Unterstützte Podman-Ausführung verwendet nun native Quadlets.

Kubernetes und OpenShift Targets passen in die neue Target-Architektur, aber die Laufzeitausführung für sie wird absichtlich auf eine spätere Veröffentlichung verschoben.

Die vollständige technische Änderungsliste, Kompatibilitätsdetails und Sicherheitshinweise finden Sie im v0.4.15 Changelog.
