# v0.4.20 Release Runbook

Dieses Runbook ist eine interne Release Engineering-Dokumentation. Es ist absichtlich nicht Teil der benutzernahen Release Notes.

## Ziel

Machen Sie den letzten v0.4.20 Pfad deterministisch, nachdem v0.4.19 freigegeben wurde.

Der Freigabebefehl lautet:

```text
v0.4.19 released
  -> synchronize release/v0.4.20 with final develop
  -> focused readiness
  -> affected runtime gates
  -> guided Docker + Podman proof
  -> one unchanged-candidate pre-release
  -> release
```

## Vor der Freisetzung von v0.4.19

Erlaubt:

- Umsetzung am `release/v0.4.20`;
- Einheit/Vet/Konformität/Real-Welt-Validierung;
- vorübergehende Validierungsbranchen;
- GitHub-gehostete Docker-Validierung;
- Selbstgehostete Laufzeitvalidierung nur dann, wenn Ersatzläufer vorhanden sind;
- Demoarbeit an `baseharbor-demo:release/v0.4.20`.

Nicht:

- Verschmelzen v0.4.20 in `develop`;
- die aktiven v0.4.19 Pre-Release-Workflows für v0.4.20 ändern;
- alle Docker- oder Podman-Runner verbrauchen, während die v0.4.19-Validierung aktiv ist;
- Führen Sie die letzte v0.4.20 vor der Synchronisation mit der letzten v0.4.19.

## Synchronisierung nach v0.4.19

1. Nehmen Sie das letzte v0.4.19/develop SHA auf.
2. Synchronisieren `release/v0.4.20` mit diesem genauen Zustand.
3. Lösen Sie einmal Konflikte.
4. Wiederholung:
   - `bash scripts/v0.4.20-readiness.sh core`;
   - `bash scripts/v0.4.20-readiness.sh realworld`.
5. Wenn die Synchronisation Runtime/Provider/Lifecycle Code berührt, führen Sie zuerst nur die betroffenen atomaren Runtime Gates aus.
6. Beginnen Sie keine vollständige Vorabfreigabe, bis jedes betroffene Atomtor auf demselben Kandidaten SHA grün ist.

## Laufzeitreihenfolge

Verwenden Sie unabhängige Docker und Podman Läufer parallel.

Empfohlene Bestellung:

### Stufe 1 — quellenneutrale Entwicklungsreise

- geführt
- Lebenszyklus
- Politik
- Konnektivität
- Vollzerstörung

Dies sind die ersten Runtime Gates, weil sie direkt Repository-Adoption und die Entwickler-Reise durch v0.4.20 geändert.

### Stufe 2 — Regressionen um bestehende Fähigkeiten

- Datenkapazitäten
- Beobachtungsfähigkeit
- Identität
- Sicherheit
- Aussöhnung
- Ausfall
- Backup-Wiederherstellung

Führen Sie ein erfolgreiches unabhängiges Gate nicht erneut aus, es sei denn, seine Eingaben haben sich geändert.

### Stufe 3 — Integration von Anbietern

- Kaninchenmq-Laufzeit
- mongodb-Laufzeit
- Dauerhafter Schlüsselwert
- Steuerungs-Plane-Recovery
- loki-Laufzeit
- Tempo-Laufzeit

### Stufe 4 — Endgültige Nachweise

- Docker geführte Reise;
- Podman geführte Reise;
- eine vollständige Vorabfreigabe auf einen unveränderten Kandidaten;
- Wiederverwendung von unveränderlichen Beweisen.

## Laufende Politik

- Docker- und Podman-Validierung sollten parallel laufen, wenn Läufer frei sind.
- Halten Sie mindestens einen Läufer für eine aktive frühere Veröffentlichung zur Verfügung.
- Starten Sie nicht die gesamte Plattform, wenn ein atomares Gate ein kleineres Ressourcenprofil deklariert.
- Erfolgreiche Atomtore sind Beweise; wiederholen Sie sie nicht nur, weil ein anderes Tor versagte.
- Ein ausgefallenes volles Tor wird repariert und mit dem kleinsten betroffenen Tor wiederbewiesen, bevor das volle Tor wiederbelebt wird.

## Kandidatenregel

Jeder Beweissatz muss den genauen BaseHarbor SHA und den genauen Baseharbor-Demo SHA nennen.

Jede Codeänderung entwertet nur Beweise, deren Eingaben oder Verhalten betroffen sind.
Für v0.4.22 bindet die endgültige Zulassung einen Kandidaten an alle 55 geforderten Nachweise.
Frühere Nachweise können nur durch die authentifizierte Eingabeäquivalenz beitragen
Empfang beschrieben in[evidence resume](v0.4.22-evidence-resume.md); ihre ursprüngliche
Anwärter, Demo Pin, Run und Versuch bleiben unverändert.

## Veröffentlichungs-Dokument-Regel

Benutzerbezogene Release Notes enthalten nur benutzer-sichtbare Änderungen.

Implementierungsdetails, Testarchitektur, Kandidat SHAs, Corpus-Counts und CI-Mechanik gehören zu:

- ÄNDERUNGSLOGIEN;
- Erteilung/PR-Beweise;
- Architektur/Validierungsdokumentation;
- Dieses Runbook.
