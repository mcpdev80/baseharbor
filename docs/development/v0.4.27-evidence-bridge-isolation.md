# v0.4.27 evidence bridge — isolated adoption contract

Status: **prototype only**, not a qualification or release approval.

## Existing authoritative owners (do not replace)

- `scripts/pre-release-resume.py`: canonical release requirements, archive parsing, input-equivalence and manifest validation.
- `scripts/pr-verified-atomic-evidence.py`: authenticated PR run/job/artifact origin and selected-gate validation.
- `scripts/pr-gate-plan.py` and `.github/workflows/ci.yml`: conservative changed-area selection, trusted planning and final checks.

The v0.4.27 archive resolver and staging publisher in `scripts/r27_archive_*.py` are **not** substitutes for these owners. They only establish an immutable local byte envelope after the existing authenticated verifier has accepted the original run and inputs.

## Proposed boundary

1. Trusted v0.4.27 workflow obtains the exact candidate SHA, workflow run ID and attempt from GitHub Actions, **not** from a PR-supplied JSON document.
2. Existing canonical evidence owner verifies required jobs, original artifact IDs/digests, original integrated source SHA, consumer pins and selected-gate coverage. Missing, skipped, failed or unverifiable requirements are **not** promoted to PASS.
3. Only accepted and redacted output is serialized into a bounded v0.4.27 archive. The new staging publisher checks manifest/payload integrity; its return value is **integrity-only**, never a qualification decision.
4. Independent verification reads the archive against a separately authenticated expected manifest digest. It must also bind the immutable originating run/attempt, candidate SHA and required checks using the existing owner. A manifest claiming success is insufficient.
5. A protected, authorized Planning publisher attaches an immutable evidence pointer and verifier result to the matching task/PR. Publication is idempotent, rejects conflicting IDs and records partial failures for retry. Planning content cannot instruct the verifier or select trusted workflow code.

## Activation and isolation

- v0.4.26 workflow, planner, producer, verifier and pins remain unchanged.
- No v0.4.27 auto-trigger or credentials in this prototype. A future dedicated workflow must be explicitly reviewed and activated only after the release dependency is ready.
- Existing v0.4.26 PR final-check policy still applies to this draft PR. Its current failure is not waived or treated as success.
- Do not merge, tag, qualify, deploy or publish planning evidence on the strength of these prototype tests.

## Authenticated workflow-run preflight

`scripts/r27_workflow_run_contract.py:verify_authenticated_workflow_run` composes
the event/API identity check with the existing restricted `github_getter(token)`
transport. It returns only validated run ID, candidate SHA and workflow path;
event or API IDs that are booleans, floats or strings are rejected. Transport,
JSON and identity errors fail closed. No raw API response reaches an issuer.

This is a preparatory API, not an activated workflow or signing entrypoint.
The caller must run independently protected executor code and provide a scoped
credential. Next integration must bind the verified identity to exact attempt/job
authorization and the protected policy-file issuer, with policy pins and signing
credentials sourced outside candidate control. No candidate code may execute in
the credential-bearing process. Protected workflow provenance, key custody and
end-to-end Required Check qualification remain open.

## Acceptance matrix (must be executable before promotion)

- Valid original run/attempt with exact source and consumer pins: accepted only through the existing trusted verifier.
- Wrong run, attempt, head SHA, integration SHA, expired artifact, duplicate origin, absent job or missing gate: fail closed.
- Forged manifest PASS, untrusted PR-supplied digest, changed requirement catalog or stale planning task: fail closed.
- Archive path traversal, symlink, non-regular file, oversize, duplicate check, checksum mismatch and identity collision: fail closed.
- Identical retry: no duplicate Planning publication; conflicting retry: blocked.
- Planning write denied/network failure: original evidence retained, no false completion, bounded retry with explicit status.
- No required native gates are skipped merely because the new archive passes integrity checks.

## Prototype limitations

The current publisher uses path-based directory checks and does **not** defend against a concurrent hostile writer swapping parent directories (TOCTOU). The current resolver likewise assumes an isolated trusted filesystem root. Neither is suitable for hostile shared storage without dirfd/openat-style directory confinement and an independent authenticated provenance source. No test result in this PR claims otherwise.

## Agreed target architecture (2026-10-23; supersedes the archive prototype as the intended design)

- One compact authenticated PASS receipt per qualified exact commit; no permanent CI ZIPs, logs, per-gate blobs or dependence on retained GitHub runs. Target kilobytes, not megabytes.
- The trusted issuer must authenticate the original jobs, requirements, candidate and integrated source **before** issuing the receipt. A plain JSON PASS or an untrusted self-signature never qualifies.
- Bind each receipt to the exact commit, policy digest, required-check coverage and trusted issuer; verify its signature using a separately controlled trust anchor. Run IDs, if present, are informational only.
- After merge, check that the merged tree and its dependencies are covered; reuse eligible PR receipts and execute only uncovered or invalidated integration gates. PR PASS alone never implies merged-tree PASS.
- At release, calculate the diff and dependency impact since the prior release, reconcile PR/integration receipts against the final release candidate and execute only missing required gates **plus** a mandatory end-to-end release smoke test on the exact artifacts to be shipped.
- Issue one compact release receipt only when all requirements and the final smoke test pass. A change to the final candidate invalidates affected coverage.
- Missing trust anchor, stale policy, incomplete coverage, unverifiable receipt or ambiguous merge lineage fails closed. Offline verification must not query GitHub Actions.
- The existing archive publisher/resolver are exploratory and do not implement this receipt contract. Do not activate or merge them as release qualification.
- Preserve v0.4.26 trusted workflows and Codeman's ongoing work; introduce the receipt issuer, verification and planner integration as separately reviewed v0.4.27 changes with executable regressions.

## Mandatory zero-touch automation and developer diagnostics

- PR push: trusted planner automatically computes affected gates; trusted CI executes the minimal complete set; issuer automatically writes one compact authenticated commit receipt only after complete PASS.
- Merge to develop: automatically correlate merged tree and eligible receipts, compute integration impact, execute missing gates, and issue a receipt for the integrated commit. No manual run ID entry, evidence gathering or replay of already valid checks.
- Release candidate: automatically collect eligible commit/integration receipts, calculate changed areas and transitive dependencies, run missing required gates and a mandatory smoke test against the exact publishable artifacts; publish a compact release receipt only on full PASS.
- Developer-facing diagnostics must include a stable machine-readable error code, concise German/English-capable summary, affected commit/gate, concrete reason, automatically scheduled recovery (if any), and a specific developer action only when truly necessary. Never show generic 'validation failed' as the sole explanation.
- Distinguish WAITING (automatic work in progress), ACTION_REQUIRED (code or configuration correction), BLOCKED (missing trust/policy), and PASS. Skipped, unavailable, expired or unverifiable evidence never silently becomes PASS.
- Automatic retries are bounded and idempotent; no duplicate receipts, runaway CI loops or repeated green gates. If automation cannot recover, surface the precise blocker rather than requesting routine approval.
- This section is an acceptance contract, not a claim that the prototype already automates the flow. Do not alter the v0.4.26 pipeline as part of this isolated preparation.
