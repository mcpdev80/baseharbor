# v0.4.20 Release Runbook

This runbook is internal release engineering documentation. It is intentionally not part of the user-facing release notes.

## Goal

Make the final v0.4.20 path deterministic after v0.4.19 is released.

The release order is:

```text
v0.4.19 released
  -> synchronize release/v0.4.20 with final develop
  -> focused readiness
  -> affected runtime gates
  -> guided Docker + Podman proof
  -> one unchanged-candidate pre-release
  -> release
```

## Before v0.4.19 release

Allowed:

- implementation on `release/v0.4.20`;
- unit/vet/conformance/real-world validation;
- temporary validation branches;
- GitHub-hosted Docker validation;
- self-hosted runtime validation only when spare runners exist;
- demo work on `baseharbor-demo:release/v0.4.20`.

Do not:

- merge v0.4.20 into `develop`;
- modify the active v0.4.19 pre-release workflows for v0.4.20;
- consume all Docker or Podman runners while v0.4.19 validation is active;
- run final v0.4.20 pre-release before synchronization with final v0.4.19.

## Synchronization after v0.4.19

1. Record the final v0.4.19/develop SHA.
2. Synchronize `release/v0.4.20` with that exact state.
3. Resolve conflicts once.
4. Re-run:
   - `bash scripts/v0.4.20-readiness.sh core`;
   - `bash scripts/v0.4.20-readiness.sh realworld`.
5. If synchronization touches runtime/provider/lifecycle code, run only the affected atomic runtime gates first.
6. Do not start a full pre-release until every affected atomic gate is green on the same candidate SHA.

## Runtime order

Use independent Docker and Podman runners in parallel.

Recommended order:

### Stage 1 — source-neutral developer journey

- guided
- lifecycle
- policy
- connectivity
- full-destroy

These are the first runtime gates because they directly exercise repository adoption and the developer journey changed by v0.4.20.

### Stage 2 — regressions around existing capabilities

- data-capabilities
- observability
- identity
- security
- reconciliation
- failure
- backup-restore

Do not re-run a successful independent gate unless its inputs changed.

### Stage 3 — provider integrations

- rabbitmq-runtime
- mongodb-runtime
- durable-key-value
- control-plane-recovery
- loki-runtime
- tempo-runtime

### Stage 4 — final evidence

- Docker guided journey;
- Podman guided journey;
- one full pre-release on an unchanged candidate;
- release reuses that immutable evidence.

## Runner policy

- Docker and Podman validation should run in parallel when runners are free.
- Keep at least one runner available for an active earlier release.
- Do not start the entire platform when an atomic gate declares a smaller resource profile.
- Successful atomic gates are evidence; do not repeat them merely because another gate failed.
- A failed full gate is repaired and re-proven with the smallest affected gate before the full gate is retried.

## Candidate rule

Every evidence set must name the exact BaseHarbor SHA and exact baseharbor-demo SHA.

Any code change invalidates only evidence whose inputs or behavior are affected. The final pre-release, however, must use one unchanged candidate across all of its required gates.

## Release-document rule

User-facing release notes contain user-visible changes only.

Implementation details, test architecture, candidate SHAs, corpus counts and CI mechanics belong in:

- CHANGELOG;
- issue/PR evidence;
- architecture/validation documentation;
- this runbook.
