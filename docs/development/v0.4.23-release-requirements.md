# v0.4.23 release requirements

Status: implementation in progress; no complete runtime approval exists.

`scripts/release-requirements.json` is the versioned inventory of required proofs.
The released v0.4.22 baseline remains required. v0.4.23 adds public contracts,
configuration policy, browser/terminal, remote Docker, remote Podman live
Console integration, and Core-only bootstrap on rootless Docker and Podman. Counts are derived from the release's selected inventory;
a successful baseline alone cannot approve the new release.

Each requirement names its evidence schema, executing jobs and consumer roles.
The inventory is read from the exact candidate, not from a mutable default
branch. Missing or duplicated definitions fail closed. Coverage and approval
receipts bind the requirement digest as well as the candidate and demo pin.

## Evidence reuse

Reuse hashes product code, tests, schemas, authentication/policy, build inputs,
the requirement inventory and evidence tooling. Workflow job execution inputs
include static/reusable call arguments, runner declarations, timeouts,
environments, build steps and evidence-generation steps. Only scheduling edges
and matrix fan-out are omitted from this comparison. A runner or verifier change
therefore requires new evidence even when a job keeps its display name.

Original successful child-job manifests remain immutable and retain their
source SHA, demo pin, run, attempt and archive digest. A newer compatible failed,
cancelled or artifact-less attempt blocks fallback to older success. Missing
proofs remain pending. Source-only checks never substitute for runtime proof.

## Publication handoff

For v0.4.23, `scripts/release-handoff.py` permits only the final changelog,
roadmap, release index, release notes and release audit prose to change after
validation. Workflow, runtime-image, verifier, build, policy/auth, contract,
consumer pin and test changes are execution changes and require revalidation.
The release publisher derives its required count from the tag's inventory and
re-authenticates the approved evidence origins.

## Integration completion boundary

The three Core-only static integration jobs are wired to the candidate-owned
pending requirement list. They check public schema/type drift, shared organization
configuration/policy resolution, and HTTP/browser-origin/terminal contracts with
race detection. Their original JSON test logs and requirement-bound manifests
are retained for 90 days. Empty or skipped test selections cannot produce a
successful manifest. Their qualification scope is **Core source contracts**;
they do not establish an actual browser/issuer/PTY or remote lifecycle journey.

The remote Docker/Podman and live Console jobs are scheduled; their complete
production qualification remains pending. Planning refuses to omit required
integration origins. Private consumer verification now
re-authenticates exact-source push runs, their latest attempts, qualification jobs,
artifact archives and production-scope receipts. Missing private configuration,
partial/test-authority receipts and newer failed attempts prevent approval.
This is a guard against premature approval, not evidence that these requirements
have passed. Console/Connector exact source and build pins belong in their
private integration evidence; public receipts must use commitments that do not
reveal private source identifiers. No v0.4.23 tag is authorized by this document.

The verifier reads an owner-only regular file selected by
`BASEHARBOR_PRIVATE_EVIDENCE_FILE` and authenticates GitHub with
`BASEHARBOR_PRIVATE_EVIDENCE_TOKEN`. The file uses
`baseharbor.private-evidence-pins/v1` with a `gates` map, each required private role
binding its trusted repository, exact `commit` and
`.github/workflows/release-integration.yml`. Public integration manifests contain
only `consumer_commitments`: SHA-256 commitments of those canonical JSON bindings.
Private source IDs and archives are never copied into public coverage.

Each private job is named `Integration · <full gate id>` and retains a root
`manifest.json` in `private-integration-<gate with slashes replaced by hyphens>-<run>-<attempt>`.
The `baseharbor.private-integration-evidence/v1` receipt binds repository,
consumer/Core/demo commits, role, gate, workflow run/attempt, job and build digest.
It requires successful execution and owned cleanup, explicit production authority,
release eligibility and every gate-specific qualification in the verifier.
The new producer workflow, private authentication provisioning and complete native
journeys still need qualification; the existing primitive/read/terminal receipts
cannot satisfy this release boundary.

## Core installation qualification

The #810 addition requires two explicit runtime proofs:
`integration/docker/core-bootstrap` and `integration/podman/core-bootstrap`.
They verify Core-only setup without a repository, both machine-role defaults,
mandatory SQL/Secrets/Identity readiness, stable installation identity on retry,
protected credential output and owned cleanup. Their runtime host must actually
report rootless mode; source-only tests or skipped acceptance tests cannot approve
these requirements. Original JSON test logs are retained for 90 days. The runtime tests retain actual per-service
and simultaneous Core memory samples, native image IDs/limits, host memory/swap/PSI,
a sampled startup/convergence peak and an idle window stable within 10% for at least
30 seconds. Native runtime memory/cache accounting and observation timestamps are
explicit; these are topology-specific observations, not a universal minimum.

This addition does not qualify resource calibration, private consumers or remote
application lifecycle. Those proofs remain independently required before release.

## Authenticated consumer gate scheduling

The public pre-release workflow schedules all three consumer-dependent gates:
`integration/docker/remote-target`, `integration/podman/remote-target` and
`integration/static/live-console`. These lightweight verification jobs do not
start additional runtime runners. They independently authenticate the trusted
private producer's exact source, newest push run and attempt, qualification job,
archive digest, complete production journey and successful owned cleanup.
A source-only or partially qualified private receipt fails the public gate.
The final approval independently re-authenticates the same private origins.

The workflow reads two separately provisioned Actions secrets:
`BASEHARBOR_PRIVATE_EVIDENCE_PINS` contains the reviewed bounded JSON source-pin
configuration with schema `baseharbor.private-evidence-pins/v1`;
`BASEHARBOR_PRIVATE_EVIDENCE_TOKEN` grants read access to the required private
source/run/job/artifact origins. Public repository access keeps its normal
workflow token. The pin configuration may alternatively be supplied as an
owner-only `BASEHARBOR_PRIVATE_EVIDENCE_FILE` outside Actions. Simultaneously
supplying both configuration sources is rejected.

Private identifiers and archives remain private. A successful public receipt
contains only opaque source commitments and public Core/demo/run bindings. A
failed rerun removes stale successful receipts and retains a safe failure code.
Wiring these jobs does not qualify unfinished consumer functionality or confirm
that the Actions secrets have been provisioned. Full private producer journeys
and final source pins remain release prerequisites.

A dedicated Source Preflight branch,
`runtime-validation/source-preflight/v0.4.23-private-evidence-access`, additionally
checks the protected configuration's complete gate/role bindings and authenticates
exact private source commits plus Actions metadata. It retains only safe access
booleans and explicitly sets `release_approved: false`. This access check neither
downloads private payloads into public evidence nor qualifies an incomplete
consumer journey. Ordinary source branches do not require private credentials.
