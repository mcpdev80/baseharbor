# BaseHarbor v0.4.17

BaseHarbor v0.4.17 adds standards-first managed application identity and the minimum operator-authentication boundary required before the v0.5 contract freeze.

The release keeps the normal developer path small: local dev remains trusted-local, while test and prod require an authenticated operator. Applications consume standard OIDC/OAuth2 interfaces rather than a BaseHarbor authentication SDK.

## Managed application identity

Applications can declare provider-neutral managed identity. BaseHarbor resolves the provider, creates or reconciles the application/environment identity scope, materializes a standard OIDC binding and verifies the realized state.

The managed Keycloak reference provider supports:

- isolated application/environment realms and clients;
- OIDC discovery and JWKS;
- exposure-derived redirect and logout URIs;
- scopes and claims;
- portable MFA, TOTP, WebAuthn, passkey and passwordless requirements;
- automatic TLS/trust;
- ownership-aware observe, reconcile, verify and destroy.

External OIDC remains supported without requiring provider-side provisioning. Provider-native names and administration APIs do not become portable application intent.

Shared provider infrastructure does not imply shared application identities.

## Operator authentication by environment

Operator access is scoped to the effective Target and Environment: dev uses trusted-local mode; test and prod require authenticated OIDC operator access.

For protected environments the CLI uses standards-compliant OIDC Authorization Code + PKCE and stores only a short-lived owner-only local session.

Commands: `baha login -e test`, `baha whoami -e test`, and `baha logout -e test`.

The first interactive use of an unconfigured protected Target/Environment can bootstrap either the managed Keycloak operator boundary or an external OIDC provider. The resulting configuration is Target/Environment-scoped and is reused by applications on that boundary.

Application identity and BaseHarbor operator identity remain logically separate even when one physical IdP provides both.

Advanced RBAC, JIT elevation, approvals and break-glass governance remain outside v0.4.17.

## First-class shared provider lifecycle

v0.4.17 makes resource-efficient shared placement a core provider rule instead of a product-specific exception.

The bundled PostgreSQL and Valkey providers now support both `shared` and `application` placement. Their default is environment-bounded shared placement:

- PostgreSQL runs once per Target/environment sharing boundary and creates application-isolated databases and least-privilege roles.
- Valkey uses one Target-owned provider lifecycle and creates isolated per-application cache services/credentials so normal Redis/Valkey clients remain compatible without exposing sibling keys.
- Service Binding 1.1 projections remain application-scoped even when provider infrastructure is shared.
- Application destroy removes only the application's database/role/cache resources and bindings.
- The shared provider survives while sibling applications still use it and is removed at the provider/Target ownership boundary.
- Dedicated `application` placement remains supported for cases that require a separate provider instance.

This means ten applications requesting SQL no longer imply ten PostgreSQL provider instances by default. Shared infrastructure saves memory, CPU, image/runtime overhead and startup time without weakening application ownership.

The official v0.4.17 demo uses shared placement for every managed provider and keeps only the application workload application-scoped.

For PostgreSQL, shared lifecycle has a strict administration boundary: one internal `baseharbor_admin` identity is used only by BaseHarbor for provider lifecycle, while every Application + Environment + SQL instance receives its own deterministic role, own database and protected credential reference. The administrator is never emitted to application bindings. Reconcile revokes public database/schema access, verifies the application credential against its own database and checks sibling databases are denied.

Application backup/restore remains database-specific even on the shared provider. Destroy verifies protected registration plus live database ownership before terminating connections and dropping only the selected application's database/role. The provider remains running while any sibling application is registered; only the final consumer may remove the shared runtime and volume.

## Provider interfaces and optional management UIs

The guided application flow treats provider interfaces by semantic purpose instead of product name.

Optional management surfaces currently include:

- PostgreSQL administration through pgAdmin;
- cache administration through Redis Commander;
- shared object-storage administration through SeaweedFS Admin;
- the existing shared OpenBao web UI;
- managed identity login/account and separate Keycloak administration surfaces.

Selected development UIs are materialized automatically with managed TLS/trust and canonical HTTPS URLs. The effective Target owns one development domain, defaulting to `baha.localhost`, and one local HTTPS gateway. Internal random loopback ports remain runtime implementation detail and are no longer the normal developer-facing address.

Canonical naming is deliberately short:

```text
<app>.baha.localhost        application workload/API
pgadmin.baha.localhost      shared PostgreSQL UI
cache.baha.localhost        shared cache UI
storage.baha.localhost      shared object-storage UI
auth.baha.localhost         shared OIDC/login surface
auth-admin.baha.localhost   shared identity administration
secrets.baha.localhost      shared OpenBao UI
metrics.baha.localhost      shared Prometheus UI
```

Application-scoped provider surfaces, when explicitly selected, use `<app>-<service>.<dev-domain>`. External providers retain provider-owned URLs.

A shared provider creates one administration surface for the provider boundary rather than one UI per application. Test/prod administrative surfaces remain restricted/non-public by default.

The same canonical routing model applies to the normal application endpoint. An unambiguous development workload receives `https://<app>.<dev-domain>` automatically and Swagger/OpenAPI is exposed beneath the same host at `/swagger/`. `status`, `doctor` and structured status output report canonical browser URLs rather than random loopback ports.

Managed OIDC is placement-aware. With the default shared Keycloak provider, the public issuer uses `https://auth.<dev-domain>`; an explicitly application-scoped identity provider uses an application-qualified host. Workload containers keep the appropriate internal provider endpoint and trust binding while the public issuer remains canonical.

## Unified development access

Development Targets also own one BaseHarbor-managed management login. The default username is `developer`; BaseHarbor generates a strong password and exposes it only through the explicit `baha dev credentials` command.

When managed Identity is present, BaseHarbor reconciles the same developer identity through managed OIDC. Provider surfaces that require native authentication reuse the same development credential through provider-specific adapters. Service credentials such as database passwords, S3 keys and runtime identities remain separate least-privilege credentials.

The development domain can be inspected or changed with `baha dev domain [DOMAIN]`. The wizard asks for the development domain and management access once for the Target instead of asking for hostnames or separate administrator credentials per capability.

This shared local convenience credential is never used for test/prod. Protected environments continue to use individual operator OIDC sessions, policy and stronger authentication.

## Identity readiness, audit and recovery

`status`, `doctor`, JSON and evidence re-check the realized identity boundary instead of treating successful provisioning as permanent truth. Managed Keycloak verification covers issuer/discovery, owned realm/client state, redirect/logout drift, binding state and required authentication policy. External OIDC verification covers discovery and the materialized application binding.

Authenticated lifecycle audit events carry secret-safe operator identity and assurance context where available. Tokens, passwords, provider-admin credentials and authentication secrets are excluded.

Recovery treats portable identity intent separately from provider-held identity-directory data. The portable OIDC/client policy is reconstructed from application metadata. Provider-held users, credentials, MFA and passkey state are not claimed as recoverable without a scoped provider export; managed identity therefore remains an explicit durable recovery boundary, while external OIDC remains external.

## Environment-isolated provider registry

Provider registry bindings are deployment-scoped by Application plus Environment.

This fixes a pre-freeze ownership defect where two environments of the same application on one Target could otherwise replace each other's provider-registry binding even though their runtime resources were isolated.

Existing v1 registry entries without an environment remain readable and are migrated to the current deployment environment on normal reconciliation.

## Agent and read-only policy behavior

Read-only policy/evidence inspection no longer requires an installed Docker or Podman orchestration binary when repository Compose source can be analyzed statically.

The fallback remains fail-closed for security findings and is used only when runtime orchestration is genuinely unavailable. Runtime/provider errors are not silently converted into success.

## Development working-tree fast path

Local development treats the current repository working tree as valid application source. A developer can edit application code and run `baha up` without committing or pushing first.

When the application is already READY and the portable `baseharbor.yaml` contract plus protected deployment-control state are unchanged, `baha up` uses a workload-only fast path. The existing workload engine fingerprints build and rendered service configuration, rebuilds only affected build-backed services, recreates only configuration-changed services, waits for workload HTTP/TLS readiness, and then re-checks overall application readiness.

Changes to `baseharbor.yaml`, protected deployment-control state, an unavailable/unready runtime, or any condition that cannot safely prove workload-only convergence continue through the full application reconciliation path.

`baha app update` keeps a separate purpose: it safely advances a Git-backed application from its configured upstream and therefore continues to require a clean, non-diverged working tree. It never stashes, resets, overwrites or discards local development work.

## Compatibility

- Manifest v1 remains the portable application contract.
- OIDC/OAuth2 and Service Binding remain the application-facing integration boundary.
- Keycloak, pgAdmin, Redis Commander and SeaweedFS remain reference/provider implementation details.
- Docker Compose and Podman/Quadlet retain equivalent logical identity and provider ownership semantics.
- Existing provider-registry v1 state remains readable; environment scope is additive deployment metadata.
