# BaseHarbor v0.4.17

BaseHarbor v0.4.17 adds standards-first managed application identity and the minimum operator-authentication boundary required before the v0.5 contract freeze.

The release keeps the normal developer path small: local dev remains trusted-local, while test and prod require an authenticated operator. Applications consume standard OIDC/OAuth2 interfaces rather than a BaseHarbor authentication SDK.

## Managed application identity

Applications can declare provider-neutral managed identity. BaseHarbor resolves the provider, creates or reconciles the application/environment identity scope, materializes a standard OIDC binding and verifies the realized state.

The managed Keycloak reference provider supports:

- isolated application/environment realms and clients;
- OIDC discovery and JWKS;
- exposure-derived redirect and logout URIs;
- scopes and claims;
- portable MFA, TOTP, WebAuthn, passkey and passwordless requirements;
- automatic TLS/trust;
- ownership-aware observe, reconcile, verify and destroy.

External OIDC remains supported without requiring provider-side provisioning. Provider-native names and administration APIs do not become portable application intent.

Shared provider infrastructure does not imply shared application identities.

## Operator authentication by environment

Operator access is scoped to the effective Target and Environment: dev uses trusted-local mode; test and prod require authenticated OIDC operator access.

For protected environments the CLI uses standards-compliant OIDC Authorization Code + PKCE and stores only a short-lived owner-only local session.

Commands: `baha login -e test`, `baha whoami -e test`, and `baha logout -e test`.

The first interactive use of an unconfigured protected Target/Environment can bootstrap either the managed Keycloak operator boundary or an external OIDC provider. The resulting configuration is Target/Environment-scoped and is reused by applications on that boundary.

Application identity and BaseHarbor operator identity remain logically separate even when one physical IdP provides both.

Advanced RBAC, JIT elevation, approvals and break-glass governance remain outside v0.4.17.

## Provider interfaces and optional management UIs

The guided application flow treats provider interfaces by semantic purpose instead of product name.

Optional management surfaces currently include:

- PostgreSQL administration through pgAdmin;
- cache administration through Redis Commander;
- shared object-storage administration through SeaweedFS Admin;
- the existing shared OpenBao web UI;
- managed identity login/account and separate Keycloak administration surfaces.

Selected development UIs are materialized automatically with managed TLS/trust and loopback host access. Test/prod administrative surfaces remain restricted/non-public by default.

A shared provider does not create one administration UI per application.

## Identity readiness, audit and recovery

`status`, `doctor`, JSON and evidence re-check the realized identity boundary instead of treating successful provisioning as permanent truth. Managed Keycloak verification covers issuer/discovery, owned realm/client state, redirect/logout drift, binding state and required authentication policy. External OIDC verification covers discovery and the materialized application binding.

Authenticated lifecycle audit events carry secret-safe operator identity and assurance context where available. Tokens, passwords, provider-admin credentials and authentication secrets are excluded.

Recovery treats portable identity intent separately from provider-held identity-directory data. The portable OIDC/client policy is reconstructed from application metadata. Provider-held users, credentials, MFA and passkey state are not claimed as recoverable without a scoped provider export; managed identity therefore remains an explicit durable recovery boundary, while external OIDC remains external.

## Environment-isolated provider registry

Provider registry bindings are deployment-scoped by Application plus Environment.

This fixes a pre-freeze ownership defect where two environments of the same application on one Target could otherwise replace each other's provider-registry binding even though their runtime resources were isolated.

Existing v1 registry entries without an environment remain readable and are migrated to the current deployment environment on normal reconciliation.

## Agent and read-only policy behavior

Read-only policy/evidence inspection no longer requires an installed Docker or Podman orchestration binary when repository Compose source can be analyzed statically.

The fallback remains fail-closed for security findings and is used only when runtime orchestration is genuinely unavailable. Runtime/provider errors are not silently converted into success.

## Compatibility

- Manifest v1 remains the portable application contract.
- OIDC/OAuth2 and Service Binding remain the application-facing integration boundary.
- Keycloak, pgAdmin, Redis Commander and SeaweedFS remain reference/provider implementation details.
- Docker Compose and Podman/Quadlet retain equivalent logical identity and provider ownership semantics.
- Existing provider-registry v1 state remains readable; environment scope is additive deployment metadata.
