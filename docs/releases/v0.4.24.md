# BaseHarbor v0.4.24 — Release notes (Unreleased)

**Status:** 0.4.24 – Unreleased; release not approved or published. The documentation describes implemented functionality separately from runtime acceptance.

## CLI and developer experience

- Task-oriented `baha new`, repository-aware application commands and guided operator workflows.
- Core/Target selection with `baha use`, Target-aware machine/JSON/MCP contracts and help/Doctor improvements.
- Issues #852–#855: real help line breaks, distinct Core TUI tabs, explicit preservation inventories for repository Compose data, and useful trust status after Core destruction. The ordered fixes from PR #856 are integrated in PR #837.
- Application-managed SQL and cache operations are `baha app sql` and `baha app cache`. The older `app psql` and `app valkey` names are not documented as supported.
- Ownership-aware trust cleanup, including `baha trust uninstall --yes` and explicit preservation of foreign CAs.

- Noninteractive quick init accepts explicit bootstrap consent (`--quick --yes`), distinguishes real terminals from `/dev/null`, and fails before manifest writes when Core is unavailable (#827). Stopped development routes give reconciliation guidance instead of blaming declared exposure (#828). Fresh automatically renewed service certificates remain healthy outside the seven-day renewal window (#829). MCP stdio drains decoded request replies on stdin EOF with a bounded, explicit failure for unfinished operations (#831).

- Root `down` distinguishes unsupported options from positional arguments before runtime access (#830).


- `config prompt` rejects EOF and non-terminal input before writes; saving requires explicit confirmation (#864).
- `BASEHARBOR_STATE_DIR` isolates configuration, selected Targets, deployment observations and native runtime/provider state from XDG installations (#865). Preserve the root across invocations; recovery defaults to a sibling directory outside destructible state.
- Workload access and logs resolve actual native managed bindings, including SQL/cache TLS references (#866).
- Resume and verified no-op reconciliation refresh deployment observations; readiness is derived from the same live checks used by status/JSON/MCP (#867, #871). Running workloads without verifiable readiness are reported as running, not verified ready.
- Rebootstrap after owned Core destruction allocates a fresh private recovery path while preserving retained recovery bytes; explicit existing paths and active Core collisions remain rejected (#868).
- Port fallback requires consent and reports both the requested and selected host ports even when successful activity details are hidden (#869).
- Compose `include` fails closed with a typed unsupported result and explicit flatten/review/source-selection instructions; nested sources are not partially detected (#870). See [workload source limitations](../explanation/workload-sources.md).

## Core, providers and recovery

- Provider-update admission checks release-pinned digests, installation ownership, verified backup prerequisites and compatible provider versions.
- PostgreSQL physical basebackup, isolated safe extraction and file integrity verification are implemented. Native Docker and Podman rootless HA recovery transport acceptance passed at Core `49a2fab76079b98b5697ba9f556abb6e6c066cac`, [run 37954182113](https://github.com/mcpdev80/baseharbor/actions/runs/37954182113).
- An authenticated three-member etcd mTLS isolated snapshot/restore/boot/quorum path passed with a separate cluster identity while the source Patroni quorum remained healthy.
- SQL recovery receipts distinguish started/restored/recovered states and do not replay ambiguous commits automatically.
- Fresh installations use standard topology when `ha` is omitted or false; component overrides control explicit native HA. SeaweedFS and Prometheus no longer implicitly start multiple data members. Retained installations are protected from silent topology conversion. See the [complete provider audit](../explanation/providers.md#explicit-ha-and-native-provider-topology).
- Status and Doctor distinguish data/service members, auxiliary processes and authenticated replication observations. Unknown replication/failover proof is reported explicitly.
- Shared providers are deployed once per Core/Target. Shared Keycloak uses a dedicated database/user on Core PostgreSQL; application SQL databases/users and Valkey ACL users/key namespaces remain isolated logical consumers. AppScoped placements retain separate deployments. Protected empty SQL-only modules are observed through their actual Core owner (#857).
- Configured-only applications can be destroyed without installing Core after ownership and absence checks. `baha app init --agents` only updates the bounded AGENTS.md section, including noninteractive JSON output; precise errors and Doctor distinguish NOT DEPLOYED from incomplete retained state (#858–#860).
- Logical provider recovery replaces only the bound database’s non-system schemas and restores its original ownership and ACLs in one transaction, including initdb’s standard `public` schema. Unknown SQL commit outcomes remain blocked from blind replay.

The candidate targets OpenBao 2.7.1. Native Keycloak 26.7.5 → 26.8.0 is admitted only for a single owned Core with an offline SQL/configuration backup and recovery; HA remains restricted to newer patches in the same minor stream. PostgreSQL major upgrades and unreviewed provider minor/major paths remain blocked. Real-version, state-preservation and injected-failure recovery require the targeted native Docker/Podman gates. Exact source SHAs, run IDs and their outcomes are recorded in [PR #837](https://github.com/mcpdev80/baseharbor/pull/837).
