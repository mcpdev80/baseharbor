# BaseHarbor v0.4.10

v0.4.10 is a security and runtime-hardening patch for the v0.4 line. It publishes the corrected managed-Compose runtime after the original v0.4.9 release validation exposed real Loki/Alloy and OpenBao startup defects.

## Why this release exists

The immutable v0.4.9 tag introduced the centralized logs capability, but its release acceptance uncovered problems that only appeared under real Docker/Compose execution:

- Loki/Alloy host publishing did not work correctly while both services were attached only to an internal Compose network;
- provider volume/config permissions needed to work without a privileged root initialization helper;
- OpenBao could not safely use its image entrypoint with a read-only root filesystem until its generated config path was made explicitly writable;
- a fresh control-plane start could report success before OpenBao was actually exec-ready.

v0.4.10 fixes those defects without weakening the zero-trust runtime model.

## Managed containers are actually non-root

The current Compose reference runtime now hardens the managed service set consistently:

- PostgreSQL and Valkey;
- OpenBao;
- Caddy;
- SeaweedFS;
- OpenTelemetry Collector;
- Prometheus;
- Loki and Alloy;
- Application Runtime Broker;
- Runtime Provider Executor;
- Connectivity Relay.

Where technically supported they run with:

- an explicit non-root identity;
- read-only root filesystem;
- all Linux capabilities dropped;
- `no-new-privileges`;
- only narrowly scoped writable volumes/tmpfs.

The validation fixture checks the effective process UID as well as the configured Compose user. A container configured as non-root but actually running UID 0 does not satisfy the release gate.

## OpenBao hardening

OpenBao starts directly as its non-root `openbao` user. BaseHarbor does not add a root init container or grant `CAP_CHOWN`.

The image-generated local configuration is written to an ephemeral writable `/openbao/config` tmpfs while durable OpenBao state remains on its dedicated persistent volume. The image-supported `SKIP_CHOWN` mode prevents an unnecessary privileged ownership-repair attempt.

Fresh control-plane startup also waits until OpenBao is genuinely exec-ready before reporting success.

## Loki and Alloy under rootless Compose

Loki and Alloy keep an internal-only network for provider traffic. A separate provider-owned bridge exists only so Docker/Podman can realize the required host-published listeners.

Those host-facing listeners remain bound to `127.0.0.1`; this change does not introduce wildcard host exposure, host networking or a container-runtime socket.

The end-to-end logs acceptance still verifies:

```text
workload RFC5424/syslog
  -> Alloy
  -> Loki
  -> LogQL query
```

## Future Kubernetes/OpenShift compatibility

Compose-specific UIDs remain deployment details, not portable application intent.

BaseHarbor-owned runtime images prepare writable state directories so a future Kubernetes/OpenShift runtime can assign an arbitrary non-root UID rather than inheriting a fixed Compose UID. v0.4.10 does not claim Kubernetes/OpenShift runtime support; it preserves the security boundary needed for it.

## Compatibility and upgrade impact

- Manifest v1 is unchanged.
- No application manifest migration is required.
- Provider placement semantics remain `shared | application | external`.
- Existing logical resources and application ownership semantics are unchanged.
- This is a backward-compatible patch release for the v0.4 line.

## Release integrity

The existing `v0.4.9` tag is immutable and is intentionally not moved or recreated. v0.4.10 is the corrected release line containing the security follow-up.
