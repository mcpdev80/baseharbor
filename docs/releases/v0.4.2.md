# BaseHarbor v0.4.2

BaseHarbor v0.4.2 separates an application's logical resource from the provider instance that happens to serve it.

That distinction lets BaseHarbor reuse infrastructure where sharing is sensible, keep dedicated infrastructure isolated where it matters, and adopt existing external services without pretending BaseHarbor owns them.

The developer workflow stays the same: **no Manifest v1 migration is required**.

## What changes

BaseHarbor now understands three provider scopes:

- **shared** — one BaseHarbor-managed provider can serve multiple applications;
- **application-scoped** — a provider belongs to one application and cannot cross that ownership boundary;
- **external** — an existing/BYO provider can satisfy a logical resource while its lifecycle stays outside BaseHarbor.

The current stack maps naturally to this model:

```text
OpenBao              -> shared
PostgreSQL instances -> application-scoped
Valkey instances     -> application-scoped
```

## Why this matters

This is the foundation for later choices such as shared observability, dedicated databases, customer-managed services and managed cloud providers without changing the application's logical contract.

A second application can reuse the same shared provider without BaseHarbor accidentally provisioning a duplicate. A dedicated provider cannot be reused by another application. An external provider can be bound, but BaseHarbor will not delete, update or back up the provider itself.

## Safety and compatibility

Provider registry state is stored in protected BaseHarbor state, written atomically and updated under a process lock. Corrupt, duplicate or ambiguous state fails closed.

Credentials and secret-bearing endpoints do not belong in the registry.

Existing v0.4.1 repositories are adopted automatically after the next successful:

```bash
baha app apply
```

or:

```bash
baha app up
```

Destroying an application removes its registry bindings and BaseHarbor-owned application-scoped provider records while shared and external provider instances remain.

## Intentionally not included

v0.4.2 does not add a new public provider-selection syntax, replace the existing Compose provisioning paths, or implement Kubernetes/OpenShift/cloud providers. Provider placement remains operator state so the portable application contract stays stable.
