# BaseHarbor v0.4.15.1

BaseHarbor v0.4.15.1 is a focused hotfix release for defects found during real repository adoption and post-v0.4.15 lifecycle testing.

It intentionally preserves the v0.4.15 architecture and compatibility surface. Larger runtime-identity changes, especially consolidating all shared provider Compose projects into one stack, are deferred to normal v0.4.x work instead of being rushed into this patch.

## Runtime Broker compatibility

A CLI rebuilt from the released source line could previously reject the matching v0.4.15 Runtime Broker solely because the Git commit SHA differed.

v0.4.15.1 keeps Git SHA as provenance but treats the versioned runtime contract as the compatibility boundary. Deterministic version mismatches now fail immediately instead of waiting through the readiness retry window.

## Repository adoption and Compose behavior

Real-world Compose repositories exposed several adoption gaps.

v0.4.15.1:

- resolves YAML anchors and merge keys during repository inspection;
- fails explicitly on unsupported Compose `include` or `extends` inheritance instead of silently losing services;
- refuses deterministic init when repository ambiguity has not been resolved by explicit intent;
- detects database bootstrap mounts such as `docker-entrypoint-initdb.d` and stops before replacing a database if the bootstrap would otherwise be discarded;
- automatically remaps occupied fixed host-port bindings through a BaseHarbor-owned deployment override without rewriting the repository;
- prevents interactive TTY stdin from leaking into Compose/BuildKit progress commands and causing indefinite rebuild hangs.

## Lifecycle and registry correctness

Application and installation state is more consistent after partial failures and stop/destroy operations.

- `baha app down` records the observed stopped state.
- `baha app list` tolerates incomplete deployment directories and reports warnings instead of failing the complete list.
- Global `baha status` shows BaseHarbor-native target, control-plane and application information rather than raw Compose output.
- Out-of-repository restore verifies that the source repository can be resolved before durable state is changed.
- `baha destroy --all` removes BaseHarbor-owned Runtime Broker volumes while still preserving application-owned workload data.

## Targets

The implicit local target now appears in `baha target list`.

Creating a new target no longer silently makes it the default unless `--default` is supplied, and invalid target names now explain the accepted lowercase slug rules.

## MCP lifecycle

Mutating MCP operations can legitimately exceed common client request timeouts during image pulls, builds and readiness convergence.

Once a mutating lifecycle request has been accepted, BaseHarbor now keeps its convergence independent from client-request cancellation so a short client timeout does not intentionally truncate the deployment half-way through.

Clients should still use a realistic lifecycle timeout; 300 seconds is the recommended general-purpose starting point. Read-only MCP tools may be auto-allowed while mutating tools remain approval-gated.

## Compatibility

Manifest v1 remains unchanged.

Docker remains Compose-based and Podman remains native Quadlet/systemd-user based. The fixed-port fallback is implemented as a deployment-local override with aligned semantics across both providers.

Runtime/provider project identities from v0.4.15 are intentionally unchanged in this hotfix. Operator-visible shared-stack consolidation is deferred because it requires an explicit migration strategy.
