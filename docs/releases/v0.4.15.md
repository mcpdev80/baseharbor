# BaseHarbor v0.4.15

## Deployment Targets

BaseHarbor now models the deployment destination as a first-class **Target**, separate from the portable Application contract and the selected Environment.

A concrete deployment identity is:

```text
target + application + environment
```

Targets describe the runtime provider, access reference and target scope. The repository remains the source of portable application intent; selecting a Target never rewrites `baseharbor.yaml`.

Target configuration is stored in the XDG user configuration:

```text
$XDG_CONFIG_HOME/baseharbor/config.yaml
~/.config/baseharbor/config.yaml
```

Mutable runtime and deployment state is isolated per Target:

```text
$XDG_DATA_HOME/baseharbor/targets/<target>/
~/.local/share/baseharbor/targets/<target>/
```

This allows Docker and Podman destinations, and later Kubernetes/OpenShift destinations, to coexist without sharing BaseHarbor-owned state.

The effective Target resolves in this order:

```text
explicit --target
BASEHARBOR_TARGET
configured default target
implicit local compatibility target
```

Useful commands include:

```bash
baha target
baha target -o json
baha target list
baha target show NAME
baha target create NAME --provider docker --access local-docker --reference local --scope default
eval "$(baha target activate NAME)"
baha app list
baha app list --all-targets
```

Optional shell integration for Bash, Zsh and Fish can display the active Target directly in the prompt. Production indicators remain explicit text and never rely on color alone.

The same Target metadata is exposed through structured CLI results and the read-only MCP tool `baseharbor.target`.

Kubernetes and OpenShift Target definitions are accepted by the contract, but execution remains fail-closed until those runtime providers are implemented.

## Podman runtime: Compose to Quadlet

BaseHarbor translates Compose-based workload and managed-service definitions into native **Podman Quadlets**.

Docker continues to use Docker Compose. On Podman, the full BaseHarbor lifecycle is managed through rootless `systemd --user` and no longer depends on `podman-compose`.

Pre-Release Podman acceptance explicitly blocks `podman compose`, so successful release evidence proves that the validated Podman path is Quadlet-only.


## Full installation destroy

v0.4.15 adds an explicit installation-wide cleanup path:

```bash
baha destroy --all
baha destroy --all --yes
```

Plain `baha destroy` keeps its existing ownership-safe Target-scoped behavior. The `--all` path is intentionally different: after an explicit warning it enumerates deployments and Targets, releases managed connectivity, reuses the existing application destroy lifecycle, removes BaseHarbor-owned shared providers/runtime/control planes, and finally removes BaseHarbor XDG data/config.

Cleanup continues best-effort across partial or damaged BaseHarbor state and reports `REMOVED`, `SKIPPED`, `NOT FOUND` and `FAILED` outcomes. Application source repositories and foreign/external application-owned resources are never deleted.
