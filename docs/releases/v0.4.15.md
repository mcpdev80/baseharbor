# BaseHarbor v0.4.15

v0.4.15 completes the pre-freeze Target, secure service-access, observability and agent-native lifecycle foundation while preserving Manifest v1 and provider-neutral application intent.

## Highlights

### First-class deployment Targets

Deployment destination is now a first-class **Target**, separate from Application and Environment.

A concrete deployment identity is:

```text
target + application + environment
```

Targets describe runtime provider, access reference and target scope. Repository intent stays portable and selecting a Target never rewrites `baseharbor.yaml`.

Target configuration lives in XDG user configuration and mutable runtime/deployment state is isolated below:

```text
$XDG_DATA_HOME/baseharbor/targets/<target>/
~/.local/share/baseharbor/targets/<target>/
```

The same application/environment can therefore coexist on multiple Docker/Podman Targets without sharing BaseHarbor-owned state.

Useful commands:

```bash
baha target
baha target -o json
baha target list
baha target show NAME
baha target create NAME --provider docker --access local-docker --reference local --scope default
eval "$(baha target activate NAME)"
baha app list
baha app list --all-targets
```

Target selection resolves in this order:

```text
explicit --target
BASEHARBOR_TARGET
configured default target
implicit local compatibility target
```

Kubernetes and OpenShift Target definitions remain contract-only and fail closed at execution until those runtime providers are implemented.

### Podman uses native Quadlets

Docker continues to execute Docker Compose directly.

Podman now translates the Compose-compatible workload/provider model into native rootless Quadlets managed through `systemd --user`. BaseHarbor no longer depends on `podman-compose` for the supported Podman path.

Pre-Release Podman acceptance explicitly blocks `podman compose`, so successful evidence proves native Quadlet execution.

### TLS everywhere and environment-aware service access

Managed network service access now uses the provider-neutral secure service-access baseline established for future managed identity work.

Key properties:

- TLS or stronger authenticated transport for managed network services;
- developer-friendly trusted-local access in dev without manual certificate/token handling;
- automatable protected credentials/trust material in test;
- authenticated, least-privilege management/observability access in production;
- managed-local PKI plus external/BYOC PKI support behind provider/runtime boundaries;
- no product-specific TLS/auth fields in portable application intent.

The application consumes standard URLs, environment variables and file bindings. Trust/auth realization remains deployment/provider state.

### Complete Metrics / Logs / Traces semantics

Observability is now driven through the shared provider/runtime signal model rather than product-specific registration branches.

When enabled, BaseHarbor can collect authorized signals from:

- application workloads;
- application-scoped managed providers;
- shared/platform providers within the allowed sharing boundary;
- Runtime Broker and Runtime Executor.

The common source classes remain:

```text
application
application-provider
platform-provider
```

Provider Integration descriptors declare supported signal status, realization mode and verification semantics. Unsupported or adapter-required signals are reported truthfully rather than silently presented as collected.

Runtime Broker and Runtime Executor now expose/produce standards-based observability:

- OpenMetrics;
- structured secret-safe logs;
- OTLP/http-protobuf traces.

Prometheus/Loki/Tempo/Collector remain reference implementations behind provider-neutral contracts.

### Complete agent-native lifecycle over MCP/JSON

The machine/MCP surface now covers the supported semantic lifecycle through the same domain logic used by the CLI:

- inspect;
- plan;
- apply;
- status;
- doctor;
- observe;
- update;
- repair;
- backup;
- restore;
- destroy;
- policy check/explain;
- Target inspection.

Mutating/destructive operations preserve policy, ownership, preflight, reconciliation and verification semantics. Destructive operations require explicit approval. Recovery choices and missing required inputs produce typed actionable machine errors.

No generic shell, Docker, Compose, Podman or provider-native execution primitive is exposed.

### Full installation destroy

An explicit installation-wide cleanup path is available:

```bash
baha destroy --all
baha destroy --all --yes
```

Plain `baha destroy` keeps its existing Target-scoped fail-closed behavior.

`--all`:

- enumerates registered deployments across Targets;
- releases managed connectivity;
- reuses the existing application destroy lifecycle;
- removes BaseHarbor-owned shared providers/runtime executors/control planes;
- cleans BaseHarbor XDG state/config last;
- continues best-effort across partial/broken BaseHarbor state;
- reports `REMOVED`, `SKIPPED`, `NOT FOUND` and `FAILED` outcomes.

Application source repositories, foreign resources and external application-owned data are preserved.

## Compatibility and upgrade impact

- Manifest v1 remains supported and unchanged as the compatibility contract.
- Runtime, capability and delivery provider axes remain separate.
- Docker remains Docker Compose based.
- Supported Podman execution changes from Compose-provider execution to native Quadlets.
- Existing portable application instrumentation does not need to change when deployment security/PKI realization changes.
- Kubernetes/OpenShift execution is not part of this release.

## Security

v0.4.15 strengthens the default security boundary:

- managed network access has an explicit TLS/auth story;
- secret/private-key/token material remains protected state and is excluded from normal machine/human output and evidence;
- observability preserves application/environment/placement isolation;
- MCP mutation never bypasses normal lifecycle safety;
- destroy operations remain ownership-safe and do not guess foreign ownership.

## External acceptance

The external `baseharbor-demo` remains a normal consumer/test fixture. CI orchestration lives in the BaseHarbor repository.

The mandatory Pre-Release workflow validates one exact BaseHarbor candidate plus one exact demo SHA across:

- source/build/documentation checks;
- Docker runtime acceptance;
- Podman/Quadlet runtime acceptance;
- full Docker demo acceptance;
- full Podman/Quadlet demo acceptance;
- immutable combined release evidence.

## Deferred work

v0.4.15 intentionally does not implement:

- Kubernetes/OpenShift runtime execution;
- full managed OIDC/RBAC/JIT identity;
- v0.4.16 selectable recovery-unit expansion;
- v0.4.16 audit/evidence semantics;
- v0.5 public contract freeze.

Those remain assigned to their later roadmap issues/releases.
