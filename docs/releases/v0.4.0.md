# BaseHarbor v0.4.0

BaseHarbor v0.4.0 is primarily an **architecture and developer-experience release**. The existing Compose workflow from v0.3 remains fully supported, but BaseHarbor now has the provider-neutral boundaries needed to grow toward Kubernetes, OpenShift and replaceable backend providers without forcing applications to change their logical contract.

## Highlights

The biggest change is the new separation between **what an application needs** and **how a deployment provides it**.

Applications continue to use the existing Manifest v1 `baseharbor.yaml`. Internally, BaseHarbor now translates the portable parts of that manifest into a provider-neutral `PortableContract`. Runtime selection, deployment policy and concrete backend products stay outside the application contract.

v0.4 also introduces a reusable declarative input resolver. This allows `baha app init` and repository-aware `baha up` to ask only for values that are actually missing, while automation can provide non-secret deployment inputs explicitly.

## Added

- **Provider-neutral application contract seam** through `PortableContract`.
  Manifest v1 remains compatible, while logical SQL, key/value and secret requirements are normalized away from Compose implementation details.

- **Runtime provider identity and capability negotiation**.
  Compose is still the only complete runtime provider, but operations now explicitly resolve the selected provider and verify required capabilities before entering runtime-specific code.

- **Deployment-owned runtime provider and profile state**.
  Runtime selection is no longer something an application contract should have to encode.

- **Declarative input resolver** with:
  - safe defaults;
  - generated values;
  - external/operator supplied values;
  - conditional `required-if` dependencies;
  - explicit secret marking and redaction.

- **Automation-safe deployment input injection**:
  `baha app init --input NAME=VALUE` can provide declared non-secret values without interactive prompts.

- **Shared deployment-input flow for `baha app init` and `baha up`**.
  Existing state is reused, only unresolved values are requested, and non-interactive mode does not invent unsafe external values.

- **Explicit contract evolution rules**.
  Manifest v1 remains a supported compatibility surface and incompatible required semantics must use a new contract version.

## Changed

- `baseharbor.yaml` is now explicitly treated as the **public compatibility surface**, while `PortableContract` is the internal provider-neutral application-intent view.

- Application requirements, runtime-provider selection and capability-provider/product selection are now separate architectural concerns.

- Runtime-facing application commands now pass through a central provider/capability guard before reaching the current Compose implementation.

- Provider substitution is **fail-closed**: an unsupported provider or missing runtime capability causes a clear error instead of silently falling back to Compose or weakening guarantees.

- Repository deployment initialization is more deterministic:
  interactive commands ask only for unresolved values, while automation can provide explicit non-secret values.

- Documentation and architecture now distinguish current implementation from future provider work more strictly.

## Security

- Secret input values are redacted when rendered and excluded from generic persistable resolver output.

- Unsupported runtime providers and capabilities fail before mutation.

- Provider/runtime state remains protected deployment state rather than committed application configuration.

- Existing secret storage, TLS validation, runtime identity and backup/restore security boundaries remain unchanged and separate from generic input handling.

## Deprecated

No public command or Manifest v1 field is deprecated in v0.4.0.

The architecture does, however, move away from treating Compose-specific Manifest v1 fields as the long-term provider-neutral model. They remain supported compatibility inputs and are **not scheduled for removal in this release**.

## Removed

Nothing from the supported v0.3 public CLI or Manifest v1 workflow is removed.

## Compatibility and upgrade notes

Existing v0.3 repositories should continue to work without rewriting `baseharbor.yaml`.

Legacy deployment state without explicit runtime-provider metadata defaults safely to Compose.

There is no Kubernetes or OpenShift runtime implementation in v0.4.0. Those remain planned later phases; v0.4 provides the contract and provider seams they will use.

If you already use BaseHarbor with Compose, the expected upgrade experience is therefore:

```text
v0.3 application contract
        |
        v
upgrade BaseHarbor
        |
        v
same application contract
same Compose workflow
new provider-neutral internals
```

## What this enables next

v0.4 is the foundation for the next platform steps:

- replaceable SQL, cache, secrets and object-storage capability providers;
- explicit environment/platform policy;
- standard and HA topology profiles;
- Kubernetes runtime support;
- OpenShift/enterprise specialization.

The key promise is that those future changes should not require applications to adopt a completely new operational contract.
