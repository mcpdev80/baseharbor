# BaseHarbor v0.4.8

v0.4.8 adds the first real metrics collection/storage integration without making Prometheus part of the application contract.

The application describes the metrics interface it provides. The deployment decides whether to collect it. The platform selects the provider.

## Why this matters

A developer can expose a normal OpenMetrics-compatible endpoint and describe it once:

```yaml
workload:
  compose: compose.yaml
  services:
    - api

metrics:
  sources:
    - name: application
      service: api
      port: 8080
      path: /metrics
```

That source is represented by the versioned `metrics/v1` capability. There is no `prometheus: true` field and no Prometheus-specific target configuration in `baseharbor.yaml`.

For the current Compose runtime, Prometheus is the first reference provider behind that contract.

## What changed

BaseHarbor now:

- understands `metrics/v1` as a provider-neutral application-provided metrics source;
- detects conventional OpenMetrics/`/metrics` repository evidence and reconciles it to the canonical metrics capability;
- resolves Prometheus 3.14.0 through the generic provider-placement model, using safe shared placement by default and supporting application-scoped or named shared-boundary placement;
- generates Prometheus file-discovery targets automatically instead of requiring manual target editing;
- gives every participating application its own isolated metrics network and attaches the selected Prometheus instance only to explicitly registered application networks;
- gives every app/environment/service a deterministic collision-resistant network alias;
- labels scraped targets with BaseHarbor application, environment, workload service and logical source identity;
- verifies actual scrape/ingestion through Prometheus before declaring the metrics path ready;
- removes application target state during application destroy;
- removes the shared Prometheus provider and BaseHarbor-owned storage during global destroy.

Prometheus is pinned to 3.14.0 for this release rather than the 3.15 release-candidate line.

## Collection policy

Metrics collection is deployment/platform policy.

The Compose defaults are:

- `dev` / `development`: enabled;
- test / staging / production: disabled;
- `BASEHARBOR_METRICS_ENABLED=true|false`: explicit operator override.

This keeps local development convenient while avoiding an implicit production observability deployment.

An application may declare a metrics source even when collection is disabled. Its portable contract remains valid; BaseHarbor simply does not bind it to the Prometheus provider in that deployment.

## Provider placement and isolation

Prometheus uses the generic BaseHarbor placement model. The safe default is shared, but application-scoped placement is supported and shared placement may be restricted to a named sharing boundary.

Shared never means flat access. Two applications may both have a Compose service named `api` and both expose `/metrics` on port 8080; each receives its own isolated metrics network, and the selected Prometheus instance is attached only to the application networks explicitly registered for that placement boundary. Distinct target files and application/environment/source labels keep data attributable.

The release acceptance test runs two isolated application targets through one shared/default Prometheus instance and requires both real scrapes to succeed. Unit coverage additionally proves independent application-scoped instances and independent named shared boundaries.

## Security

The Prometheus provider:

- has no Docker/Podman socket;
- uses a read-only root filesystem;
- drops Linux capabilities;
- enables `no-new-privileges`;
- exposes its HTTP API only on host loopback for local lifecycle verification;
- receives no application credentials or provider-global secrets through target state.

Generated target files contain endpoint identity and non-secret attribution labels only.

## Compatibility and upgrade impact

Manifest version remains `1`.

Existing applications without `metrics.sources` are unchanged. Existing OTLP applications remain unchanged.

`telemetry.otlp/v1` and `metrics/v1` are deliberately separate:

- OTLP describes application telemetry export transport;
- metrics/v1 describes an application-provided metrics source.

Requesting OTLP alone still does not start Prometheus. Metrics collection does not start Grafana, Loki or Tempo.

## Intentionally deferred

v0.4.8 does not add:

- Grafana dashboards;
- Loki log storage;
- Tempo trace storage;
- alert routing/rule management;
- Kubernetes/OpenShift ServiceMonitor realization;
- provider-selection UI;
- VictoriaMetrics/Mimir implementations;
- automatic routing of OTLP metrics into Prometheus storage.

Those remain separate provider/policy tracks. The purpose of v0.4.8 is to establish the replaceable metrics capability/provider boundary and prove one production-shaped Compose implementation end to end.
