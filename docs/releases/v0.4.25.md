# BaseHarbor v0.4.25

Release candidate — not yet published.

## Start small

A supported local application with no managed service requirements can now run
on Docker or rootless Podman without installing the management Core or logging
in. BaseHarbor no longer implicitly requests SQL. A real workload is still
required; an empty directory does not become a ready application.

## Less manifest setup

Manifest v1 keeps its existing format. Start with `version`, `app.name` and
`app.environment`; add `services` only for capabilities the application needs.
BaseHarbor assigns one durable application identity during explicit initialization
and reuses it across edits, restart and deployments. Do not enter `app.id` in
authored YAML: it is rejected before mutation. System-generated records and
machine results retain the canonical ID. Reading or planning never creates one.

## See what an application needs

Plans share one capability/provider resolution and footprint across CLI, JSON,
MCP and HTTP. Compatible Target providers can be reused; shared resources stay
protected when one application drops a capability. Unknown dependency or memory
figures remain unknown rather than promising savings that were not measured.

## Compatibility and limits

SQL, cache and Identity have selective native realization and add/remove/re-add
paths; Identity includes its genuine SQL dependency. Removing a requirement
releases its binding and retires owned runtime that no active consumer needs.
Persistent data, credentials and recovery material remain at their owned locations
by default. Another application's or an independent management consumer's
requirements continue to protect their shared services.

Provider-change plans distinguish lost functionality from verified continuation,
and retained material from working access. Deliberate removal without continuation,
unknown consequences and owned data deletion require **Achtung** and two explicit
confirmations of the concrete plan. Ordinary apply consent does not grant either
confirmation or data deletion. Ownership and actual execution support remain
required; no plaintext secret fallback or unauthenticated access is introduced.

An explicitly installed management Core retains its TLS/OIDC, mTLS, HA and
recovery requirements. Unsupported native BYO adapters fail before provisioning.
This pre-v1 release does not provide a migration for authored application IDs.
The capability/provider wizard, profile import/onboarding, new Console/TUI
features and host-platform support belong to later releases.

The candidate remains under qualification. Secrets/HTTPS and mixed selective
lifecycles, every provider-change entry point, and candidate-matched Demo,
Console and Node Connector journeys must pass the canonical readiness audit
before pre-release. Earlier scoped runtime receipts do not establish that status.

Dependency maintenance includes verified Action/image pins, updated Pages actions
and the Alpine recovery helper. Renovate groups updates into one reviewed batch
without automerge after the configuration reaches its active base branch.
