    BaseHarbor v0.4.8

    v0.4.8 verwandelt die Fähigkeitsplattform in etwas, was Anwendungen nicht nur zur Bereitstellungszeit, sondern auch während des Laufens nutzen können.

    Das Release vereint vier miteinander verbundene Schritte:

    1. kontinuierliche Reconciliation zwischen Repository und Auftrag;
    2. sichere Anwendungszeit-Ressourcenoperationen, wobei S3 die erste echte dynamische Ressource ist;
    3. anbieterneutrale Metriken-Sammlung mit Prometheus als erster Compose-Referenzanbieter;
    4. explizite richtungsübergreifende Konnektivität ohne Abschwächung der Anwendungsisolation.

    Der Anwendungsauftrag bleibt überall produktneutral. BaseHarbor fügt mehr Infrastruktur-Verhalten hinzu, ohne dass Anwendungen baseHarbor-spezifisch werden müssen.

    Kontinuierliche Entwicklung der Anwendung

    BaseHarbor behandelt Anwendungsabsichten jetzt als sich entwickelnder Wunschzustand und nicht als einmaliger Setup-Fragebogen.

    Repository-Inspektion kann Fähigkeiten unterscheiden, die bereits von neuen, mehrdeutigen oder veralteten Beweisen erfüllt sind. Neu erkannte Anforderungen bleiben Vorschläge, bis explizit akzeptiert; Nichtwiederentdeckung einer bestehenden Fähigkeit erlaubt BaseHarbor nie, sie zu entfernen.

    Laufzeit-Betriebsnachweis wird auch von der Autorisierung getrennt. Code zu erkennen, der einen S3-Eimer erstellen oder eine Metrik-Quelle registrieren kann, gewährt diese Operation nicht automatisch.

    Dies gibt BaseHarbor einen Weg von der ursprünglichen Annahme durch späteres Anwendungswachstum, ohne den Vertrag der Anwendung zu regenerieren oder zu ersetzen.

    Runtime Resource API

    v0.4.8 vervollständigt den ersten Real Application-Time-Ressource-Pfad.

    Eine laufende Anwendung kann die pro-Anwendung Runtime Resource API für explizit autorisierte Fähigkeiten Operationen verwenden. Mutationen sind asynchron und idempotent, mit persistentem Betriebszustand, der Broker-Neustart überlebt.

    Die Sicherheitsgrenze bleibt streng:

    • der Broker pro Anwendung hat keine Docker/Podman-Buchse;
    • provider-global Administrator-Anmeldeinformationen nie die Anwendung Workload oder Broker eingeben;
    • Die Genehmigung ist dienst- und nicht anwendungsweit erteilt;
    • Laufzeitressourcen bleiben im Besitz der Anwendung;
    • cross-application read/bind/delete wird abgelehnt;
    • geheime Bindungen werden nur über den authentifizierten Bindungsweg zurückgegeben;
    • Betriebs-Metadaten bleiben frei von Anmeldeinformationen.

    Entwicklungsbroker stellen die eingebettete OpenAPI 3.1-Dokumentation auch auf einem Loopback-only-Port aus. Interaktive API-Dokumentation ist standardmäßig für die Entwicklung aktiviert und bleibt standardmäßig für Test/Staging/Produktion aus.

    Dynamische S3-Ressourcen

    object-storage.s3/v1 ist die erste über die Runtime Resource API verdrahtete Fähigkeit.

    Ein autorisierter Applikationsdienst kann zur Laufzeit einen S3-Eimer erstellen, inspizieren und löschen. BaseHarbor führt die Providermutation über den gemeinsam genutzten mTLS Runtime Provider Executor aus, anstatt dem Applikationsanbieter globale Anmeldeinformationen zu geben.

    SeaweedFS bleibt der erste Referenzanbieter. Runtime-created Buckets erhalten scoped Anmeldeinformationen und können über die normale S3 API mit authentifizierter Put/Get-Verifikation verbraucht werden.

    Die gleiche anwendungsgerechte Fähigkeit bleibt für zukünftige Ceph RGW, AWS S3 oder andere konforme Anbieter geeignet.

    Anbieterneutrale Metriken

    Anwendungen können einen normalen OpenMetrics-kompatiblen Endpunkt deklarieren:

    workload:
  compose: compose.yaml
  services:
    - api

metrics:
  sources:
    - name: application
      service: api
      port: 8080
      path: /metrics

    Diese Quelle wird dargestellt durch metrics/v1. Es gibt keine prometheus: trueFeld und keine Prometheus-Zielkonfiguration in baseharbor.yaml.

    Prometheus 3.14.0 ist der erste Compose-Referenzanbieter.

    BaseHarbor:

    • erkennt konventionelle OpenMetrics//metrics Nachweise für das Vorratslager;
    • erzeugt automatisch Datei-Entdeckungs-Ziele;
    • Etikettenserie mit Anwendungs-/Umwelt-/Dienstleistungs-/Quellenidentität;
    • erfordert einen wirklich erfolgreichen Scrape sichtbar als up=1;
    • unterstützt sowohl statisch deklarierte als auch explizit autorisierte laufzeitgenerierte Metrikquellen;
    • beginnt Grafana, Loki oder Tempo nicht als Nebenwirkung.

    Allgemeine Vermittlung von Anbietern

    Während der Implementierung von Metriken schließt v0.4.8 eine breitere Architekturlücke.

    Anbieterplatzierung ist jetzt eine explizite generische BaseHarbor-Domäne:

    Capability
  -> Provider
  -> Placement
       - application
       - shared
           - optional sharing boundary
       - external
  -> Runtime realization of the selected placement

    Der normale Entwicklerpfad bleibt einfach. BaseHarbor wählt sichere Standardeinstellungen, es sei denn, ein Operator bittet absichtlich um mehr Kontrolle.

    Für Prometheus unterstützt die aktuelle Compose-Implementierung:

    • shared— die sichere Voreinstellung;
    • shared mit einer benannten Teilungsgrenze;
    • application— eine anwendungsspezifische Prometheus-Instanz.

    Das generische Modell unterstützt external, aber der Prometheus Referenz-Anbieter nicht Werbung für externe Platzierung in v0.4.8, weil eine externe Metrik Sammlung Adapter ist noch nicht implementiert.

    Fortgeschrittene Compose-Operatoren können die Platzierung von Prometheus derzeit über den Bereitstellungszustand hinwegnehmen:

    BASEHARBOR_PROVIDER_PROMETHEUS_SCOPE=shared|application
BASEHARBOR_PROVIDER_PROMETHEUS_SHARING_BOUNDARY=<name>

    Dies folgt der UX-Regel von BaseHarbor:

    Konvention standardmäßig, Konfiguration nach Wahl.

    Anbieter Platzierung bleibt außerhalb der tragbaren Anwendung Absicht.

    Die Platzierungs-Scopes haben nun strenge Anbieter-Instanz Bedeutung:

    • application ist ein dedizierter Anbieter Instanz für genau eine Anwendung / Umgebung; Compose realisiert es mit dedizierten Anbieter Laufzeitzustand;
    • shared ist eine faule BaseHarbor Platform/Core Runtime-Infrastruktur und bleibt auch dann geteilt, wenn derzeit nur eine Anwendung sie verbraucht;
    • external bleibt außerhalb des Lebenszyklus von BaseHarbor.

    Explizite anwendungsübergreifende Konnektivität

    v0.4.8 fügt auch eine Minimal-Plattform-Anbindungsrichtlinie für Fälle hinzu, in denen isolierte Anwendungen kommunizieren müssen:

    app-a/api -> app-b/sql

    Die Regel wird einmal geschrieben. Sie wird nicht in beiden Bewerbungsverträgen dupliziert und ist unabhängig von der Anbieterfreigabe.

    BaseHarbor löst die konkrete Umgebung, den Runtime-Service, das Zielnetzwerk und den TCP-Zielport aus dem Laufzeitzustand. Explizite Umgebung oder Port-Qualifikation ist nur erforderlich, wenn die Auflösung mehrdeutig ist.

    Komponieren bewahrt die Richtung technisch. Quelle und Ziel werden nicht auf einem gemeinsamen Bridge-Netzwerk platziert. BaseHarbor erstellt eine verbindungsspezifische Quellverbindung und ein gehärtetes Relais aus dem versionskonformen BaseHarbor Runtime-Image. Nur die Quelle und das Relais verbinden diese Verbindung; das Relais schließt zusätzlich ein Zielnetzwerk an und leitet nur an den aufgelösten Zieldienst/Port weiter. Das Ziel schließt nie an die Quellverbindung an.

    Das Relais hat keinen host-veröffentlichten Port oder Docker/Podman-Socket, läuft nicht-root mit einem schreibgeschützten Root-Dateisystem, lässt Linux-Funktionen fallen und ermöglicht no-new-privileges.

    Konnektivitätspolitik überlebt app down; Staffellaufzeit wird suspendiert und später versöhnt app up/apply. Anwendung/globale Zerstörung scheitert geschlossen, während Konnektivitätspolitik immer noch auf verwaltete Anwendungen verweist.

    Null-Vertrauensmetriken Trennung

    Shared bedeutet nicht flachen Zugang.

    Jede teilnehmende Anwendung erhält ein eigenes isoliertes Metrik-Netzwerk. Shared Prometheus wird nur an die explizit für die Platzierungsgrenze registrierten Applikationsnetzwerke angehängt.

    Das bedeutet, dass fünf Anwendungen auf einer BaseHarbor-Installation sicher unterschiedliche Formen verwenden können, zum Beispiel:

    App A + B -> shared/default
App C     -> application-scoped
App D + E -> shared/team-x

    ohne dass D/Es Anbieter-Trust-Grenze gegenüber A/B ausgesetzt wird.

    Die Registrierung von Laufzeit-Metriken ist service-scoped. Ein Dienst kann sich nur selbst registrieren, und die Laufzeit-API akzeptiert Zielport/Pfad-Semantik anstatt beliebiger Hosts oder URLs. BaseHarbor leitet die eigentliche Scrape-Identity-Server-Seite ab.

    Zielzustand enthält keine Anmeldeinformationen oder Provider-globale Geheimnisse.

    Platzierungsänderungen sind lebenszyklussicher

    Anbieterplatzierung wird in der geschützten Anbieter-Register beibehalten.

    Lifecycle cleanup verwendet daher die registrierte/aktuelle Platzierung anstatt davon auszugehen, dass die heutige Umgebung überschreiben immer noch die Platzierung während der vorherigen Anwendung verwendet entspricht.

    Wenn sich die Platzierung ändert, konvergiert und überprüft BaseHarbor zuerst den neuen Metrikpfad, entfernt dann den vorherigen Ziel-/Trust-Edge-Zustand des Anbieters und versöhnt erst danach das Providerregister.

    Runtime-only-Metriken Berechtigungen erhalten auch geschützten Provider-Registratur-Zustand, auch wenn keine statischen metrics.sources Eintrag existiert.

    Erhebungspolitik

    Die Metrics-Sammlung bleibt von der Anbieterplatzierung getrennt.

    Standardeinstellungen komponieren:

    • dev / development: aktiviert;
    • Test / Inszenierung / Produktion: deaktiviert;
    • BASEHARBOR_METRICS_ENABLED=true|false: explizite Operatorüberschreibung.

    Eine Anwendung kann halten metrics/v1 Intent während der Sammlung ist deaktiviert für eine Bereitstellung. In diesem Fall BaseHarbor nicht auflösen oder Bereitstellung eines Metrik-Anbieter.

    Globaler Lebenszyklus und Anwendung

    Die Anwendung zerstöre entfernt nur den Metrikzustand der Anwendung entsprechend der registrierten Platzierung:

    • Mit der gemeinsamen Platzierung werden die Ziele dieser Bewerbung und die Registrierung des Trust-edge aufgehoben;
    • Die Bewerbungsplatzierung entfernt die dedizierte Prometheus-Instanz;
    • externe Anbieter bleiben extern im Besitz des Lebenszyklus.

    Global baha destroy --yes listet und entfernt jede im Besitz von BaseHarbor befindliche gemeinsame Prometheus-Instanz auf, einschließlich genannter Sharing-Grenzen.

    Die Lebensdauer des Shared Providers bleibt unabhängig von einer einzigen Anwendung. Global baha down die bestehenden Container der gemeinsamen Plattform/Core Runtime-Anbieter stoppt, ohne deren Netzwerke, Volumen oder Anbieterstatus zu löschen;baha up nimmt diese Anbieter wieder auf und versöhnt sich mit fortbestehenden anwendungsübergreifenden Verbindungen; die Laufzeiten des Anbieters mit Anwendungszweck verbleiben im Eigentum ihres Anwendungslebenszyklus.

    Kompatibilität und Upgrade-Wirkung

    Die offensichtlichste Version bleibt erhalten 1.

    Bestehende Anwendungen ohne Metriken-Intent bleiben unverändert. Eine unbenutzte Prometheus-Deployment-Überschreibung hat keine Auswirkungen auf Anwendungen, die nicht verwenden metrics/v1.

    Bestehende OTLP-Anwendungen bleiben unverändert.telemetry.otlp/v1 undmetrics/v1 bewusst getrennt sind:

    • OTLP beschreibt den Transport von Anwendungstelemetrie-Exporten;
    • metrics/v1 beschreibt eine anwendungsbezogene Metrikquelle.

    Das Provider-Register-Format bleibt rückwärtskompatibel; das neue Sharing-Grenzfeld ist additiv.

    Kubernetes und OpenShift werden von v0.4.8 nicht implementiert.Das Platzierungsmodell ist bewusst unabhängig von Compose-Netzwerken/Projekten, so dass später Kubernetes Namespaces/Cluster, OpenShift-Projekte, Helm-Releases und Operatoren die gleiche Semantik ohne Änderung der Anwendungsabsicht implementieren können.

    Sicherheit

    Der Prometheus-Anbieter:

    • hat keine Docker/Podman-Buchse;
    • verwendet ein schreibgeschütztes Wurzel-Dateisystem;
    • die Linux-Fähigkeiten fallen lassen;
    • ermöglicht no-new-privileges;
    • veröffentlicht seine HTTP-API nur auf Host-Loopback;
    • verbraucht nur schreibgeschützten Zielzustand;
    • erhält keine Anmeldeinformationen durch Zielerkennung.

    Die Runtime Resource API und der Provider Executor verwenden weiterhin Anwendungs-/Workload-Identität, mTLS und die Autorisierung mit den geringsten Privilegien.

    Vorsorglich aufgeschoben

    v0.4.8 fügt nicht hinzu:

    • einem externen Prometheus-Sammeladapter,
    • Grafana-Dashboards,
    • Loki-Logspeicher;
    • Speicherung von Tempo-Trace-Daten;
    • Alarmführung/Regelverwaltung;
    • VictoriaMetrics/Mimir-Implementierungen;
    • automatisches Routing von OTLP-Metriken in die Prometheus-Speicherung;
    • Kubernetes/OpenShift ServiceMonitor Realisierung;
    • Kubernetes/OpenShift/Helm/Operator-Laufzeitimplementierung;
    • Provider-Auswahl Web UI.

    Diese bleiben später Anbieter/Laufzeit-Tracks. Das v0.4.8 Ziel ist es, die sicheren, austauschbaren Verträge zu etablieren, auf denen sie aufbauen können, ohne Anwendungen umzuschreiben.
