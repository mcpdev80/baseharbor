    Capability-first application contracts (v0.4.25)

    Binding scope: #872, corrected 2026-10-11. This supersedes the fixed SQL/Secrets/Identity bundle, authored IDs and deferred removal described in earlier planning and qualification records. Existing security, ownership, HA and recovery guarantees remain requirements.

    Authoring and system-owned identity

    version: 1
app:
  name: myapp
  environment: dev

    Services are optional and never implicit. SQL is services.sql: true, beneath services; rich service requirements and named instances use the existing grammar. No provider: section, alternate shorthand parser or additional required file.

    Developers NEVER set application IDs. ParseYAML rejects every app.id, including empty values, before mutation. Remove that field and explicitly initialize the application. There is no ID question or flag and no legacy authored-ID conversion. ParseCanonicalYAML uses the same parser with internal-record permission; only existing system-owned Store/backup adapters may use it. YAML serializes internal records, while AuthoredYAML omits the ID from developer outputs. Internal IDs and machine results remain valid and must never be regenerated during reading.

    MCP app.create and app.adopt accept the same typed intent without ApplicationID. Their input schemas derive from the canonical Manifest types, omit that system-owned field and reject a supplied value before mutation. Version, Name and Environment are required; omitted requirement sections use their empty defaults. Executable requirements and source selection are still validated. Authorization precedes identity persistence; outputs include the actual generated canonical ID. Repeated adoption never overwrites authored source. A retained canonical owner after an interrupted adoption supplies the same ID on retry.

    Operation Identity and mutation contract
    Parse / inspect / plan No allocation or persistence; resolve existing authoritative claims only
    Explicit initialization / registration Generate once if truly new, persist in existing canonical Store
    Repeat / restart / edit / another Target Reuse the same system-owned identity
    Conflicting or missing registered identity Fail before mutation; recover authoritative state, never allocate replacement
    Concurrent initialization Reuse Store.Create winner or report incomplete state for safe retry
    Developer app.id Actionable rejection, preserving authored file and existing user data

    ResolveIdentity is pure. Store.InitializeIdentity uses the existing canonical .baseharbor/apps/<name>/baseharbor.yaml owner. Deployment records project this identity. Adapters correlate repository/source ownership, not names across unrelated repositories. Read-only adapters never call Create, InitializeIdentity or Sync. No parallel identity registry, automatic migration or deletion of existing data.

    Provider resolution and footprint

    Application contract expresses need. Existing Target/deployment bindings express provider and placement. ProviderPreference optionally selects InstanceID or ProviderKind (both must agree when provided); empty means Automatic. Negotiation uses actual registered capability surfaces, without a hard-coded provider list. Existing compatible bindings remain stable; explicit disagreement is a typed conflict. Different Targets can realize the same portable requirement differently.

    ResolveFootprint reads one Target's existing capability.Registry v2 and provider facts from existing plans/observers. Facts carry actual dependency instance IDs: null means unknown, [] means verified none. No discovery writes, new registry, scheduler or second resolver. Cross-Target/foreign resources, cycles, missing dependencies and incompatible or ambiguous choices fail closed. Automatic without an available declaration is unresolved and cannot authorize provisioning. A verified selected provider is structurally complete even while its binding awaits the existing apply transaction.

    Runtime permission/consumption adapters supply verified DependencyRoots from existing plans to the same resolver. Nil roots with those intents mean incomplete; [] proves no extra provider realization, not absence of security requirements. Each ConsumerIntent supplies its own roots; one consumer cannot borrow another consumer's verification. Unknown roots never authorize a Core-free mutation.

    No capability implies the old Core package. SQL, cache, Secrets, Identity and HTTPS select only the realization and its genuine declared dependencies. Identity may need SQL. HTTPS does not automatically need Identity or OpenBao. Independently enabled management/Console services contribute their actual security requirements as separate consumers; TLS/OIDC/mTLS/authorization/HA/recovery are never weakened. The legacy core output classifies an actual declaration, never requests a bundle.

    The shared read-only result is baseharbor.footprint/v1:

    Field Meaning
    requirements Requested capability, existing binding or requested/unbound, selected instance/state
    existing / additional Existing/shared/stopped resources versus declared newly needed resources
    dependencies Selected dependency IDs; null is unverifiable, [] is verified none
    unused Informational IDs outside this request and without bindings; never removal authority
    scope / ownership / shared / consumers Existing ownership and binding count; no invented app counts
    memory_bytes / containers measured/estimated/unknown; values require nonnegative quantity and source
    core / complete Actual declared requirement and structural certainty; incomplete forbids unsafe mutation

    Unknown measurements may coexist with complete structural resolution. Estimates come from provider evidence, never guessed RAM/container promises or totals.

    Native backend placement replacement

    The existing operator placement policy can switch owned PostgreSQL/Valkey between shared and application-scoped realization through normal app apply. The desired footprint reports the destination as requested/unbound until verified apply publishes its binding. The concrete impact names original and destination owners and explicitly states that destination data is independent: old contents are not automatically copied. Original volumes, protected credentials and registry owners remain; a return to either placement reuses its retained storage. Unknown access or material continuity remains partial and requires the current acknowledgements.

    Applied and pending backend placements are realization metadata in the existing deployment GeneratedState, not authored application intent or another registry. Read-only canonical native inventory uses that owner projection, so changed operator policy cannot rewrite the previous realization during retry. An interrupted deployment protects both original and destination providers in the same Target consumer union, even when a sibling uses different current policy. Only actual destination/workload verification and old-runtime convergence permit publishing the new binding and clearing the pending projection. Other consumers retain shared runtime. One shared source split into named destinations is shown with all destination effects rather than a fabricated single replacement.

    This native placement path does not implement database content migration, OpenBao/Identity material handoff or unsupported external provider adapters.

    Automatic selection retains the deployment's selected placement after a one-shot operator override is removed, including capability disable/re-add. Explicit operator policy requests a new replacement; execution captures that selection and revalidates it against the acknowledged plan. Native PostgreSQL verification uses the retained container role and database. Native Valkey projects its default principal with the retained password; the protected shared ACL identity remains available for a return to shared placement. This principal change is an explicit plan consequence, not a credential reset.

    Target consumer union and add/remove/re-add

    Application --full-reset and remote application destruction acknowledge an aggregate baseharbor.provider-impact-scope/v1 owned by the selected deployment. The embedded provider plan alone cannot authorize deletion of the deployment's protected state. Both current acknowledgements are required; full reset also requires separate data-deletion consent. Changed publication/recovery ownership invalidates that consent. Unverified remote material/access is explicitly partial. Default remote destruction retains the existing publication, credentials and deployment owner, releases references only after verified container removal, and uses the protected retired intent for explicit reactivation. No unauthenticated access or successful material handoff is inferred from retained files.

    ResolveProviderPlan(snapshot, consumers, inventoryComplete) delegates every active consumer to ResolveFootprint and unions its full dependency closure. ConsumerIntent is an ephemeral projection of an existing app or independent management owner: Key, Active, Manifest, Preferences, DependencyRoots. Inactive entries retain identity and release bindings. The caller proves complete Target inventory from authoritative existing owners. Unaccounted bindings or unverifiable facts make the plan incomplete. Automatic convergence then preserves resources; intentional changes use the concrete consequence analysis and acknowledgement below.

    For an interrupted existing deployment, ConsumerIntent.RetainedIntents may project canonical applied/pending manifests under the SAME active system app ID and environment. Each uses the existing ResolveFootprint and relevant explicit preferences; requirements and provider/dependency closure are deduplicated into one consumer. Retained capability bindings are not released merely because the desired manifest no longer requests them. Runtime roots alone cannot preserve those bindings. The adapter supplies the observed dependency-root union for all canonical projections, including runtime permissions/consumption. Different or missing owners and inactive retained projections are invalid; unknown retained requirements keep inventory incomplete. Only verified lifecycle completion removes the retained projection and permits ordinary last-consumer convergence. No new identity, stored manifest owner or resolver is introduced.

    baseharbor.provider-plan/v1 contains per-consumer footprints, required provider IDs, released bindings and ownership/evidence-backed changes:

    Action Meaning
    add Materialize selected newly required realization
    reuse Keep realization required by an app, management consumer or dependency
    restart Reactivate an owned stopped required runtime
    stop Stop owned running runtime after the last consumer releases it
    remove-runtime Remove unneeded owned stopped runtime, preserving persistent data
    preserve External/BYO, foreign/unverifiable or incomplete inventory; never implicit deletion

    All changes carry PreserveData=true. These are plans, not permissions to invoke runtime mutation directly. Session 2 consumes them through existing plan -> preflight -> confirm -> apply -> verify. Preserve each data/recovery item with an individual reason; deletion requires explicit destructive consent and ownership proof. Automatic convergence preserves shared-still-used resources; intentional owned removal discloses every affected consumer. External/foreign infrastructure is never deleted. Repeat apply, interrupted retry and disable/re-enable converge idempotently. Capability removal belongs to v0.4.25, not a later reclamation project.

    CLI/human, JSON and MCP consume the same domain results and existing machine error/exit/authorization mappings. ResolutionError remains typed. Fixtures: internal/application/testdata/v0425-resolution.json; union invariants: internal/application/provider_union_test.go. The full provider/capability wizard is v0.4.26; #777 profile/host contracts below remain specification only.

    Provider changes: consequences and developer choice

    Developers may add, change, replace, disable and remove functionality, including choosing no continuation or complete deletion. Missing alternatives are disclosed consequences, not a permanent policy veto. An alternative-less, unknown or destructive outcome displays Achtung and requires two independently explicit acknowledgements of the concrete current plan. Data deletion additionally needs the existing distinct destructive authorization. Ordinary apply consent does not implicitly acknowledge either stage or delete data.

    DescribeProviderChanges(snapshot, union, requests, observation) enriches the same resolved consumer union. It neither resolves another provider graph nor mutates state. Direct provider operations and app/Target lifecycle adapters project their requests into this API. ProviderPlan.Impact carries the shared optional result; CLI, JSON/MCP and the later wizard consume the same baseharbor.provider-impact/v1. The existing plan/preflight/confirmation/apply/verify authorities execute it.

    Domain result Required meaning
    before / after Actual provider kind/instance, Target, scope/owner, locations and safe access/security references; proposed After is not an execution receipt
    dependencies / dependents / functions Affected apps and independent management/Console consumers; transitive dependency path, required/optional need, lost/changed/remaining function and observed expiry/validation behavior
    scenario Capability no longer requested; provider removed while still required; replacement; provider still used by another consumer; unused provider
    materials Individual current material and location, recovery references, intended retained/transferred/deleted/revoked/expired/invalidated/nonrecoverable/unknown disposition and destination/access
    prerequisites Concrete handoff, rebind or adapter-specific verification, support/evidence and consequence if unverified; no fictional fallback
    effects Applicable actual before/after availability, consistency, durability, retention, protocol, policy/TLS/HA, delivery, routing, reconnection or recovery changes from the adapter
    complete Knowledge completeness; false requires Achtung/two acknowledgements and does not prohibit the informed choice
    plan_id / revision Deterministic digest of consequences plus relevant binding/ownership/dependency state and existing-owner revision; materially changed facts invalidate old consent
    confirmations_required / destructive One ordinary stage, or two for alternative-less/unknown/destructive effects; explicit data-deletion consent remains separate

    ProviderPlan.ConsumerActivity includes explicitly inactive consumers from the same intents; past runtime use is not mistaken for current need. Incidental quantity sampling does not invalidate otherwise identical consequences.

    ProviderImpactObservation is an ephemeral projection of existing installation, deployment, runtime, registry, credential, certificate and recovery owners. IntegrationDescriptor.ChangeContract() supplies the shipped provider's function, material and operational inventory requirements. Iterate ReferenceIntegrations(); there is no second provider registry or fixed product warning engine. Unknown extension contracts and missing observations are visibly unknown. They are never reported generically safe or successfully continued.

    Consumer-specific Continuations prove a supported replacement and verified rebind. A running compatible replacement by itself is insufficient. Verify secure handoff/access before claiming continued function or deleting the old realization. If no handoff exists, the developer can instead acknowledge the resulting lost function twice and continue the requested removal. Retained inaccessible storage is recovery, not secret delivery, token issuance or certificate renewal. Do not write secrets to plaintext manifests, repositories, logs or an invented fallback. Intentional removal of required authentication shows the affected service/access as unavailable; it never silently enables unauthenticated management.

    Only actual OpenBao usages produce secret-policy, dynamic-credential or PKI consequences. Lease expiry/revocation and downstream validity require real evidence; exporting a credential is not continuity proof. Current token/certificate validity is distinct from future issuance, renewal, JWKS refresh, sessions and revocation. Observed offline validation and expiry may produce changed rather than instantly unavailable validation. Do not invent uniformly invalid tokens or certificates. Caches, jobs, sessions, queues and telemetry buffers are not automatically considered disposable. Unknown retention/location remains unknown. Retained material stays at its actual location; deleted material says no destination; deletion. Ownership and authorized references must be proven by existing owners. Two acknowledgements grant no authority over somebody else's external resources.

    Multiple changes form one aggregate plan. Removing a replacement's dependency invalidates its continuation; stopping SQL identifies dependent Identity/broker functions. Scoped unbinding preserves the other consumers' runtime and reports which consumer loses access. Automatic last-consumer convergence preserves data; explicit fully destructive requests inventory every affected item before consent.

    ValidateProviderChangeConsent checks both stages, current plan digest and separate deletion consent. Existing interactive and noninteractive authority adapters collect acknowledgements; the interactive adapter asks separately for data deletion after the required plan acknowledgements. Declining that question or reaching EOF does not authorize deletion. Machine consent supplies delete_data independently. No extra CLI flags or independent frontend policy engine. Always replan from current authoritative observations immediately before mutation. A stale plan must be displayed and acknowledged again. Technical inability to execute an unsupported handoff is reported honestly, not disguised as successful relocation.

    RecordProviderChangeResult accepts actual verified execution outcomes, reports complete/partial/failed state, actual final locations and every pending operation. Actual affected-function outcomes require their own consumer/root/function verification and evidence; a runtime stop alone is not a login/lease/PKI receipt. It never copies proposed After into an accomplished result. Missing material, changed disposition or missing recovery evidence remains a partial failure. PendingProviderChanges preserves the original consumer scope and returns only unfinished operations/material actions for the existing idempotent replan/retry lifecycle. It is not a scheduler or new persistence authority. Interrupted handoff, rollback/reconnection work and irreversible effects remain visible in receipts.

    Global registration changes across Targets

    A global external-provider registration has its existing registration owner, not an invented runtime Target. ComposeProviderImpactScope composes unchanged ProviderImpactPlan outputs for every observed Target. The adapter inventories configured and retained Target state, applied and interrupted deployment bindings, and independent management consumers before declaring the scope complete. This projection performs no additional resolution and creates no state owner.

    The aggregate PlanID binds the registration owner/content revision, all Target plans and their actual consequences. Leaf consent cannot approve the whole scope; changed registration, Target membership, binding or consequence requires fresh consent. Countdown samples alone do not invalidate unchanged absolute validity. Unknown/incomplete or destructive scope shows Achtung and uses the same two acknowledgements and separate destructive consent as single-Target changes.

    ProviderScopeOwner.destructive marks permanent deletion of the aggregate owner itself, including installation configuration/state when no provider leaf exists. It contributes to the scope revision and requires separate delete_data consent in addition to both current-plan acknowledgements. Omitting this optional field retains the existing non-destructive owner semantics.

    RecordProviderImpactScopeResult validates each Target's execution through the existing receipt authority. Registration-entry deletion alone never proves consumer reconfiguration or all-Target success. Missing/unknown owner or Target receipts remain partial; preserved registration/ownership supports fresh replan and retry. External infrastructure, data and credentials remain outside local registration-removal authority. The runtime/transport adapter must still observe, authorize, revalidate, execute and verify each requested operation.

    Existing ancillary realizations

    ResolutionSnapshot.Ancillary observes existing gateway/sidecar realizations from runtime/route owners. ProviderFact.Ancillary and OwnerReference identify them; ProviderFootprint and impact realizations retain that distinction. This is an ephemeral inventory alongside the existing registry, not another registration or state owner. Ancillary Provider.Capabilities is empty: Automatic does not offer these as application providers, and explicit capability selection is incompatible. The same dependency closure includes their actual IDs only through verified provider dependencies or consumer roots. The same union accounts for shared users, owned retirement, unknown state and impact. No unconditional sidecar/Core package.

    A Target-owned shared gateway uses its real existing installation/route owner and no fabricated application UUID. It does not claim that Caddy's selectable provider integration supports generic Shared placement. App sidecars retain their actual system-owned app ID. The native executor uses Shared scope and its single existing Target project owner (RuntimeExecutorDependency); every app/management root references that same physical ID. It is never owned by one app or counted through independent app aliases. The per-app broker uses Application scope.

    Ordinary declared workload components use distinct runtime-workload ancillary metadata (RuntimeWorkloadDependency), including zero-capability apps. They are not privileged executors or selectable capability providers. Actual run/access, in-flight work, configuration and volume consequences require observation; a matching project label does not authorize an undeclared component. Runtime broker/executor metadata describes actual authorization, credential, execution/control and in-flight effects; usages still require observation.

    Derived consumer actions and lifecycle coverage

    The lifecycle matrix covers all declared functions and material kinds for all fourteen reference integrations, for add/resume/update, stop, destroy, remove-runtime, disable/unbind, rebind and replacement. External runtime mutation is rejected for lack of authority; an intentional local loss of access remains possible. Declaration tests are not native execution acceptance.

    ProviderImpactObservation.ConsumerActions projects supported operations of the existing consumer adapter. ProviderChangeRequest.ConsumerActions explicitly selects their IDs. Each action identifies consumer/root/function, actual modes, selected function outcome, dependencies, credential references and locations, and credential owner, synchronization and rotation before/after. An unselected local authentication mode never becomes a fallback. Unsupported/unverified actions remain unknown and can be explicitly accepted; they are never reported working. Selected action dependencies are checked through the existing transitive provider graph on the actual Target. A stopped, removed, foreign, unobserved or cyclic prerequisite, or an unknown dependency closure, makes continuation unknown even when the action's directly named provider is running. Aggregate changes cannot claim continuity through a dependency they interrupt. Replacement providers use the same check for their entire dependency closure. Each node must be registered or canonically ancillary on the selected Target, observed running, supported and verified with realization evidence; a running fact without that observation is insufficient. A planned add/resume does not prove executed availability. Reobserve after actual recovery and acknowledge the fresh plan before claiming continuation. Unverified replacement remains partial and can still be deliberately accepted with the required confirmations. Credential references stay identical unless their change is explicitly selected. Adapters additionally verify that retained values and established synchronization remain consistent; this pure result neither reads nor regenerates passwords. OIDC ownership is distinct from native database/service credentials. For example, Prometheus uses existing devaccess credentials and native basic authentication; SeaweedFS keeps native admin references in its existing protected runtime owner. Identity removal must not reset either merely because an issuer disappears.

    ObservedAt and actual ValidUntil/ExpiresAt derive remaining_validity_seconds for tokens, certificates and leases. Missing current validity evidence stays unknown; expired offline validation is unavailable. Retained certificate files imply neither indefinite TLS nor future renewal.

    Protected X.509 files expose valid_from and expires_at from the parsed certificates. A bundle uses the latest start and earliest expiry of every certificate, including when a key block precedes them. The current observation distinguishes not-yet-valid, within-window and expired material. This proves time bounds only; chain trust, revocation, endpoint access and future renewal still need actual verification. Key contents and certificate subjects are not emitted.

    The consent digest ignores only the changing remaining-validity countdown; absolute expiry, actual expired/valid consequences and changed material still require fresh consent. ProviderMaterial.Retention separately verifies survival of stop and runtime removal for meaningful transient state: cache, sessions, jobs, queues/messages, in-flight work, telemetry buffers, leases and tokens. A volume alone is insufficient; verified loss is individually nonrecoverable and requires destructive consent.

    Actual execution receipts must account for each affected function, selected consumer action and operational effect. Missing reconfiguration or changed owner, credential reference, synchronization, rotation or guarantee remains partial/failed. Retry retains selected consumer actions and obtains consent against the fresh plan. A material step is complete for retry only when its verified disposition, final location, delivery/access references and preserved recovery references all match; the correct destination alone cannot hide an incomplete secure handoff. Final receipts and retry exclusion use the same material checks. An unknown material disposition remains unfinished even when the adapter verifies that uncertainty; acknowledging the change does not establish material completion. Incomplete authoritative inventory keeps the overall receipt partial, including when no known operation remains. Verified individual operations are still applied and excluded from replay; the existing lifecycle must observe and replan the unknown inventory before it can establish overall completion. Recovery references follow explicitly selected owned backup transfers/deletions across the aggregate plan. A complete owned deletion may include its inventoried backups with destructive consent; unselected or foreign recovery stays protected.

    Tempo — traces/tempo_ha.go, topology and PKI reload owner Actual trace ingest/query consumers, buffers/store/index and retention; rebind delivery/query routes and verify TLS/access; distinguish sampling/delivery gaps from deleted history
    Ancillary broker/executor — runtimebroker/compose_render.go, existing executor/runtime owners Existing policy, service credentials/certificates and in-flight control/work consumers; authorization and expiry/renewal dependencies; verify selected reconnect/control operation; never register these sidecars as new capability offers

    The same dependency graph propagates database, gateway, secret/PKI and authentication changes to every actual direct and transitive consumer. Selected transition dependencies are evaluated against aggregate changes: removing the newly selected mode's dependency cannot be reported as a working continuation. Runtime mutation path inventory and native proof of these actions are Session 2's acceptance duty.

    #777 portable connection-profile transport (contract only)

    This is an import/export transport envelope for later #777 implementation, not a replacement for existing development.StackProfile (development/v1), Target configuration, access storage or provider registry. No implementation, file creation or onboarding UI is delivered by this specification.

    Envelope field Contract
    version Exact baseharbor.connection-profile/v1; reject unsupported versions
    name Human alias; never an identity or authorization claim
    core.installation_id / core.url Existing canonical Core UUID and HTTPS management endpoint; verify server identity
    trust.ca_pem / trust.sha256 One public PEM CA certificate and its DER SHA-256 fingerprint; verify agreement and require an independently authorized trust decision
    targets List of portable descriptors: name, tenant_id, runtime_provider, scope; retain existing Target semantics
    access OIDC issuer, client_id and scopes only; no imported authorization claims
    expires_at Optional transport expiry; reject expired enrollment material
    extensions Namespaced future optional fields; no change to existing required semantics

    An example transport describes a Core, trust and selected Targets; it does not contain application intent, provider credentials or a new authoritative state. Targets reference a Core where applicable; profiles are not Targets and do not merge dev/prod installations. Core-less local operation needs no imported profile.

    Exclude passwords, private keys, refresh/access tokens, AppRole secrets, recovery material, local sockets/engine contexts, checkout paths and local state roots. Authentication/enrollment artifacts use existing protected access owners after explicit login/enrollment; importing descriptors cannot grant a role, claim a foreign deployment, activate arbitrary endpoints or start resources. Imported public trust alone cannot self-authorize a server. Verify Core UUID, HTTPS, issuer, tenant and selected Target before writing existing config/access owners.

    Import is parse -> validate -> resolve references/conflicts -> show diff -> explicit authorization -> existing owner transaction -> verification. Same identity plus same content is idempotent; same alias with another identity is a conflict. Partial writes must be rolled back or exposed as incomplete with a recovery action, never reported as successful. Export is read-only and preserves portable identity without secret/local fields. Host-local values are resolved after import through existing local config. Implementations arrive in later releases and require schema/transaction conformance against these semantics.

    Host Platform boundary (contract only)

    The semantic boundary baseharbor.host-platform/v1 is adapter capability negotiation, not a new runtime, registry, scheduler or multi-OS implementation.

    Responsibility Boundary
    Platform/feature detection Host facts and supported/unsupported/unverifiable outcome with evidence
    Engine selection Actual runtime endpoint, context and rootless/rootful mode; no silent fallback to privileged engine
    Local paths / source access Host-local mapping stays outside portable manifest/profile; deterministic failure for unavailable source
    Credential / trust access Existing protected owner and explicit trust changes; no automatic security downgrade
    Browser / PTY / shell Host operation support and typed unavailable result; preserve non-TTY/EOF/cancel contracts
    Runtime execution Existing RuntimeProvider owns workload lifecycle and provider verification
    Enrollment / remote authority Existing Core/Node authority and mTLS; local host adapter cannot mint remote authority

    Linux, WSL2 and Darwin implementations are later releases. Adapters report real support instead of pretending an unsupported host operation succeeded. Host paths, sockets and platform defaults must not change ApplicationID, capability intent, Target ownership, footprint evidence or machine error semantics. No host probing with persistent effects from inspection/footprint.

    Normative offline schemas: contracts/footprint/v1/footprint.schema.json and contracts/connection-profile/v1/profile.schema.json. Profile shape validation never proves valid CA material, fingerprint agreement, expiry, tenant uniqueness or authorization; later importers must enforce these semantic checks and allow only reviewed non-secret extensions.

    Local workload authorization

    A portable test or prod environment does not by itself request operator OIDC. An actual local CLI/JSON or local stdio invocation may use verified local-runtime authority for one application operation on one Target and environment. The adapter observes the selected local Docker engine/binding or native rootless Linux Podman info selection. This authority is invocation context, not an OIDC principal, portable input or another identity registry.

    Explicit stored/environment operator OIDC policy, an independent management installation (including a valid partial owner), tenant scope, remote execution and HTTP retain their existing authenticated boundaries. HTTP strips inherited local authority. Unknown engine/owner state never fabricates a local proof. Application authorization may provision its genuine provider dependencies; explicit management commands keep their own authorization. Local authority does not grant provider-change confirmations or destructive data consent. The two current-plan acknowledgements remain separate.

    The implementation has domain/adapter negative tests. Actual local production CLI and stdio runtime acceptance remains required on the qualified candidate.

    Fresh execution dependencies and credential delivery

    ProviderImpact.ContinuationDependencies binds the selected replacement and consumer actions to the existing Target graph, including transitive ancillary owners. ProviderExecutionOutcome.ContinuationDependencies supplies fresh observations of the same identities and edges after execution. Missing, stopped, unsupported, unverified, foreign or changed owners/edges cannot be reported as a completed continuation. ObserveProviderContinuationDependencies is read-only; it consumes existing registry/ancillary facts and observations, never schedules recovery or creates another state owner. A changed graph needs fresh replan/consent. Failed result evidence remains visible and pending retry.

    Native provider observations require every selected canonical container to be present and running, with healthy status when a health check exists. A single running HA member does not qualify the whole declared module. This observation proves process/health inventory only, not quorum, authenticated access, data continuity or unlisted sidecar completeness.

    Canonical profile-only recovery helpers are retained in the complete owned inventory but are not continuously required processes. One-shot prerequisites declared with service_completed_successfully and restart: no require actual successful completion instead of running state. Docker verifies the owned exited container; Quadlet may retain that evidence in its current canonical systemd unit after removing the container. Missing, failed, foreign, stale or overridden completion evidence leaves availability unverified. Observing completion never starts or repairs a task, and full lifecycle resource selection remains unchanged.

    Normal reapply must not regenerate a missing credential in an existing protected native credential group. SQL, Valkey, RabbitMQ, MongoDB and S3 groups, their independent logical instances and supported management credentials are checked before initial-value generation. Existing runtime declarations, binding material or retained group keys distinguish continuation from a new independent group. Incomplete retained material requires recovery through its original owner; the failed reapply leaves the owner unchanged and never includes secret values in diagnostics. New independent instances and intentional capability retirement remain possible. This guard does not prove live authentication, migrate data or provide a replacement authentication mode.

    External OIDC reapply without repeated secret/CA inputs reuses protected material only for the same provider, issuer and client. It does not regenerate credentials, forward them to another authority or silently change a confidential client to a public client. A different authority requires explicit replacement material where retained confidential credentials/trust exist. Unsupported credential/trust removal remains an explicit technical limitation; it does not assert that a public-client or system-trust fallback was implemented.

    Identity binding verification compares the host and workload client/credential/ trust projections with runtime and application environment references. Divergence or stale references are failures without secret values in errors. This proves consistent delivery, not user login, token/refresh validity, revocation or future renewal. Their actual access checks remain separate requirements.

    Installation destruction child authority

    The installation consequence scope contains each selected application reset scope. The aggregate acknowledgements and separate data decision delegate only to those exact destructive application-deployment scopes after revalidation. They cannot authorize another operation, a changed owner, an undisplayed child or an unknown child scope. Aggregate revision uses semantic child scope IDs rather than live footprint samples. A failed child retains its affected Target and protected retry owner; lower fallback or Target cleanup cannot bypass that child authority. Native operation failures remain partial failures requiring a fresh observed plan and acknowledgements before retry.
