    Machine Interface v1

    Scope

    CLI JSON and MCP expose the same underlying BaseHarbor semantic state.

    The machine interface is an adapter over the shared BaseHarbor lifecycle. It is not a second orchestration path.

    Lifecycle surface

    The v1 semantic operation set covers the currently supported application lifecycle:

    inspect
plan
apply
status
doctor
observe
evidence
update
repair
backup
restore
destroy
policy.check
policy.explain

    apply represents the semantic converge operation; MCP does not mirror every human CLI alias or presentation command.

    Safety classes

    Every machine operation declares one of:

    • read_only;
    • mutating;
    • destructive.

    Destructive operations declare whether explicit approval is required. destroy requires explicit approval before any mutation.

    Unknown or unresolved safety requirements fail closed.

    Machine operator authorization

    Every machine operation is authorized below the presentation layer through one transport-neutral decision model.

    The decision binds:

    effective actor/principal
        +
operation + safety class
        +
application/environment/target/workspace context
        ↓
allow / deny

    Development uses explicit trusted-local actor semantics. Managed environments fail closed when the required authenticated operator principal is absent or invalid. The decision is secret-safe and exposes only stable actor identity/provenance fields, never tokens or private credential material.

    MCP, CLI/JSON and future HTTP/Console adapters must consume the same authorization boundary; no adapter may define a separate RBAC model.

    Non-interactive behavior

    Machine operations never depend on an interactive terminal.

    When a lifecycle action requires unresolved developer/operator input, the operation returns a structured actionable error instead of prompting or guessing. Examples include:

    • missing required application secrets;
    • an explicit recovery choice before updating durable state;
    • destructive approval;
    • unsupported or ambiguous ownership state;
    • policy denial.

    Secret handling

    Passwords, tokens, private keys and secret values MUST NOT be accepted or returned through normal machine result fields.

    Backup and restore accept an owner-only local password-file reference rather than the plaintext password.

    Credential-bearing URLs MUST NOT be returned as normal machine output.

    Requirements

    • Machine results MUST be versioned.
    • Errors MUST be structured and secret-safe.
    • CLI, JSON and MCP MUST reuse the same lifecycle semantics.
    • Interfaces MUST NOT bypass authorization, policy, ownership, preflight, reconciliation or verification.
    • Managed-environment machine operations MUST fail closed without the required authenticated operator identity.
    • Mutations MUST preserve the plan -> preflight -> apply -> verify lifecycle.
    • Destructive operations MUST preserve explicit safety/approval semantics.
    • MCP MUST NOT expose generic shell, Docker, Compose, Podman or provider-native execution as a substitute for BaseHarbor lifecycle operations.
    • Runtime-provider implementation details MUST NOT become MCP semantics.
    • Unsupported lifecycle operations MUST return an explicit typed result.
    • Docker/Compose and Podman/Quadlet MUST expose the same agent-facing semantic operations where the lifecycle operation is supported.

    The typed machine operation registry in internal/machine is the authoritative operation/safety definition.

    Core and installation destruction consent

    control-plane.destroy and installation.destroy accept provider_change_consent in addition to ordinary approval. Execution requires both stages for the current aggregate scope. Installation destruction and selected Core volume deletion additionally require independent consent delete_data=true. --yes or approval=true alone cannot authorize destruction. The CLI preview and typed denial expose the current concrete scope; JSON reports include provider_change_plan. Changed configuration bytes, consumer registrations, protected Core owner bytes, Target membership or native resource inventory invalidate prior consent before cleanup starts. Retained unbound application providers and protected management consumers require their own authorization.

    Selected-Core destruction accepts delete_data as an optional selection. Its absence removes only canonical Core containers/startup units and retains volumes, networks, protected owners, consumer registrations and other providers/workloads. Active bindings are consequences requiring two current-plan acknowledgements, not a permanent removal veto. Selecting data deletion changes the plan and also requires independent provider_change_consent.delete_data=true. Partial native cleanup retains owners for fresh replan/retry; its consequence receipt remains partial until all actual consumer functions are separately verified.

    Application stop through HTTP

    Core discovery now includes the existing app.stop operation. Its HTTP adapter uses the same selected deployment, provider consequence scope, independent plan-bound acknowledgements, ownership revalidation and actual stop result as CLI/JSON/MCP. The input accepts provider_change_consent; generic approval cannot substitute either required stage. A Console must acknowledge the outer baseharbor.provider-impact-scope/v1 plan for that selected deployment, rather than one of its leaf plans. Foreign selectors and ambiguous consent objects are rejected before the runtime operation. Retained owners do not establish continued consumer functionality; incomplete consequences remain partial.

    Transport source checks do not replace source-matched authenticated browser or native runtime qualification; final v0.4.25 ecosystem acceptance remains open.

    Selected Core stop

    control-plane.stop accepts target and optional provider_change_consent with the same current scope plan ID and independent acknowledgement stages as other provider changes. Generic approval and --yes do not supply these stages. The local Core-mode baha down --json and MCP operation share the selected PostgreSQL/OpenBao stop authority and typed result: target, state, runtime and provider_change_result. Other providers, workloads and connectivity stay requested and running. The native verifier checks selected process state, persistent resource retention and consolidated-project sibling preservation. The existing native adapter may remove selected stopped containers; the result inventories actual removed and retained resources without claiming data deletion. The current plan binds observed native process identities/state and internal image identity revisions as well as protected file bytes; restart/image changes invalidate earlier acknowledgement. A stopped runtime does not establish complete consumer/secret/PKI/session continuity; that consequence result remains partial where unverified. There is no HTTP Core-stop adapter or authenticated browser acceptance implied by this seam.
