## 2. Timeout-Wert-Begründung (30s)
- **Herkunft**: `30*time.Second` ist eine **fixe Go-Konstante** im Commit; keine Konfiguration,
  kein Env-Var, kein Per-Target-Wert, keine Herleitung aus Messungen. Der Commit-Meldung und dem
  Code ist kein Grund für 30 s zu entnehmen.
- **Kette zum blockierenden Leaf-Call**: `Step` (app_wizard_controller.go:229 Needs-Next, :252 Preview-Yes)
  ruft `freshFacts(ctx, d)`. `freshFacts` wrappt `refresh`. `refresh` (app_edit.go:79 / app_new_wizard.go:97)
  ruft `authorities.Read(refreshCtx)` bzw. `readGuidedApplicationContext(refreshCtx, …)` +
  `buildResolvedApplicationPlan(refreshCtx, …)`. `readGuidedApplicationContext` ruft
  `observeApplicationProviderFacts(ctx, …)` — eine **serielle** Kette aus `observeIdentity/Broker/SharedBackend/
  ApplicationBroker` + je Owner `observeStandalone/NativeBackend/Exposure`. Jede dieser Funktionen ruft
  `detectRuntimeForTarget` → `provider.InspectProjectResources(ctx)` / `provider.ListRuntimeContainers(ctx)`
  → `internal/runtime/compose_resources.go:directOutput` → `exec.CommandContext(ctx, engine, …).Run()`.
  Der `ctx` (also `refreshCtx`) erreicht also **wirklich** die blockierenden `exec`-Leaf-Calls. Der Guard
  wirkt mechanisch, wenn ein Runtime-Aufruf hängen bleibt. ✔
- **Sinnhaftigkeit pro Runtime**: die fixen 30 s gelten **uniform** für Docker und Podman. In Cluster B
  wurden 45 s (Podman-Start-Stall) bzw. 90 s (no-output-Fenster) als **legitim** gemessen. 30 s liegt
  **unter** diesen Werten.
  - **Docker**: lokaler Daemon antwortet normal schnell; 30 s sind hier großzügig, kein Problem.
  - **Podman/rootless**: `podman`-CLI plus CNI- und Rootless-Setup können laut Cluster-B-Evidenz 45 s
    Startstall haben; eine einzelne legitime Preview kann damit >30 s brauchen. Auf einem überladenen CI-
    Runner (shared runner, no output >90 s) ist 30 s zu knapp: „langsam aber erfolgreich" kippt zu
    „DeadlineExceeded".
  → **Befund**: der 30s-Wert ist auf Docker harmlos, auf überladenen Podman-Runnern **zu aggressiv**;
    es fehlt eine runtime-spezifische oder messungsbasierte Herleitung (f30-Follow-up: per-Provider-bounded
    Context + Heartbeat). Dies ist **kein** Blocker, aber eine begründete Verbesserungsmöglichkeit.

## 4. Race-Risiken / was, wenn Facts-Refresh spät eintrifft
- `context.WithTimeout(ctx, 30s)` erzeugt `refreshCtx`, das `defer refreshCancel()` stellt die Cancel-Call
  sicher. Nach `w.refresh(refreshCtx, d)` prüft `freshFacts` **zusätzlich** `if err := ctx.Err(); err != nil`
  — also den **Parent**-Context (nicht den Timeout-Context). Das ist sauber:
  - Kommt der Refresh **spät** ein (z. B. 31 s), schlägt der `WithTimeout`-Deadline durch → `refreshCtx.Err()
    == DeadlineExceeded` → `refresh` gibt Error zurück → `freshFacts` gibt Error zurück (Ruhe, kein nil-
    Ergebnis). **Kein Race**: Der Timeout gewinnt sauber, es wird kein halber/stale-Footprint zurückgegeben.
- Trifft der Refresh **vor** 30 s ein (normaler Fall): kein Cancel, `ctx.Err()==nil`, normaler Return.
- **Beobachtung**: Der Guard fängt nur **indefinites Blockieren** ab (silent >90 s Hang). Er macht aus dem
  „stillen Hang" einen **„Fehler statt Stille"** (DeadlineExceeded → Wizard wird abgebrochen, nicht hängen
  bleiben). Er **beseitigt nicht** die Root-Ursache (serielle, unbedingte Provider-Enumeration ohne
  Heartbeat/per-Provider-Bounding). Auf überladenen Runnern ist das Risiko, dass **legitime** Preview >30 s
  dauert und nun als Fehler durchgeht — das ist das B1-Vorbehalt aus F34.
- **Kein Datenrace / kein Data-Race auf shared state**: `refreshCtx`/`refreshCancel` sind lokal in
  `freshFacts`, kein Geteiltes. Der Parent `ctx` wird nicht mutiert. ✔
- **Kein zweiter Owner / kein Parallel-Schreiben**: dieser Turn ist rein read-only; Kandidaten-Baum wurde
  **nicht** angefasst (`git status --porcelain` clean), nur diese Evidence-Datei geschrieben.
