# object-storage.s3/v1

`object-storage.s3/v1` is BaseHarbor's portable S3-compatible object-storage capability.

Applications request logical buckets. They do not name SeaweedFS, Ceph RGW, AWS S3, a host port, a provider-native bucket name, an IAM user, an access key or a storage topology.

## Required semantics

- stable logical bucket identity per application/name;
- S3-compatible endpoint semantics suitable for normal AWS/S3 SDKs;
- authenticated bucket-scoped access credentials or secure credential references;
- bucket isolation across applications and logical buckets;
- object `Put`, `Get` and `Delete` for the current v1 contract;
- bucket listing required for normal application operation;
- real authenticated Put/Get verification before readiness;
- provider-specific bucket/user/policy identity remains provider state;
- provider-internal object-storage dependencies must not create application-facing S3 resources unless the application separately requests this capability.

## Binding

The provider-neutral binding contains the logical bucket name plus `secure-binding/v1` metadata.

Concrete endpoint, provider-native bucket name, region selection and credential values are materialized only at the trusted runtime/application-binding boundary.

Current Compose applications receive standard S3/AWS-compatible configuration, including an endpoint, bucket, region and credentials. Credential-bearing output is masked by default in normal CLI inspection.

## Security

Each managed logical bucket receives separate credentials scoped only to that bucket. Shared provider infrastructure does not imply shared bucket authorization.

Plaintext access keys or secret keys are forbidden in capability metadata, provider diagnostics and portable application intent.

## Provider lifecycle

Providers use the shared BaseHarbor lifecycle:

```text
resolve -> preflight -> provision -> bind -> verify
```

Preflight performs no mutation. Verification performs a real authenticated object Put/Get flow and removes the probe object afterwards.

## Current reference provider

SeaweedFS is the current lazy shared Compose reference provider. It is materialized only when at least one application explicitly requests `object-storage.s3/v1`.

Application buckets remain application-owned logical resources. The shared provider runtime is platform-owned and survives `baha app down` / destruction of another application's buckets.

## Compatible provider direction

The same capability may be implemented by Ceph RGW, AWS S3 or another conforming S3-compatible provider without changing application intent. Provider selection, placement and credentials remain protected operator/deployment state.

## Out of scope for v1

- application-requested replication/topology classes;
- public S3 endpoint exposure;
- provider-specific lifecycle/tiering/versioning configuration;
- object-storage contents in BaseHarbor encrypted application backup/restore;
- provider-internal S3 dependencies being promoted implicitly to application capabilities.
