# secure-binding/v1

BaseHarbor secure bindings describe **how a workload is securely connected to a capability** without putting secret material or provider-specific security internals into portable application intent.

This is a shared binding contract, not an application capability by itself.

## Relationship to Service Binding Specification 1.1

`secure-binding/v1` does not define an alternative vocabulary for ordinary service connection outputs.

When connection material has Service Binding 1.1 semantics, BaseHarbor uses the standard well-known names:

```text
type
provider
host
port
uri
username
password
certificates
private-key
```

This specification covers BaseHarbor-specific security/lifecycle metadata that Service Binding does not define: identity references, opaque credential/secret references, authorization metadata, renewal, rotation and revocation support.

Secret-bearing standard entries may resolve from protected references only at the trusted workload projection boundary. They remain forbidden in normal diagnostics, registry state and portable application intent.

## Required semantics

A secure binding may carry:

- workload/application identity;
- credential references;
- trust material references such as CA bundles;
- authorization metadata;
- secret references;
- security lifecycle support declarations for renewal, rotation and revocation;
- machine-readable security diagnostics.

Only references and non-secret metadata may cross this boundary.

## Workload identity

Where an existing standards-based identity exists, providers should preserve it rather than inventing a BaseHarbor-only identity format.

The current Compose/OpenBao runtime identity uses a SPIFFE URI:

```text
spiffe://baseharbor/apps/<application>/<environment>
```

The secure binding also carries an opaque BaseHarbor identity reference so runtimes/providers can resolve material at the trusted boundary.

## Credentials and secret references

Credential and secret entries contain:

- a logical name;
- an opaque reference.

They never contain passwords, tokens, private keys, AppRole SecretIDs, connection strings with credentials or secret values.

Provider-specific locations such as OpenBao KV paths, AppRole names, PKI mount paths, Kubernetes Secret names or cloud-secret identifiers remain provider/deployment state.

## Trust material

Trust entries carry an opaque reference plus optional non-secret format metadata such as `x509-pem`.

Private keys are credentials/secret material and are never trust metadata.

## Authorization

Authorization metadata describes the least-privilege intent required by the workload, for example:

```text
audience: managed-secrets
scopes:
  - secrets.read
```

Providers translate this into their native policy/ACL model. Product-specific policy names do not become part of the portable application contract.

## Lifecycle declaration

Bindings declare whether their security material is:

- renewable;
- rotatable;
- revocable.

The declaration describes provider/runtime support. Cross-provider rotation orchestration and zero-downtime completion are broader lifecycle work and are not implied by this revision.

## Validation and fail-closed behavior

Secure binding metadata is validated before provider preflight or mutation.

Invalid references, duplicate logical names, malformed authorization metadata or invalid diagnostics fail closed before provider lifecycle hooks run.

## Isolation

Application and environment identity are part of the logical binding scope. Two applications or two environments of the same application must not share identity or credential references unless an explicit future platform policy defines a shared identity model.

Shared provider infrastructure does not imply shared authorization.

## Current reference implementation

The existing BaseHarbor Compose security path remains authoritative:

- OpenBao provides the current shared secret/trust implementation with application isolation;
- application-scoped runtime authentication remains protected state;
- runtime broker access is application scoped;
- mTLS client identity uses the SPIFFE URI above;
- CA/certificate/key material remains protected runtime/provider state;
- required/generated secrets retain their existing delivery and restore behavior.

v0.4.5 extracts these semantics into the shared binding model; it does not replace OpenBao, introduce a new secret store, or change Manifest v1.

## Provider protocol mapping

`baseharbor.provider/v1` exposes the same semantics through `WorkloadBinding.security`.

External providers receive only provider-neutral references and metadata. Resolution of referenced credential/trust/secret material happens at the trusted BaseHarbor/provider boundary.

## Out of scope

This specification does not define:

- human login, OIDC, RBAC, MFA, JIT elevation or breakglass;
- a new public application manifest schema;
- a dynamic external provider loader;
- generic certificate issuance for public application ingress;
- full cross-provider rotation orchestration.
